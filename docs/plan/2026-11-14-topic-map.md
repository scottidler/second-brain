# Design Document: Topic Map

**Author:** Scott Idler
**Date:** 2026-11-14
**Status:** Approved (amended 2026-11-14 after the implementation audit: Phases 6-7 added)
**Review Passes Completed:** 5/5 (draft; correctness: sample table and label rule made to match the spike output, criteria no longer pin k; clarity: terms block, filter semantics; edge cases: migration, rename, swap isolation, value risk; voice/lint) + panel round 1 folded in (2 must-fix, 10 cheap-win, 4 defer; 3 Architect disputes sent back and conceded)

## Summary

Cluster the vault's summary embeddings with `e-means` (spherical k-means) into `k` topics, store one topic per note plus the centroids in oracle's index, and expose them through oracle. Cortex trains on an operator's order and assigns new notes against frozen centroids on a daemon tick; oracle only reads. A spike on ripr's index (2026-11-14) shows the topics read as topics at k=64 and that two training runs disagree on which notes belong together (adjusted Rand index 0.51 across seeds), which is why centroids are frozen.

### Problem

- Oracle returns ranked notes. It has no view of what subjects the vault holds below the tag level.
- `tag_brief` on a blanket tag returns a count and recent notes. 543 `llm` notes are one bucket.
- `vault_overview` lists the top 20 tags, which are the blanket tags.
- An agent that wants "the RAG notes" or "the Rust tutorials" has to guess a query; it cannot browse.

### Goals

- One topic per in-scope note, stored in oracle's index, readable by oracle with no inference.
- Topic assignment is sticky: a note keeps its topic until its own summary is re-embedded or an operator orders a retrain.
- Topic labels are deterministic and LLM-free.
- Oracle exposes: the topic list, the topics inside a tag, and the notes inside a topic.

### Non-Goals

- **A search index.** Excluded. Topics never gate or prune `search_vector`; `2026-06-05-graph-augmented-memory.md:303` stands. Its stated reason (SIMD-hungry native libraries) does not apply to `e-means`, which is pure Rust with no `build.rs`, but nothing here needs an index.
- **A per-topic cap in `run_pipeline` (result diversity).** Parked. Revisit when topics are live and `sb oracle eval` shows redundant top-K hits. Seam: `apply_exclude_filters` (`oracle/src/server/pipeline.rs`).
- **Eval coverage by topic in `sb oracle eval`.** Parked. Revisit with the same trigger.
- **LLM-written topic names.** Parked. Revisit if Scott rules the tag-lift labels unreadable.
- **A topic hierarchy or per-tag sub-clustering.** Parked. One flat level; revisit if one level of k cannot serve both the vault view and the tag view.
- **Topic hub notes in the vault.** Excluded. Topics are index data; nothing is written to the vault.
- **Clustering `transcript-chunk` rows.** Excluded. A topic is a property of a note; the summary row is the note.
- **Automatic retraining.** Excluded. See Resolved Decisions.

## Proposed Solution

### Overview

- `vault` owns the primitive (`vault::kmeans`, wraps `e-means`) and the storage (`vault::search::topic`).
- `cortex` is the only writer: `sb cortex topics --train` makes a generation; `sb cortex topics` and a daemon tick assign unassigned notes to the nearest frozen centroid.
- `oracle` reads: a `topic_map` tool, a `topics` key in `tag_brief`, a status block in `vault_overview`.
- Until an operator runs `--train` once, there is no generation, the tick does nothing and every reader says so. That is the opt-in.

Terms:

- **topic**: one centroid and the notes nearest to it. Identified by an integer `0..k-1`.
- **generation**: one training run's output: `k` centroids plus every assignment made against them. An integer that `--train` increments. Topic ids mean something only inside one generation.
- **assign**: give a note the topic of its nearest centroid, without moving any centroid.
- **lift**: how over-represented a tag is in a topic against the whole assigned set. 1.0 = no more common than anywhere else.

What the numbers decide:

- Training cost is nothing (15 ms at 2 threads). Cost never forces a design choice here.
- A retrain changes membership, and no renumbering fixes that: a different seed agrees at ARI 0.51, and a warm start with revival off still lands at ARI 0.535 against where it started (k=64). Topic ids cannot survive a retrain, so centroids are frozen and a retrain is an operator's order.
- Our own assignment loop agrees with `e-means` on this data, so the missing `Model::from_centroids` blocks nothing. One corpus does not prove agreement on near-ties (`Model::assign` switches to a matrix-multiply kernel on large inputs, `e-means/src/assign.rs`), so the design uses the own loop for every assignment, train-time included, and parity stops mattering.
- The vectors are unit-norm as stored; spherical mode needs no prep.

### Scope: which notes get a topic

- **Eligible** (defined without reference to embeddings): `note_type` is not in `topics.exclude-types`, `quality` is not `low`, and the note is not a merge tombstone.
- **In scope**: eligible and holding an active-model `summary` row. Only in-scope notes get a topic.
- **Pending**: eligible, no active-model `summary` row, and the embed loop still counts it as a target. The test is the embed loop's own: `SearchIndex::stale_embedding_targets` for the summary kind, which already honors the `embedding_examined` nothing-to-embed sentinel. A note that can never be embedded is settled, never pending.
- Default `exclude-types`: `entity`, `daily`, `digest`, `review`, `system`, `moc`. These are generated or aggregate notes: 1,796 of the 5,129 summary rows in the spike copy (entity 1,425, digest 219, daily 109, review 32, system 6, moc 5).
- Why: with them in (n=5,129, k=64) the spike produced topics that are only creator hubs ("Rob", "Dan Harrison", "Steve Klabnik"), only daily notes, and two separate "Daily Digest" topics. 1,425 `entity` notes and 109 `daily` notes carry no tags, so they also cannot be labelled.
- `exclude-types` deserializes to `Vec<vault::schema::NoteType>`. No type string is hardcoded outside the config default.
- An out-of-scope note has no `note_topics` row. A reader never invents one.

### Architecture

```
cortex (only writer)                     vault                              oracle (read only)
sb cortex topics --train  ->  kmeans::train (e-means)
                              search::topic::replace_generation   ->  topic_state / topic_centroids / note_topics
sb cortex topics          ->  kmeans::nearest (own loop)
daemon topics tick            search::topic::assign_batch         ->  note_topics
                                                                      search::topic::{overview, in_tags, notes}  ->  topic_map, tag_brief, vault_overview
```

**`vault::kmeans`** (`vault/src/kmeans.rs`, feature `kmeans`):

- `train(rows: &[f32], d, k, seed, epochs) -> Result<Trained>` where `Trained { centroids: Vec<f32>, labels: Vec<u32>, cosines: Vec<f32> }`. Spherical, `capture_labels(false)`. Labels and cosines come from `nearest` over `model.centroids()`, never from `Model::assign`: one function assigns every row this system ever stores.
- `nearest(row: &[f32], centroids: &[f32], d) -> (u32, f32)`: argmax dot product, lowest index wins a tie (matches `e-means`, `model.rs`).
- Validates every row norm within 1e-3 of 1.0 before training; a miss is a typed error naming the row. `e-means` does not normalize and would return a wrong answer in silence.
- Runs on the caller's rayon pool. No pool of its own.
- Named for what it wraps. `cluster` is taken twice already (`cortex::memgraph::bridge_clusters`, `borg/src/harvest/cluster.rs`).

**`vault::search::topic`** (`vault/src/search/topic.rs`, same cfg gate as `vector.rs`): schema, `replace_generation`, `assign_batch`, `unassigned`, the three readers, `TopicState`.

**`cortex::topics`** (`cortex/src/topics.rs`):

- `train(config, opts) -> TrainReport`: take `embed::acquire_lock()`, run the pending gate, read in-scope active-model summary vectors ordered by `note_path`, train inside a pool built for the call (`topics.workers` threads), `replace_generation` in one transaction.
- **Pending gate (fail closed):** if any eligible note is pending, `train` exits non-zero, writes nothing, and the error gives the pending count and names `sb cortex embed --backfill`. Why: the embed path sets the active model before the backfill runs, and the backfill goes newest first (`cortex/src/embed.rs`, `stale_embedding_targets`), so a train during a migration would freeze centroids built from recent notes only. `n >= k` does not catch that. There is no override flag.
- `assign(config) -> AssignReport`: take the lock, load centroids, for each in-scope summary row with no `note_topics` row or a different `vector_hash` than the one recorded (Phase 6; Phases 3-5 used `note_embeddings.id`), `kmeans::nearest`, write in one transaction. Also deletes `note_topics` rows for notes that left scope.
- `daemon_tick`: `assign`, skipped on `EmbedLockHeld`, a no-op with a DEBUG line when there is no generation.
- Invalid generation (trained model or dim differs from the active pin): `assign` and the tick write nothing and return `Stale`; the tick logs one WARN naming `sb cortex topics --train`.
- Fails loudly: `n < k` is an error before any write; a non-finite or non-unit row is an error naming the note.
- `clear(config) -> ClearReport`: take the lock, empty `note_topics` and `topic_centroids` and every `topic_state` key except `generation`, in one transaction. The counter survives so a later train never reuses a generation number a client has seen.
- `topics.k` edited after a train: `assign` uses the stored centroids; the report prints the stored `k` and the configured one.
- A renamed note: the old row goes by FK CASCADE, the new path is assigned on the next tick after it is embedded.
- A reader during a swap: `replace_generation` is one write transaction, but oracle's process mutex does not exclude cortex's connection, so a response assembled from several statements could mix two generations. Every reader therefore runs inside one read transaction: `topic_state`, the active pin, counts, labels and exemplars come from one snapshot.

**Daemon:** one more `tokio::time::interval` arm on `topics.interval-secs`, placed after the embed arm, wrapped in `block_in_place` like its siblings. Stop is checked before the read and before the write; the work between is under 50 ms on today's corpus.

**Why not the embed inference pool:** `in_inference_pool` is `pub(super)` and its size is fixed by its first caller (`cortex/src/embed/inference.rs`). Training on the global pool is the 2026-08-16 starvation shape. A pool built per `--train` call costs nothing next to a train an operator runs by hand.

### Data Model

Created in the gated block of `ensure_schema` beside `note_embeddings`, under the existing `#[cfg(any(feature = "vec-candle", feature = "vec-onnx"))]`. Reasons: every consumer that touches them (`cortex`, `oracle`, `sb`) already builds with `vec`, and the validity check needs the active-pin accessors, which are gated. There is no SQL foreign key to `embedding_config`. `CREATE TABLE IF NOT EXISTS`, no migration needed for a new table.

```sql
CREATE TABLE IF NOT EXISTS topic_state (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
-- keys: generation, trained_at, k, seed, epochs, e_means_version,
--       model_version, dim, trained_rows, train_mean_cosine, exclude_types

CREATE TABLE IF NOT EXISTS topic_centroids (
    topic        INTEGER PRIMARY KEY,   -- 0..k-1, the e-means label
    centroid     BLOB NOT NULL,         -- dim f32 little-endian, unit norm
    trained_rows INTEGER NOT NULL       -- members at train time
);

CREATE TABLE IF NOT EXISTS note_topics (
    note_path             TEXT PRIMARY KEY REFERENCES notes(path) ON DELETE CASCADE,
    topic                 INTEGER NOT NULL REFERENCES topic_centroids(topic),
    cosine                REAL NOT NULL,     -- dot product with the centroid
    vector_hash           TEXT NOT NULL,     -- note_embeddings.vector_hash it was assigned from (Phase 6)
    assigned_at           INTEGER NOT NULL   -- unix seconds
);
CREATE INDEX IF NOT EXISTS idx_note_topics_topic ON note_topics(topic);
```

- Keyed on `note_path`. ~~`note_embeddings.id` changes on every re-embed~~: false, found by the implementation audit (probe 20). `note_embeddings.id` is `INTEGER PRIMARY KEY` without `AUTOINCREMENT`, and `swap_embeddings_batch` deletes before it inserts, so the note holding the max rowid gets the same id back. Phases 1-5 shipped `embedding_id` as the marker; Phase 6 replaces it with `vector_hash`. See "Embedding revision marker".
- `produced_at` is whole seconds and cannot tell two re-embeds in one second apart, so it is not a marker either.
- `assigned_at` exists so doctor can separate train-time assignments from later ones (`assigned_at > trained_at`).
- FK CASCADE removes a deleted note's row; `remove_note` needs no change.
- No `generation` column on `note_topics`. `replace_generation` swaps all three tables in one `BEGIN IMMEDIATE`, so every row belongs to `topic_state.generation`. A per-row copy could only diverge.
- No stored label. Labels derive from `note_tags` at read time, and tags change without a retrain.
- `generation` is an integer that `--train` increments. It is the first one in this schema; the nearest precedent is the `graph_state` KV (`vault/src/search/graph.rs`).
- `rename_model_id` (`schema.rs`) documents the full set of tables that store a model id. `topic_state.model_version` joins it, in the same change.
- A summary recipe bump does not invalidate a generation: same model, same vector space. The new `note_embeddings.id` reassigns each re-embedded note.
- `topic_state` records `exclude_types` as trained. If the configured list differs, `assign` still runs (scope is evaluated per note) and `sb cortex topics` prints the difference.

Validity, one rule, in `TopicState::status(&self, active_model, active_dim) -> Result<Absent | Valid | Stale>`:

- `Absent`: no `trained_at` key (never trained, or cleared).
- `Stale`: `model_version` or `dim` differs from the active pin.
- `Valid`: otherwise.
- `Err`: anything else that is wrong. A metadata value that will not parse, a centroid count that differs from `k`, a centroid blob whose length is not `dim * 4`. Corrupt state is an error at every caller, never `Absent` and never an empty list.

Every reader and the writer call that one function.

### Embedding revision marker (Phase 6)

The implementation audit showed `note_embeddings` has no field that reliably marks a new embedding: the id is reused, and `produced_at` is whole seconds. Topics and the graph's semantic-edge freshness both need one. Scott, 2026-11-14: fix it on the embedding row and backfill the existing rows, not as a topic-only workaround; include the graph freshness fix.

- **`note_embeddings.vector_hash TEXT`**: lowercase hex SHA-256 of the stored vector blob (the exact little-endian f32 bytes written). One function computes it, in `vault::search`, and every write path calls it: `swap_embeddings_batch` and any other `note_embeddings` insert.
- **Migration + backfill**, in `ensure_schema` beside the `recipe` column migration (precedent: add a column, no table rebuild): `ALTER TABLE ADD COLUMN`, then hash every row whose `vector_hash` is NULL, in one transaction, idempotent. After `ensure_schema` returns, no row has a NULL hash; a NULL found later is an error at the reader, never a silent "changed" or "unchanged".
- **Topics**: `note_topics.embedding_id` becomes `vector_hash` (the table is unshipped, so the `CREATE TABLE` changes in place; no migration). `unassigned` / `summary_vectors` select a note when it has no row or `t.vector_hash != e.vector_hash`, in SQL, so the tick loads no vectors to decide.
- **Graph freshness**: `edge_build_state.semantic_built_at` is replaced by `semantic_vector_hash TEXT`. `semantic_edge_targets` selects a note whose active-model summary `vector_hash` differs from (or has no) recorded `semantic_vector_hash`; `record_edge_build` stores the hash the edges were built from (`note_summary_produced_at` becomes a hash reader). Migration backfill: a note fresh under the old rule (`semantic_built_at >= MAX(produced_at)` of its active-model summary) gets that summary's current hash; every other note stays NULL and is rebuilt on the next pass, which is exactly what the old rule would have done. `semantic_built_at` is then dropped: a field kept beside its replacement could only diverge.
- `rename_model_id`'s `produced_at` comparison is an ordering between two model sets, not change detection. Unchanged.
- Bite tests: re-embed the note holding the max rowid and prove topics reassign it and the graph marks it a semantic target; re-embed twice inside one second and prove the same.

### API Design

**Config**, new top-level `topics:` block in `cortex.yml` (precedent: `graph:`, `entities:`), `#[serde(default, rename_all = "kebab-case", deny_unknown_fields)]`, annotated in `config/templates/cortex.yml.example`:

```yaml
topics:
  k: 64                 # topics per generation; read by --train only
  seed: 7               # recorded in topic_state with every generation
  epochs: 5.0
  workers: 2            # rayon threads for --train
  interval-secs: 900    # daemon assign tick
  exclude-types: [entity, daily, digest, review, system, moc]
```

**CLI** (`sb/src/cli/cortex.rs`, one verb with flags, sibling of `Graph` and `Embed`):

```
sb cortex topics                       # assign unassigned in-scope notes, print the report
sb cortex topics --train               # train a new generation from config, replace the old one
sb cortex topics --train --k 96 --seed 11   # per-run overrides of config
sb cortex topics --clear               # back out: empty the topic tables, keep the generation counter
```

- `--k` and `--seed` without `--train` are a clap error (`requires = "train"`). `--train` and `--clear` conflict.
- Report fields: `status`, `generation`, `k`, `trained-at`, `eligible`, `pending`, `in-scope`, `assigned`, `assigned-this-run`, `removed-this-run`, `mean-cosine`, `train-mean-cosine`. Printed by `sb` in the house format (yaml on a TTY, json when piped).
- Exit: 0 on success, including `Absent` with no `--train` (report says `status: absent`); non-zero on `Stale` without `--train`, on a pending note under `--train`, on `n < k`, on a bad row, on corrupt topic state.

**Oracle:**

- New tool `topic_map` (`TopicMapRequest`, `deny_unknown_fields`):
  - no arguments: every topic with at least one note: `{topic, notes, tags: [{tag, lift, notes}], exemplars: [title x3]}`, ordered by `notes` desc, then `topic`.
  - `tags` + `tags_mode`: the same topics, with `notes` counting only the notes that carry those tags, zero-count topics dropped. This is the sub-theme view. A topic's label never changes with the filter: labels are a property of the topic.
  - `topic: <n>`: the notes in that topic, nearest the centroid first, with `detail` and `limit` like every list tool. Combines with `tags`.
  - `generation: <g>` (optional): the generation the caller's topic ids came from. A mismatch with the stored generation is an argument error (`is_error: true`) naming both numbers. Without it, a `{topic: n}` call after a retrain would return a different subject in silence.
  - Envelope: `{status, generation, trained-at, k, count, results}`. `Absent` or `Stale` returns `{status, count: 0, results: []}` plus a `hint` naming `sb cortex topics --train`. Never an error, never a silent empty list.
  - It returns notes in the `topic` form, so it goes in `NOTE_TOOLS` and its description carries the `` `trace` block `` wording.
- `tag_brief`: new key `topics`: `{generation, results}` where `results` is the top 8 topics for that tag, `{topic, notes, tags}`; `null` plus `topics-status` when not `Valid`. Added in the hand-built `json!` payload (`oracle/src/server.rs`).
- `vault_overview`: new key `topics`: `{status, generation, k, trained-at, assigned}`. Built in the oracle method by adding one key to the serialized `VaultStats`; `VaultStats` and `sb oracle stats` do not change: the topic readers live in the gated `topic` module, and `stats.rs` is ungated.
- Topic ids are valid inside one generation. Every response carries `generation` so a client can tell.

**Label rule** (one function, `vault::search::topic`): a tag labels a topic when its lift is 2.0 or more and at least max(5, 20% of the topic's notes, rounded down) carry it. Lift = (share of the topic's notes with the tag) / (share of all assigned notes with the tag). Top 3 by lift, ties by tag name. Zero qualifying tags is a legal answer: `tags: []`, and the exemplars carry the topic. Exemplars are the 3 highest-`cosine` titles.

- **The re-embed marker lives on `note_embeddings`, backfilled, and the graph's semantic freshness moves to it too.** Scott, 2026-11-14, after the implementation audit found `note_embeddings.id` reuse (probe 20). He rejected both topic-local options (a hash column on `note_topics` only | `AUTOINCREMENT` via a table rebuild): "why are we not talking about backporting, backfilling the current to use this?", then "go, include the graph freshness fix too".

- **k=64 is the default and the sample topics read as topics.** Scott, 2026-11-14, on the Phase 0 sample table (option A of three: k=64 | k=48 | labels not usable).

The rest were decided by the author while drafting, 2026-11-14. Scott can overturn any of them.

- **Frozen centroids, operator-ordered retrain.** Evidence: ARI 0.51 across seeds; a warm start with revival off still moves membership (ARI 0.535 at k=64). Panel round 1: both seats agree. Conforms to the stability disciplines in `2026-07-17-harvest-clyde-sessions.md:111`.
- **Own nearest-centroid loop in `vault::kmeans`, used for every assignment including train time; no `e-means` release.** The handoff lists it as a sanctioned option. Panel round 1: Staff Engineer accepted; the Architect objected on a reading of the handoff that its text does not support (`docs/handoff/e-means-library-integration.md`, "What it does not do"). Using one function everywhere came from the panel synthesis.
- **Name is `topic`** for tables, module, verb, config and tool. `cluster` already names two unrelated things in this repo.
- **Scope excludes generated and aggregate note types and low-quality stubs.** Evidence: the n=5,129 run.
- **Tables and readers sit behind the vec gate**, beside `note_embeddings`. Every consumer that reads them (`cortex`, `oracle`, `sb`) already builds with `vec`. Panel round 1: Staff Engineer keep, Architect ungate; the Architect's cost ("read-only consumers compile inference backends") describes no consumer in this workspace.
- **One `topic_map` tool with three forms.** Precedent: `creator_browse` lists creators with no argument and returns notes with one (`oracle/src/tools.rs`). Panel round 1: Staff Engineer accept, Architect split; the precedent settles it.
- **`--train` fails closed on a pending note, no override.** Panel round 1, both seats.
- **Panel disputes closed, 2026-11-14.** The three Architect objections (ungate the tables, require `Model::from_centroids`, split `topic_map`) went back to the Architect seat with the evidence above. It conceded all three. No finding from round 1 is open or disputed.
- **No `enabled` flag.** No generation means nothing runs. The first `--train` is the switch.
- **Labels are tags by lift plus exemplar titles, computed at read time.** No LLM call, nothing stored that can go stale.
- **ripr is the only trainer** because it is the only host with a cortex daemon and a populated index. Centroid bits differ across CPUs (`e-means` handoff); nothing compares two hosts' centroids.

## Alternatives Considered

### Alternative 1: Retrain on every tick
- **Description:** train from scratch each tick; no incremental assignment.
- **Pros:** no staleness, no `nearest` loop, always the best fit.
- **Cons:** every topic id changes every 15 minutes.
- **Why not chosen:** ARI 0.51. A topic a client saw is gone on the next call.

### Alternative 2: Warm-start retrain (`train_from` the stored centroids)
- **Description:** keep index alignment by seeding each retrain with the last centroids.
- **Pros:** tracks drift.
- **Cons:** measured at k=64: 34% of label indexes kept with revival on, 64% with it off, and ARI 0.535 against the starting partition even with it off.
- **Why not chosen:** it does not deliver the stability it promises.

### Alternative 2b: Renumber a retrain by overlap matching
- **Description:** after a retrain, match new topics to old ones by shared members (bipartite matching) and reuse the old ids.
- **Pros:** ids look stable.
- **Cons:** it renames; it cannot keep a note in the group it was in. ARI is blind to numbering and still reads 0.51.
- **Why not chosen:** the id would be stable and the subject behind it would not.

### Alternative 3: Add `Model::from_centroids` to `e-means`
- **Description:** rebuild a `Model` from stored centroids and call its `assign`.
- **Pros:** one kernel for train and assign.
- **Cons:** a second repo release before this can ship.
- **Why not chosen:** the own loop is twelve lines and assigns every row, so there is no second kernel to agree with.

### Alternative 4: Cluster every note, generated types included
- **Description:** no scope filter.
- **Pros:** every note has a topic.
- **Cons:** measured: hub-only and daily-only topics, 1,534 notes with no tags to label them.
- **Why not chosen:** it spends topics on notes that are already an index of something else.

### Alternative 5: LLM-named topics
- **Description:** a fabric pattern names each topic at train time.
- **Pros:** better names for the grab-bag topics.
- **Cons:** an LLM call on a path with none; a stored name goes stale as notes join.
- **Why not chosen:** parked, per `2026-09-21-staged-tag-proposals.md:611`. Exemplar titles cover the unnamed topics.

### Alternative 6: A cell pre-filter for `search_vector`
- **Description:** use the centroids as an inverted-file index.
- **Why not chosen:** a Non-Goal. Brute force is the standing ruling, the scan is not the slow stage, and it risks recall on the eval-best path.

## Technical Considerations

### Dependencies

- One direct dependency: `e-means` (git tag, same shape as `expand-tilde`).
- Lockfile: `rand_chacha 0.10.0` is new. `matrixmultiply 0.3.11` and `rawpointer 0.2.1` are already in `Cargo.lock` (inactive, under `ort`'s optional `ndarray`) and become compiled. `log` 0.4.29 -> 0.4.35 and `thiserror` 2.0.18 -> 2.0.21 are lock bumps `e-means` requires.
- `e-means` pins `matrixmultiply = "=0.3.11"`. A later dependency that needs a newer 0.3.x will fail to resolve; raise the pin in `e-means`, never here.
- Cross-repo blast radius: none. `e-means` is consumed as tagged; no change to it is required. Ship order: this repo only.

### Performance

- Train, n=3,333, d=384, k=64: 15.0 ms at 2 threads, 34.8 ms at 64. Assign all rows: 1.8 ms at 2 threads.
- Generation swap: about 5 ms write lock for 3,333 + 64 rows, under the 200 ms write rule.
- The tick assigns only new or re-embedded notes: tens of rows, single-threaded dot products against 64 centroids.
- Readers: one GROUP BY over `note_topics` joined to `note_tags`. Not measured; Phase 5 records `topic_map` wall-clock on ripr in its implementation notes.

### Security

- No new secret, network call or external surface. Topic data derives from notes already in the index and is served by the same local MCP process.

### Testing Strategy

- `MockEmbedder` vectors are hash noise with no structure. Topic tests plant blobs: seeded unit vectors around 3 fixed axes, built with the helper pattern in `vault/tests/perf.rs`.
- Every phase names its tests above. Tests live in sibling `tests.rs` files (`source-lint`), new files where a `tests.rs` is near the `bloat` limit.
- The seed tests, the pending-gate test and the two-connection reader test are the ones that guard the frozen-centroid design.

### Rollout Plan

- Ships dark: no generation, no behavior.
- ripr: `otto deploy`, then `sb cortex topics --train`. The daemon tick takes over assignment.
- Other hosts have no cortex daemon; their index has no generation and their oracle reports `status: absent`.
- Back out: `sb cortex topics --clear` on ripr. Every oracle surface then reports `absent`, the tick does nothing, and the generation counter is kept. The tables stay in the schema, empty.

## Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Centroids go stale as the vault's subjects shift | Med | Med | `sb doctor` prints mean cosine of post-train assignments beside the train-time mean; the operator retrains. Spike: 0.829 vs 0.843 for the newest 10% |
| A retrain renumbers topics under a client | Low | Low | Retrain is operator-ordered; every response carries `generation` |
| Grab-bag and split topics (21, 51, 6/57 in the sample) | High | Low | Labels show `tags: []` and exemplars as they are; `--train --k` is one command to try another k |
| Embedding model change strands a generation | Low | Med | `TopicState::status` -> `Stale`; readers say so; doctor Warns; tick writes nothing |
| `e-means` runs on the governance rayon pool | Low | High | `train` is only ever called inside a pool built for the call; `assign` uses no rayon |
| `matrixmultiply` exact pin blocks a future dependency | Low | Low | Raise the pin in `e-means` and re-tag |
| Agents never call `topic_map`; the feature has no measured retrieval value | Med | Med | It ships dark and costs one 15 ms train. Nothing measures `topic_map` usage today: `--mine-queries` reads only `knowledge_search` calls (`oracle/src/eval/mine.rs`). Measuring it means extending the miner, which rides the parked eval-coverage item |
| An old daemon that was not restarted re-asserts its startup model on every embed tick (`daemon_tick_with_model`) and can flip the pin back during a migration | Low | Med | Pre-existing, not caused by this design. A flipped pin reads as `Stale` here, so topics fail visibly. `otto deploy` restarts the daemon |
| Readers or the tick wait on SQLite's 5 s busy timeout behind a long embed write | Low | Low | Phase 5 records `topic_map` wall-clock on ripr; the swap itself holds the lock about 5 ms |
