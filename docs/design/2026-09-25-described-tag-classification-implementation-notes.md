# Described Tag Classification: Implementation Notes

Design doc: `docs/design/2026-09-25-described-tag-classification.md`

## Phase 0: Measure on production input against a gold set

### Design decisions
- Gold labels (`~/Claude/tags-only-trial/gold.md`): Claude ticked the set and Scott reviewed and accepted it. G2 now records that provenance.
- Wire text (`p0/build.py`): a port of `vault::search::parse_body_summary` plus `body_excerpt`. The title comes from frontmatter `title:`, falling back to the filename.
- Protect-list tags vs. domains: every note carries its domain tag. The `resources` domain is not a tag, so those notes get `entertainment`, `finance` or `books` instead.
- A2-A4 inputs are unclipped (A0 won A0 vs. A1), per "run on whichever of their inputs wins". P1 still ships the 900 clip.
- A4 indicator labels (`p0/arms.py:INDICATORS`): 3 per protect-list tag; the tag's score is the max of its indicators. The indicators are sent without descriptions.
- Screen query embedding: `p0/bge.py`, a numpy forward pass of the cached `BAAI/bge-small-en-v1.5` weights with CLS pooling and L2 norm, as in `vault/src/embedding/candle.rs:380`. It reproduces the stored oracle.db summary vectors at cosine 1.0 (4 of 4 checked). This avoids new repo code and a Rust build.
- The BM25 union takes every phrase hit, not just the top N, so the candidate set can exceed N (for example, `work` matches 1,076 notes).

### Deviations
- Descriptions were drafted from sample-note titles (up to 8 per tag, newest first, the 53 excluded), not from 5-10 full notes. Tags with no samples (`entertainment`, `politics`, `nix`, `synth`) were drafted from the slug alone.
- The drafter had already labeled the gold set, so A2-A4 carry leakage beyond "samples exclude the 53". This is recorded in Phase 0 Results; P5's confirmation on `gold-2` is the control.
- One A4 call's response was truncated in transit (`http.client.IncompleteRead`), so it was never logged, and its cost (about $0.0065) is missing from `calls.jsonl`. `jev.py` now retries transport errors as code 599.
- A6 was first run with L2 1e-2 over 300 iterations, which underfit (F1 0.016). The recorded run is the vectorized refit (L2 1e-4, 2,000 iterations, learning rate 20).

### Tradeoffs
- The instability metric reports both note-level (set differs) and label-level (symmetric difference over union) rates. The doc's "pairwise disagreement rate" is read as note-level for the gates.
- The bootstrap compares mean-over-repeats F1 between arms, rather than pairing single calls, so arms with 3 and 6 repeats compare like for like.
- Cost model: fitted in the doc's form. It is not identifiable with a constant 53-note chunk, so the per-call token and USD figures are given beside it.

### Open questions
- P3-P5: A2 misses "beats baseline" by 0.004 F1 (CI lower bound -0.006), while lifting protect-list recall (work 1/7 -> 4/7). Go on the near-miss, or hold to the rule?
- P6 passes on the baseline's six calls by a small margin (0.195 -> 0.170). Ship `repeats: 3` at 3x the call cost?

## Phase 1: Classifier infrastructure

### Design decisions
- One clip, at the wire: `clip_classifier_text` (`distillers/src/tags.rs`) replaces `body_excerpt`, which is deleted rather than kept as a shim. `TagSources::from_body` (`borg/src/pipeline/tags.rs`) and `cortex::classify::classifier_text` now hold the body whole and leave the clip to the classifiers.
- `FabricClosedVocab::prompt` also goes through `clip_classifier_text`, because `from_body` no longer clips. Without that, the fabric-closed path would send a whole transcript to Fabric, reopening audit M3. The prompt's `TITLE:` line is folded into `TEXT:`, since the clipped wire text already leads with the title.
- The HTTP boundary is a private `Transport` port (`send(body, token) -> (status, body)`), with `UreqTransport` in production. Status handling, parsing, and `ensure_jev` stay in `ClassifierDev::post`, so the fake responder exercises the same path production does.
- Batch sizing (`plan_chunks`, `note_tokens`): a greedy chunk stays under `REQUEST_TOKEN_BUDGET` = 157,708 tokens (the largest passing P0 call) and under `MAX_TEXTS_PER_CALL`. The per-note estimate is the doc's model: 26.9 + 0.43 x wire chars + 24.7 x labels sent + 0.21 x total label chars. On a 59-label bare shard with the 715-char mean P0 wire text, that is about 1,900 tokens per note (P0 measured 100,663 / 53 = 1,899), so a chunk holds about 83 notes. That is under the 159 that 402'd and over the 53 that passed.
- The 402 split only happens on `402` whose body contains `request_spending_limit`. Any other 402, such as the day cap, fails the chunk as it stands and is not retried, which is P2's backstop rule.
- A note that failed one shard is not sent to the next, so a failed note is not paid for twice.
- `CallUsage` rows cover every HTTP call. A refused or failed call is recorded as `ok: false` with 0 tokens and $0, since no response reported a cost for it.
- `sb doctor`: new `classifier_settings_finding` prints one info line each for borg and cortex. The live probe (`classifier_probe_findings`) still runs on borg's config, as before.

### Deviations
- `score_batch`'s signature matches the doc. `finish` now takes the merged `&HashMap<String, f32>` for one note instead of the per-shard slice, and `merge_shard_scores` does the merge inside `score_batch`. Same effect, correct seam.
- `ensure_jev` still fails the whole call when any result is non-Jev, rather than failing per note. The notes in that chunk then get `Err` (per note, as the doc requires), but one non-Jev answer fails its chunk-mates too. I kept this fail-closed rule unchanged because the doc does not ask for a change.
- The "later repeat failed" half of success criterion 3 cannot be tested yet: repeats are P6. The shard half is tested.

### Tradeoffs
- The token budget is the measured pass (157,708) rather than an extrapolation toward the $0.01 cap, which would be about 238k tokens at $0.042/M. The measured number costs a few more calls, but it never plans a chunk P0 did not see pass, and the 402 split still covers drift.
- `Transport` is crate-private. P2/P8 tests in cortex may need a fake across crates. Widening it then is one `pub`; exposing it now would be work for a later phase.

### Open questions
- None.

## Phase 2: Spend ledger and resumable bulk runs

### Design decisions
- The ledger and day allowance live in `distillers::tags::spend` (`SpendLedger`, `DaySpend`, `Allowance`, the `Clock` port). The resumable loop lives in `distillers::tags::bulk` (`BulkRun::run`, `ScoreCursor`). Both are submodules of `tags`, so their tests reach the private `Transport` and `ClassifierDev::with_transport` with no widening.
- The ledger path is `vault::paths::classifier_spend_ledger()` (`~/.local/share/sb/classifier-spend.jsonl`). It sits under `sb/`, not a subsystem's directory, because every bulk path and `sb doctor` share one IP-wide day.
- Rows are written only for calls with `ok: true`, from the response's `pricing.estimated_usd`. A refused or failed call carries no pricing, so it has nothing to record. A ledger line that does not parse is an error (`SpendLedger::day_total`), because reading it as low spend would let a run spend into the cap.
- The generic cursor is `ScoreCursor { scoring_config_hash, scores: {id: {scores, wire_text_hash}}, failed }`. P8 adds `tag`, `candidate_mode`, and `candidates` around it and owns the file path. `BulkRun::run` takes a `persist` callback rather than a path, and `ScoreCursor::save` writes atomically. `keep` limits the slugs stored per note, since P8 needs only the target slug.
- `scoring_config_hash` (`ClassifierDev::scoring_config_hash`) is SHA-256 over the endpoint, the shards exactly as sent, `max_labels`, and `CLASSIFIER_TEXT_CHARS`. P5 (instructions, described labels) and P6 (repeats) extend it. `wire_text_hash` is SHA-256 of `clip_classifier_text`. I used sha2 over std's `DefaultHasher` because the digest must survive a toolchain upgrade. `sha2 = "0.10"` is the version borg already builds.
- Run chunks (`plan_run_chunks`) are planned against the shard whose labels cost the most per note. So each run chunk is one request per shard, and "a chunk" costs one call per shard.
- The stop rule: before each chunk, the prediction is the model's estimate scaled up (never down) by what the service has charged against the model so far in this run. Spend counted against the limit is, per chunk, the larger of the reported and estimated cost. A response that under-reports, or has no `pricing`, cannot run the day dry. This is also what makes the $0.02-per-chunk fake stop after two chunks at $0.05.
- Service limit: `CallOutcome::ServiceLimit` covers any 429 and any 402 that is not `request_spending_limit`. `score_batch` sends nothing after one and reports it in `ScoredBatch::service_limit`. Notes it left unscored stay pending in the cursor, not failed.
- A multi-note `--retag` is a bulk path: `Classifiers::classify_bulk` (`cortex/src/classify.rs`). The primary's `estimate` is checked against the allowance, and the run refuses above it, naming how many notes fit. The estimate line is reported as an Info row against the ledger path. The batch then goes through `classify_batch_metered`, and every successful call is written as `path: "retag"`. `TagClassifier` gains two defaulted methods, `estimate` (`None`) and `classify_batch_metered` (no calls), so Deterministic and Fabric retags are unchanged and borg is untouched.
- A retag note left unscored at classifier.dev's limit is left unchanged and reported as a Warning. It does not get the deterministic fallback written over it.
- `sb doctor`: the settings line for each subsystem now shows `daily-usd-budget` and `ingest-reserve-usd`. A new `classifier_spend_finding` prints today's ledger total and the allowance, read with cortex's keys since bulk runs are cortex's, and warns on an unreadable ledger.
- Both config templates document the two keys, commented out, since code defaults carry the values.

### Deviations
- `daily-usd-budget` and `ingest-reserve-usd` are `f64`, not the doc's `f32`. `CallUsage.estimated_usd` and the ledger are `f64`, and mixing in `0.1f32` noise would put comparisons at the allowance boundary off by rounding.
- `--retag` has no `--max-usd`: the doc lists that flag only for `tag-apply`. `BulkRun` takes `max_usd` for P8.
- `--retag` classified one note per call before this phase. A multi-note retag now batches through `classify_batch_metered`, so it can be metered and written to the ledger. As P1 recorded, one non-Jev answer now fails its chunk-mates (they get the fallback), where a per-note call would have failed only itself.
- `lint_classify` now returns `Result<Report>`, because a dry-run retag also spends and must be able to refuse.

### Tradeoffs
- Scale the next chunk's prediction by what the service charged, vs. trusting the token model alone. The model does not know what the service will charge, and the success criterion's fake charges far more than the model predicts. Scaling only upward keeps the rule fail-closed.
- `failed` is a report, not a skip list: the next run retries failed notes, vs. skipping them for good. A transient 500 should not strand a note, and a note that keeps failing costs nothing, because failed calls are not billed.
- The retag estimate is checked once, up front, against the whole set, vs. scoring until the allowance runs out as the cursor does. `--retag` has no cursor to resume from, so a partial retag would leave a set half-rewritten with no record. The doc asks for refusal.
- Cortex's daemon classify (inbox and catch-up) is not treated as a bulk path and writes no ledger rows. The doc names only `--retag` over more than one note, and `tag-apply`. See Open questions.

### Open questions
- Cortex's daemon classify pass also calls classifier.dev once per inbox or catch-up note when `classifier: classifier-dev`, and it writes no ledger rows. That spend comes out of `ingest-reserve-usd` alongside borg's. Should it be metered too?
- Not run live: no `--retag` over several notes against classifier.dev, and no `sb doctor` on a host. Both were exercised only through fakes. A live check after deploy: `sb cortex classify --retag 'notes/a*.md'` (dry run) should print the estimate row, and `sb doctor` should show the spend line.

## Phase 3: Descriptions in the vocabulary schema

### Design decisions
- Gate: under the doc's rule neither A2 nor A3 beat baseline in P0. Scott overrode the rule on 2026-09-26 ("build it"; see Resolved Decisions and Phase 0 Results), so this phase is built on that decision. Descriptions are still not sent to classifier.dev: that is P5, which stays gated on the `gold-2` confirmation run.
- `TagEntry { slug, description: Option<String> }` (`vault/src/canonical.rs`) deserializes through `#[serde(try_from = "RawTagEntry")]`, where `RawTagEntry` is the untagged enum `Bare(String) | Described(serde_yaml::Mapping)`. The entry rules run in `TryFrom`, so the raw `serde_yaml::from_str` in `promote_tags` enforces them. The errors carry serde_yaml's path and location (`tags.tech: tag "go": description contains ... at line 3 column 5`).
- The map arm reads a `serde_yaml::Mapping`, not a `HashMap<String, String>`, so a non-string value (`- rust: 0.9`, `- rust:`) gets its own message naming the tag, not serde's "did not match any variant".
- `CanonicalSet.descriptions` (slug -> description) holds described tags only. `all` still holds every slug, so every reader of `all_tags()` / `canonical_set()` compiles unchanged. Test literals of `CanonicalSet` gained `descriptions: Default::default()`.
- `TagEntry::yaml_line` is the one writer of an entry's text: `slug` or `slug: "description"`, with `\` escaped. A validated description holds no `"` and no control character, so that escape is all a double-quoted scalar needs to read back the same string. `yaml_line_reads_back_as_the_same_entry` pins this.
- `insert_tags_into_group` now takes `&[TagEntry]` and writes each through `yaml_line`. `promote_tags` passes bare entries, so its output is unchanged until P7.
- `describe_entry_in_group(text, group, slug, description)` (`cortex/src/proposals.rs`) is `pub` for P4 and has no production caller yet. It parses each entry line of the group as a `TagEntry`. It rewrites the target line only if that line reads exactly as `yaml_line` would write it. So a trailing comment or a single-quoted form bails instead of being dropped or reformatted. It returns the buffer; the caller validates the whole file before writing, as `promote_tags` does.
- `tag-values.md` renders `| Tag | Description |`. An undescribed tag gets an empty cell, and a `|` in a description is escaped as `\|`. `load_canonical_tags` (`sb/src/cli/cortex.rs`) returns `CanonicalTagsFile::sorted_entries()`, sorted by slug as before. `render_all` / `render_all_at` take `&[TagEntry]`. oracle's own `load_canonical_tags` is untouched, since it lists slugs only.
- `sb doctor`: `tag_description_finding` (`sb/src/cli/checks.rs`) prints an Info line in the classifier section, `N of M tags have no description`. It reads the vocabulary at cortex's `sweep.canonical_path`. It is Info, not Warn, because an undescribed tag still classifies.

### Deviations
- The doc says "`TagEntry` untagged enum". The public `TagEntry` is a validated struct, and the untagged enum is the private raw form it is converted from. Same effect, correct seam: consumers read `slug` and `description` without matching two variants.
- Beyond the doc's three entry rules (one key, at most 200 chars, no `"`), parsing also refuses an empty description and one containing a control character (a line break or tab). An empty one would reach Jev as `slug: `. A line break would split the label's line both in the file and in the Jev question.
- The success criterion `sb cortex schema --render` ran with the worktree binary (`target/debug/sb cortex --vault <scratch copy> schema --render`) against a scratch copy of the live `system/schemas/`, not against `~/repos/scottidler/obsidian`. Result: exit 0, `tag-values.md` written with `| Tag | Description |` and 117 rows with empty description cells; the other three docs were `unchanged`.

### Tradeoffs
- Row format `| slug |  |` (empty cell) vs. omitting undescribed tags or writing `-`. The empty cell keeps every tag listed and makes the backfill gap visible in the vault. A placeholder would read as a description.
- The describe rewrite bails on any line not in the written form, vs. rewriting it anyway. A hand-formatted line (comment, single quotes) is rare, and silently losing a comment or re-quoting Scott's text is worse than a refusal naming the line.

### Open questions
- The live vault's `system/schemas/tag-values.md` still has the one-column table. After this ships, `sb doctor` and `sb cortex schema --check` report it as drifted until someone runs `sb cortex schema --render` on the host. Run it as part of the deploy?
- Not run live: `sb doctor` on a host (the finding is unit-tested, and it is checked against the shipped file).

## Phase 4: sb cortex tag-describe

### Design decisions
- Gate: as P3. Under the doc's rule neither A2 nor A3 beat baseline in P0. Scott overrode the rule on 2026-09-26 ("build it"; see Resolved Decisions), so this phase is built on that decision. No description was written into `config/canonical-tags.yml`: the backfill `--apply` is Scott's approval step.
- Drafting pattern (`borg/patterns/describe-tag.md`), on Scott's steer: Phase 0's trial descriptions were thin (mean 73 chars, drafted from titles only, 3 of 117 with a `; not ...` clause). The pattern drafts from each sample's title and summary, aims for 120-200 chars, names concrete terms that appear in the samples, and adds `; not <neighbor>` whenever a sibling or a common homonym collides (worked example: football blocking; not ad blockers). It stays a definition, never a rule about when to apply the tag, because P0's instruction-style arm A3 cut recall. Registered in `PATTERNS` (`sb/src/cli/bootstrap.rs`).
- Module `cortex::tag_describe` (`cortex/src/tag_describe.rs`): `draft_descriptions` (dry run) and `apply_descriptions` (`--apply`) are separate functions, so `--apply` has no drafter in reach and cannot make a fresh LLM call. `run_draft` is the production entry: it scans the vault and builds the `FabricDrafter`.
- The drafter is a port, `TagDrafter::draft(&DescribeRequest) -> Result<String>`. `FabricDrafter` runs the pattern through `crate::fabric::run_pattern` with `fabric.timeout-secs`, the same runner the entities extractor uses. `parse_description` reads `{"description": ...}` (a code fence or prose around the object is tolerated) and holds it to `TagEntry::described`'s rules. An over-cap or quote-bearing answer is an error, never trimmed to fit.
- The pattern's input is the tag, the group, every sibling entry as `TagEntry::yaml_line` writes it (so a described sibling shows its description to contrast against), and the samples. Each sample is `clip_classifier_text(title, summary)`, where summary is `classify::classifier_text` (`## Summary`, else the body), which is now `pub(crate)` along with `note_title`. So the drafter reads the same string the classifier scores.
- Samples (`select_samples`): notes whose `tags` carry the slug, minus the `--exclude-from` paths, newest first by `date` then `ingested`, ties broken by path so a re-run picks the same set. `run_draft` first drops notes the vault config does not govern (`vault.exclude` / `vault.include`, via `crate::is_excluded`), which keeps `system/quarantine/` copies out of the samples. Default 8 (`DEFAULT_SAMPLES`, Phase 0's count), `--samples` 1-10.
- `--exclude-from` (`load_exclude_list`): one vault-relative path per line, blank lines skipped, a leading `./` stripped. An absolute path is an error naming the line, because it would match no note and silently exclude nothing.
- The cache is `vault::paths::tag_describe_cache_dir()` (`~/.cache/sb/tag-describe/<tag>.json`, new `xdg_cache_dir()` honoring `$XDG_CACHE_HOME`). A `CachedDraft` is `{tag, group, description, source: fabric | set, samples: [path]}`. `samples` is what the P5 harness checks against both gold sets. On load, the tag must match the file name and the description is re-validated.
- A dry run proves each draft lands before caching it: it runs `describe_entry_in_group` on the in-memory buffer. A layout the rewrite refuses shows up at review time, not at `--apply`.
- Failure scope: an unknown tag, or a protect-list tag without leave, fails the whole run before any LLM call. A single bad draft (fabric error, unparseable or rule-breaking answer) fails only that tag. It prints as `! tag: <error>`, is not cached, and the command exits non-zero after the rest are drafted. For a backfill over about 112 tags, one bad answer does not throw away the others.
- `--apply` is all-or-nothing: every tag's text (a cached draft or `--set`) is gathered first, so a missing cache refuses the run before any write. The edits go into one buffer, which is parsed as a whole `CanonicalTagsFile`, then written with one atomic write. The deployed-copy refusal is now a shared `refuse_deployed_apply` in `sb/src/cli/cortex.rs`, used by both `tag-promote` and `tag-describe`.
- Output: `+ tag: "description"` per tag, then an indented line with the sample count (or `--set wording`), the group, and the cache path.

### Deviations
- `--set TAG=TEXT` is exempt from the protect-list refusal. The doc refuses protect-list tags without `--allow-protected` because "their wording should be his", and `--set` is his wording. What `--allow-protected` gates is an LLM draft, at both dry run and `--apply` (a cached `fabric` draft of a protected tag still needs the flag to land).
- `--set` follows the command's dry-run default rather than writing at once: without `--apply` it prints and caches the wording (`source: set`, no samples); with `--apply` it writes. The doc's "writes Scott's own wording with no LLM call" holds for `--set ... --apply`. Either way, no LLM call is made for a `--set` tag. Positional tags are optional when `--set` is given.
- Live success criteria were run with the worktree binary against a scratch `XDG_CONFIG_HOME` (a copy of the host `cortex.yml` plus the new `describe-tag.md`, since the deployed patterns dir does not have it yet) and a scratch `XDG_CACHE_HOME`, so no draft was left in the host cache. `MISE_CONFIG_DIR=~/.config/mise` was needed because the fabric binary is a mise shim, and mise refuses the global config as untrusted once `XDG_CONFIG_HOME` moves. The vault read was the live vault, read-only; `--exclude-from ~/Claude/tags-only-trial/gold-exclude.txt` (83 paths).
  - `sb cortex tag-describe rust --canonical config/canonical-tags.yml --exclude-from ~/Claude/tags-only-trial/gold-exclude.txt`: exit 0, one line `+ rust: "the rust programming language: crates, cargo, memory safety, compiler, rewriting codebases (typescript/zig to rust), rust binaries and cli tools; not corrosion or rust the metal oxide"` (183 chars), drafted from 8 samples, none in the gold list; `sha256sum -c` on `config/canonical-tags.yml` OK (byte-identical).
  - `sb cortex tag-describe work --canonical config/canonical-tags.yml`: exit 1, `Error: tag "work" is on the protect list (`no-classifier-tags` in .../config/canonical-tags.yml); write its description yourself with --set work=TEXT, or pass --allow-protected to use a drafted one`. The file is byte-identical and no LLM call was made.
  - `--apply` was checked against a scratch copy of the vocabulary only: `rust`'s line became `    - rust: "..."` and `diff` showed no other change. `--apply` for `python`, which has no cache, refused with `no cached draft for "python" ...`.

### Tradeoffs
- Keep drafting the remaining tags after one fails and exit non-zero, vs. stopping at the first failure. Every good draft is cached and reviewable, and the failure is still loud (a `!` line and the exit code).
- Newest by `date` (the content date borg preserves across reingest) before `ingested`, vs. `ingested` first. `date` is what a reader means by a note's age, and it is present on manual notes that have no `ingested`.
- One cached file per tag, overwritten by each dry run, vs. keeping a history of drafts. `--apply` must land exactly the last draft shown; a history would add a choice with no command to make it.

### Open questions
- The first `otto deploy` after this ships installs `describe-tag.md` into `~/.config/sb/patterns/`. Until then, a host run of `tag-describe` fails with fabric's missing-pattern error, and `sb doctor`'s pattern drift check flags the new file.
- Tags that no note outside the gold sets carries: 4 were drafted from the slug alone in P0 (`entertainment`, `politics`, `nix`, `synth`). The command drafts them from the name, group and siblings, and prints `drafted from 0 sample note(s)`. Should the backfill `--set` those by hand instead?

## Phase 5: Send described labels

### Design decisions
- Gate: as P3/P4, Scott's override stands for the code ("build it"). The **confirmation** half of the gate (a `gold-2` run against the frozen shipping config) is explicitly out of scope for this phase: `gold-2.md` is frozen but unlabeled, and no description has been approved through P4's `--apply`. Nothing in this phase writes a description into `config/canonical-tags.yml`, touches the live vault, or makes a live classifier.dev call.
- `labels_for_shard(shard: &[String], descriptions: &HashMap<String, String>) -> Vec<(String /*wire*/, String /*slug*/)>` (`distillers/src/tags.rs`): sorts its own output by slug rather than trusting the caller's order, so a described string (`ai: ...`) never reorders past its bare neighbour (`ai-safety`) inside a shard. The **partition** itself (which slugs land in shard A vs B, the pinned 59/58 split) still comes from `shard_labels` over the bare, slug-sorted vocabulary, unchanged; `labels_for_shard` only decides what each shard's slugs are called on the wire.
- `ClassifierDev::label_shards(&self) -> Vec<Vec<(String, String)>>` is the one place `labels_for_shard` is called against `self.canon.descriptions`, so `score_batch`, `wire_usd` (cost estimate), `plan_run_chunks` (bulk chunk sizing), and `scoring_config_hash` all see the same shards. `wire_label_shards` strips the pairs down to the wire strings alone for the three callers that only need cost, not the mapping.
- `score_chunk` now takes the shard's wire labels **and** a `wire_to_slug` map; it sends the wire labels (so a described tag reaches Jev as `homelab: <description>`), validates the returned keys against the wire labels through the unchanged `check_shard_scores` (the existing missing/unknown-key rule, now checked against wire strings), then maps every surviving key back to its slug before merging. The `.expect(...)` on the lookup is safe by construction: `check_shard_scores` already proved every returned key is one of the wire labels sent, and `wire_to_slug` is built from that exact same list.
- `scoring_config_hash` now hashes the wire-label shards (so a description or wording change invalidates every cached `tag-apply` score, per the Data Model's `scoring_config_hash` contract) and adds `instructions` to the digest, since P5 is what makes that field variable.
- `TagsClassifierConfig.instructions: String` defaults to `""`. `request_body` omits the `instructions` key entirely when empty rather than sending `""`, so the wire request for today's all-bare vocabulary is unchanged byte for byte (pinned by `a_bare_only_vocabulary_posts_a_request_byte_identical_to_before_phase_5`). Team-lead direction: A3 (rubric-tightening instructions) did not win P0's rule, so the shipped default carries no instructions string; a host may still set one.
- New fixture `distillers/src/tags/fixtures/classifier-dev-described-2026-09-26.json`: real title/summary and real Opus-drafted `homelab` description from the P0 trial (`~/Claude/tags-only-trial/p0/wire.json` note 31, `descriptions.json`), and the real score (`0.96`) that arm A2's first repeat recorded for that note on both `homelab` (described) and `git` (bare), from `~/Claude/tags-only-trial/p0/runs/A2-1.json`. It is **derived**, not a fresh recording: P0's harness (`arms.py`) logs only the final per-note `{slug: score}` map after its own inverse mapping, never the raw per-shard response keyed by the wire label (`"homelab: <description>"`), and no live described-label call has been made since (the confirmation run is still pending). The fixture reconstructs the wire-keyed shard response by hand from those real numbers. The existing bare fixture (`classifier-dev-2026-09-20.json`) is untouched.
- Config templates (`config/templates/{borg,cortex}.yml.example`) gained a commented-out `instructions:` line next to the other classifier keys, following the existing convention that new keys ship as code defaults and are merely documented in the template (P2's `daily-usd-budget` / `ingest-reserve-usd` did the same).

### Deviations
- None beyond the confirmation-gate carve-out the team lead specified: the doc's Phase 5 gate is "A2 or A3 beat baseline in P0, **and** a confirmation run passes" (`gold-2`); this phase ships the code half only. `sb doctor` was not touched (not named in this phase's bullets or success criteria); it still reports `daily-usd-budget` / `ingest-reserve-usd` and the description count from P2/P3, not `instructions`.

### Tradeoffs
- One `label_shards()` seam feeding `score_batch`, `wire_usd`, `plan_run_chunks`, and `scoring_config_hash`, vs. each computing its own wire labels. A described entry's cost, budget planning, and cache invalidation all move together off one calculation; the cost is an extra `Vec` allocation per call, which is negligible next to an HTTP round trip.
- The fixture reconstructs a wire-format response from Phase 0's already-merged, already-inverse-mapped output rather than waiting for a live described call. Re-recording live would exercise nothing the confirmation run (P5's actual gate) doesn't already cover, and would spend against the free day for a fixture that unit tests replay offline anyway.

### Open questions
- None beyond what P0/P4 already left open: whether A2's near-miss justifies shipping past a strict reading of the rule (Scott already answered "build it" for P3-P4; this phase is the send-path half of that same call), and when Scott labels `gold-2.md` so the confirmation run in this phase's second success criterion can actually run.

## Phase 6: Repeat mean

### Design decisions
- Gate: Phase 0 Results already recorded P6 as go on the baseline winner's six calls (P5 is no-go, so A0's six calls are the like-for-like comparison): mean-of-3 instability 0.170 below single-call 0.195, and mean-of-3 F1 0.743 not below single-call F1 0.741.
- `TagsClassifierConfig.repeats: u8` (`distillers/src/tags.rs`), code default 3 (Phase 0's arm). `ClassifierDev` stores `cfg.repeats.max(1)`: a misconfigured 0 reads as 1 rather than silently scoring nothing, since `wire_usd`'s estimate and a bulk caller's allowance check both assume at least one call per shard.
- `score_batch` restructures its per-shard loop: for each label shard, an accumulator (`Vec<Result<HashMap<slug, (sum, count)>>>`) runs the shard's `repeats` calls, each adding its scores into the running sum/count per slug rather than overwriting. `pending` is recomputed from the accumulator (not just `per_note`) before every repeat, so a note that fails partway through a shard's repeats is dropped from later repeats of that same shard immediately, not only from the next shard: a 402/429/failed chunk marks the accumulator `Err` for those notes, and an empty `pending` set breaks the repeat loop early with no extra calls. Only after all of a shard's repeats finish (or give up early) does the shard fold into `per_note`: `Ok` becomes the per-slug average (`sum / count`), `Err` becomes the note's `Err` for the whole batch. This is what makes "a note whose later repeat fails is Err, not Ok with partial scores" hold: the first repeat's scores are discarded, never surfaced, once a later repeat of the same shard fails.
- `score_chunk` (same recursive halving-on-402 shape as before) now writes into that per-shard accumulator instead of appending a `HashMap` to a per-note `Vec`; averaging happens once per shard in `score_batch`, not per call. This also means a single repeat (`repeats: 1`, or any host that sets it) takes the identical code path as three, with `count` always 1: there is no separate single-call branch to keep in sync.
- `wire_usd` multiplies its per-shard token sum by `repeats` before pricing: `score_batch` posts every shard `repeats` times, so the estimate `BulkRun::run` checks against the day allowance, and `TagClassifier::estimate` reports to `--retag`, must scale the same way the real call count does. `plan_run_chunks` (a single physical request's token/text-count budget) is unchanged; `repeats` multiplies how many such requests are sent per chunk, not one request's own size.
- `scoring_config_hash` now hashes `repeats` alongside the shards, endpoint, `max_labels`, `text_chars`, and `instructions`: a `tag-apply` cursor scored under one repeat count must not be read as valid under another, since the averaged score itself would differ.

### Deviations
- None. The doc's `score_batch(&self, &[TagInput]) -> ScoredBatch` signature, the per-note all-or-nothing rule, and the `repeats: u8` config key are implemented as specified.

### Tradeoffs
- Accumulating sum/count per slug inside the existing per-shard loop, vs. calling the old single-repeat `score_chunk` `repeats` times and averaging the resulting per-shard `HashMap`s afterward. The chosen shape lets a note that fails partway through a shard's repeats stop being sent for that shard's remaining repeats too (not only the next shard), which avoids paying for calls whose answer would be discarded anyway; the cost is that `score_chunk` now takes a `(f32, u32)`-valued accumulator instead of a plain score map, a less obvious type at the call site, documented in its doc comment.
- Existing fixtures in `distillers/src/tags/tests.rs` and `distillers/src/tags/bulk/tests.rs` pin exact HTTP call counts and chunk sizes to test P1/P2 mechanics (chunking, 402 handling, the spend cursor) that are orthogonal to repeat averaging. Rather than multiply every expected count by 3 (and re-derive which failures short-circuit early), both files' `dev_over` test helpers now pin `repeats: 1` explicitly, with a doc comment saying why; repeat-mean behavior itself is covered by dedicated tests instead of folded into those fixtures.
- `sb doctor`'s `classifier_settings_finding` is not extended to print `repeats`, matching the precedent Phase 5 set for `instructions` (not named in this phase's bullets or success criteria either).

### Open questions
- None.

## Phase 7: `tag-promote` drafts the promoted tag's description

### Design decisions
- Gate: as P3. Scott's 2026-09-26 "build it" override stands.
- Reused P4's cache and drafter rather than building a second mechanism: `CachedDraft::save`/`load` and `tag_describe::sample_of` moved from module-private to `pub(crate)` (`cortex/src/tag_describe.rs`) so `proposals.rs` can call them directly. A promotion's cache lands in the same `~/.cache/sb/tag-describe/<tag>.json` P4 uses, keyed by tag slug the same way, so `tag-describe <tag>` and `tag-promote <tag>` would collide on one cache entry if ever run for the same not-yet-canonical tag - accepted, since a tag can't be described by P4 before it's canonical, so the collision window is empty in practice.
- `promote_tags` (`cortex/src/proposals.rs`) gained a `describe: Option<&PromotionDescribe>` parameter rather than folding describing into the existing 5-arg signature positionally: `PromotionDescribe { notes, staging_root, cache_dir, drafter }` bundles what describing needs, and `None` is exactly `--no-describe` - every one of the ~12 pre-Phase-7 tests now passes `None` and is otherwise byte-for-byte unchanged, which is itself the proof that `--no-describe` reproduces pre-Phase-7 behavior exactly (the `descriptions` map stays empty, so every `descriptions.get(tag)` miss falls through to the old bare-insert arm).
- Split the drafting/writing rule from P4's dry-run-drafts, apply-reads-cache contract, applied per invocation rather than per tag: at dry run (`apply: false`), `draft_promotion_description` always drafts fresh from the proposal's own `sources` and caches; at `--apply`, `CachedDraft::load` reads the cache and never drafts. A tag promoted without a prior dry run under describing therefore refuses at apply (missing cache), same message P4's `apply_descriptions` gives.
- **Per-tag failure tolerance, not P4's all-or-nothing.** P4's `apply_descriptions` gathers every tag's text before writing any of them (a backfill over ~112 tags should not partial-write). Promotion's candidates are typically one or a handful of tags from one proposal scan, and a description failure for one must not block a sibling that landed cleanly in the same command line: a tag whose draft errors (dry run) or whose cache is missing (`apply`) is dropped from `to_add` into a new `failed: Vec<(String, String)>` on `TagPromoteReport`, left **as a pending proposal** (not written to the vocabulary, not removed from `tag-proposals.yml`), while every other requested tag in the same call still promotes. This is a deliberate divergence from P4's tolerance model, not an oversight - documented as a Tradeoff below.
- **Samples from the proposal's own `sources`** (`samples_from_sources`, `sample_from_trace`): a vault-relative path is read as a note via the now-`pub(crate)` `tag_describe::sample_of` (title + `classifier_text`, clipped exactly as the classifier sees it); a `trace:<id>` source reads `<staging_root>/<trace>/distilled.yml`'s new `summary: Option<String>` field (added to the deliberately-narrow `StagedDistilled`, `#[serde(default)]` so it stays optional and legacy staged files still parse) via `distillers::tags::clip_classifier_text("", &summary)`. There is no note to take a title from for a trace source, so the title is empty; the assembled string is just `"\n\n" + summary`, clipped the normal way.
- A source that no longer resolves - a moved/deleted note, an expired or unreadable staged `distilled.yml`, an empty summary - is skipped as a sample, not a hard failure, mirroring `embed::read_staged_transcript`'s bounded-reach rule. Drafting off zero samples is not an error either (mirrors P4's `select_samples` finding none): the drafter still has the tag, its group, and its siblings (the group's existing entries, described or bare, read before the tag is inserted).
- `run_promote(vault_root, config, proposals_path, canonical_path, tags, group, apply, describe: bool)` is the CLI's one call site, mirroring `tag_describe::run_draft`: it does the governed vault scan (`is_excluded`/`vault.exclude`/`vault.include`, keeping quarantine copies out of samples) and builds the shared `FabricDrafter` only when `describe` is true, then calls `promote_tags`. `--no-describe` skips the scan and the fabric-runner setup entirely, not just the drafting call.
- CLI (`sb/src/cli/cortex.rs`): new `--no-describe` flag on `TagPromoteArgs`. `print_tag_promote_report` no longer returns early on `r.tags.is_empty()` alone (a run where every tag failed describing has an empty `tags` too) - it checks `r.tags.is_empty() && r.failed.is_empty()`, and the diff's own `! \`tag\` description failed...` line (built once, inside `promote_tags`, so the library and the CLI never need to agree on formatting twice) carries the failure detail. The command exits non-zero (`SilentFailure`) when `report.failed` is non-empty, matching `tag-describe`'s convention.

### Deviations
- None from the phase's two success criteria. The `PromotionDescribe`/`Option<&PromotionDescribe>` shape and the `run_promote` production entry are not named in the doc's bullets; same effect, correct seam (the doc's "`promote_tags` calls the P4 drafter" does not specify a signature, and exact signatures are chronically wrong per the phase-implementer convention).

### Tradeoffs
- Per-tag describing-failure tolerance (this phase) vs. P4's all-or-nothing `--apply` (a missing cache for ANY requested tag refuses the whole write). Chosen because `tag-promote` batches are small and independent - a batch of `entities`/`bridge`-style backfill has no equivalent here - and because leaving a failed tag as a pending proposal (rather than either promoting it bare or refusing its siblings too) is the only choice that is both fail-closed (nothing half-described lands) and non-blocking (a sibling's success isn't held hostage).
- `run_promote` builds the `FabricDrafter` and scans the vault inside `cortex::proposals` (a new dependency on `crate::tag_describe::FabricDrafter` and `crate::config::Config` from `proposals.rs`) rather than leaving that composition in the CLI as the original `TagDescribe` handler does inline. Centralizing it in cortex mirrors `tag_describe::run_draft`'s own shape and keeps `crate::is_excluded`/`crate::parse_patterns` (crate-private in `cortex::lib`) reachable without a third exported wrapper.
- The empty-title trace sample (`"\n\n" + summary`, clipped) vs. inventing a synthetic title (e.g. the trace id, or the distiller's `slug` field). A synthetic title would put non-prose text into the exact string the drafter (and, if this tag is later re-scored, the classifier) reads as content; an empty title costs two leading newlines and nothing else, since `clip_classifier_text` already assembles `"{title}\n\n{text}"` unconditionally.

### Open questions
- None.

## Phase 8: sb cortex tag-apply

### Design decisions
- Screen reading: Phase 0 recorded the screen as no-go (gold-positive recall peaked at 0.690 at N = 1,000, under the 90% bar). So the default candidate set is every eligible note (`all`), and `--candidates N` has no default N. The screened path (`screen:N`) is still built, because the cursor's `candidate_mode`, the widening rule, and the fourth success criterion all need it. It is opt-in, and the `--candidates` help text says why.
- Module `cortex::tag_apply` (`cortex/src/tag_apply.rs`): `tag_apply` is the testable core over injected ports. `run` is the production entry. It loads the deployed vocabulary from `sweep.canonical-path`, builds classifier.dev over the shared ledger and `SystemClock`, sets up the index screen, and places the cursor at `vault::paths::tag_apply_cursor_dir()/<tag>.json` (new, `~/.local/share/sb/cortex/tag-apply/`).
- Scoring reuses P2's `BulkRun` unchanged, with `keep: [tag]`, ledger `path: "tag-apply"`, and `tag: Some(tag)`. P2's loop already skips notes whose `wire_text_hash` still matches the cursor. So `--all` after `screen:300` sends only the notes outside the 300 without any new logic, and an edited note is rescored. `score_batch` returns every slug's uncapped mean score, so reading `scores[tag]` sees a ninth-ranked tag. No `finish` or `select_above_threshold` is involved.
- Deployed-vocabulary refusal (`ensure_deployed`): runs first, before the cursor or the vault is touched. The error names the file read, `sb cortex tag-promote`, and `otto deploy`.
- Mode resolution (`tag_apply`): an explicit `--candidates N` or `--all` widens against the stored mode (`CandidateMode::widest`). A bare rerun (no flag) resumes the cursor's own mode. A tag with no cursor defaults to `all`. So `--apply` after a `--candidates 300` dry run applies within that 300 rather than silently widening to the vault. A screen is recomputed only when it is requested at the width that wins. A narrower request, or a bare resume, keeps the stored list. `all` always re-lists the eligible notes, so notes added since the last run join.
- Candidate list: the stored candidates come first, then new ones, deduped. A candidate that is no longer an eligible note is counted as `missing` and never scored.
- Write (`plan_add`, `write_one`): the note is read from disk at write time, and the plan is made against the tags it holds at that moment. The plan is to add the tag if absent and under `max-per-note`. It never removes a tag and never evicts. So a tag another writer added after the scan is kept. The one field written is `tags`, through `insert_frontmatter_fields`, the writer classify uses. A note at the cap, or already tagged, is never written, so its bytes are unchanged. The dry run makes the same plan and writes nothing.
- Eligible notes (`eligible_notes`): governed by `vault.exclude` and `vault.include`, under `notes/`, and not exempt from `tags` by `frontmatter.path-exempt`. So `notes/ai/**` digests, `system/`, and inbox notes are out. Inbox notes are left to classify's own pass.
- The screen is a port (`CandidateScreen`). `IndexScreen` embeds `screen_query` through `vault::embedding::embed_query` with the index's active model. `screen_query` is `"<tag>: <description>"`, or the bare slug when undescribed. `IndexScreen` ranks with the new `SearchIndex::search_summary_vectors`, which is `search_vector` filtered to `kind = 'summary'` through a shared private `search_vector_of_kind`. It unions that with every hit of the new `SearchIndex::content_phrase_matches`, an FTS5 query `{title body summary} : "<slug>"`, sorted by path. Every phrase hit is kept, not just the top N, as in P0.
- classifier.dev is built whatever `tags.classifier` names, because this verb is the production multi-label call by definition. `threshold`, `instructions`, `repeats`, and the budget keys still come from cortex's `tags.classifier` block.
- Exit status: 0 when a run stops at the day allowance or `--max-usd`, as P2 specified. Non-zero (`SilentFailure`) when any note failed to score or write, as `tag-describe` and `tag-promote` do.
- `distillers::tags::Transport` and `ClassifierDev::with_transport` are now `pub`, as P1's tradeoff anticipated, so cortex's tests drive the real `ClassifierDev` against a fake service. Cortex's tests implement their own `Clock` (`FixedClock`), since distillers' `FakeClock` is `#[cfg(test)]` crate-private.

### Deviations
- Cursor shape: the Data Model gives `scores: {path: {score, wire_text_hash}}`. The file holds P2's `ScoreCursor` flattened beside `tag`, `candidate_mode`, and `candidates`, so each entry is `{scores: {<tag>: score}, wire_text_hash}`. The `keep: [tag]` filter P2 built for this verb stores only the target slug. Same effect, correct seam: one cursor type and one reuse rule, shared with the bulk loop. `the_cursor_file_reads_as_one_object` pins the top-level keys.
- The doc's parenthetical about `write_fields` (`cortex/src/classify.rs:634-654`, which rereads the file but writes precomputed fields) is honored by tag-apply not using that path. Classify's own catch-up and `--retag` writes are unchanged, since this phase's bullets are about tag-apply's write. See Open questions.
- Success criterion 1 is a CLI criterion, so it was checked two ways. `a_tag_missing_from_the_deployed_vocabulary_is_refused_naming_otto_deploy` covers the library, and the worktree binary covers the CLI: `sb cortex -c <scratch cortex.yml with sweep.canonical-path = config/canonical-tags.yml> --vault <scratch> tag-apply not-a-deployed-tag` exits 1 with `Error: tag "not-a-deployed-tag" is not in the deployed vocabulary (.../config/canonical-tags.yml). Promote it into config/canonical-tags.yml with `sb cortex tag-promote`, commit, and run `otto deploy`, then rerun tag-apply.`. `XDG_DATA_HOME` was scratch, so no host state was touched.
- Acceptance criterion `sb cortex tag-apply --help`: exit 0 with `target/debug/sb`.

### Tradeoffs
- A bare rerun resumes the stored mode, vs. defaulting to `all` every time. A default of `all` would make `tag-apply X --apply` after a `--candidates 300` dry run silently score the whole vault before writing. Resuming does what the dry run showed.
- Only `notes/` is eligible, vs. every scanned note. Hub, system, and inbox notes are not what "existing notes" means for a tag. Inbox notes are classified in full on promotion anyway.
- Any failed note makes the exit non-zero, vs. exit 0 with the failures only listed. It matches the fleet's other `tag-*` verbs, and it makes a transient 500 visible to a script. The failed notes stay pending in the cursor, so a rerun retries them at no cost for the notes already scored.
- The screen port takes the query text and the slug, vs. taking a `SearchIndex`. Tests then need no embedding model or database, and `IndexScreen` opens the index only when a screen is actually requested. So an `all` run never loads bge-small.

### Open questions
- Should classify's catch-up enrichment (`build_enrichment_fields` then `write_fields`) also recompute its union against the file at write time, as tag-apply now does? Today it unions against the scan-time tags. The doc's reference to `classify.rs:634-654` could be read as asking for that too.
- Not run live, per the doc's r4 staff defer: no multi-day tag-apply against classifier.dev, and no `IndexScreen` run against oracle.db with the bge-small model. The resume path is exercised only through fakes (a fixed clock and a fake service). Operator check after deploy: `sb cortex tag-apply <tag>` (dry run) on a promoted tag should print the candidate count, the scoring line with spend, and `would add` lines, and should write `~/.local/share/sb/cortex/tag-apply/<tag>.json`. Once the day's allowance is spent, a rerun the next UTC day should report only the remainder scored.
