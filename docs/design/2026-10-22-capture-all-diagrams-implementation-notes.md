## Phase 0: Measure the article filter
### Design decisions
- The draft `FIGURE_TAXONOMY_PROMPT` reuses the `TAXONOMY_PROMPT` category set and output schema verbatim and rewords only the framing (a figure on a web page, not a video frame): design doc "Phase 0 Results": so the same `SlideCategory` parser fits and Phase 5 copies the text unchanged.
- `app-ui` and `webpage` both cover website screenshots, and `b-roll` is widened to cover logos, icons, mascots, memes, and product photos: same prompt: the sample's dominant false-keep risks were XDA screenshots and decorative art, and none of those categories are in `keep`.
- Labels were fixed before the classifier ran and were not edited after: hand-labeling method: so the precision/recall are not tuned to the prompt.
- The prompt passed on its first draft, so there was no revision loop: Phase 0 gate: nothing was tuned.

### Deviations
- The classify call was made from a Python harness posting the same request body to the Messages API, not through Rust `ocr::vision_classify`: the phase said zero repo code and the Rust fn is not drivable without a harness crate; the endpoint, model (`claude-sonnet-5`), `max_tokens` (64), and body shape are identical. Same effect, different caller.
- Images over 3.5 MB or 2048 px were downscaled to a 2048 px jpeg before classify: the API's 5 MB per-image limit; 10 of 143 survivors exceed 2 MiB, max 3.2 MB, so this touched only the large-pixel-count images. Borg's real path will downscale at `max-bytes` (Phase 1).
- The prefilter was reimplemented in the harness (format, URL tokens, `min-side-px`, per-note sha256): the Rust prefilter is Phase 4; the harness mirrors the design's rules and does not claim to match that code.
- 40 sample notes are the 40 most recent readable stages with image refs (by mtime), not a random draw; the 60 labeled survivors are a seeded random draw from those.

### Tradeoffs
- 60 labels from 17 notes vs a draw across more notes: the 40-note sample yields 143 survivors from 27 notes, concentrated in a few image-heavy articles (XDA, stateof.ai, a jev post), so the labeled set is clustered. Recorded; the precision margin (one image) is flagged in the doc.
- Borderline labels (#30 Obsidian canvas screenshot, #41 portrait slide, #56 graph view) were called by eye and left as first labeled, against re-labeling to fit: the gate is only honest if labels are not adjusted.

### Open questions
- Is a precision margin of one image (0.909 vs the 0.9 gate) enough to proceed to Phase 5, or should the labeled set be widened with a second draw first? The criterion as written is met.
- Phase 4 SVG rasterization: the `resvg` CLI draws no text without a loaded font and skips CSS class styling on some SVGs (2 of 10 rendered black). Should Phase 4 load a `fontdb` fallback? The doc's Phase 4 does not mention fonts; this is recorded in Phase 0 Results.

## Phase 1: Config and owned-images plumbing
### Design decisions
- `ImagesConfig` / `FigureFilterConfig` live in their own `borg/src/config/images.rs`, with `#[serde(default)]` structs whose `Default` carries the documented values (not `ContentFilterConfig`): an omitted block, a block with only `enabled: true`, and a partial `content-filter` all land on the same defaults; tests pin each.
- `slides::cleanup` reads both keys through one `Owned { slides, images }` and `read_old_owned`, diffed per key by `compute_all_orphans` — `borg/src/slides/cleanup.rs` — slides keep their own key and behavior; a path that moves between keys is still an orphan of its old key.
- `read_old_owned` is called with `?` in `process_url_inner` where `read_old_slides_frontmatter` was `unwrap_or_default()` — `borg/src/pipeline.rs` — a swallowed read error would read as "owns no images", which defeats the degraded-reingest rule and orphans files; `read_preserved_fields` just above already fails closed on the same file.
- The ordering lives in one writer, `publish::publish_url_note` (degraded-reingest refusal -> size gate -> `figures::store` -> `archive_then_publish` -> orphan cleanup), with a typed `UrlPublishError` carrying the failure stage — `borg/src/pipeline/publish.rs` — so the success-criterion tests run through the real writer, not `process_x_post_from`, and `process_url_inner` cannot reorder the steps.
- `process_url_inner` already runs the final ordering with an empty `FigureSet` (nothing produces figures until Phase 2): `plan` -> render (`images:` from the plan) -> `publish_url_note`. `fetch_degraded` is OR-ed with the image stage's degraded flag.
- Store-failure rollback: `figures::store` removes the files it already created before returning its error — `borg/src/pipeline/figures.rs:store` — so a half-stored set never leaks into the caller.
- `images:` stays out of `BORG_PRESERVE_KEYS` and `CORTEX_PRESERVE_KEYS`; a test pins both.

### Deviations
- The design says `store` downscales over `max-bytes`; `plan` does it. Same effect, correct seam: the downscale can change the extension (gif -> png) and can drop the figure (still over the cap), and both must be known when `plan` assigns the path the note embeds and when the note renders, which is before `store` runs. `plan` stays free of I/O (decode + encode only). `plan` therefore takes `&ImagesConfig` and returns `Plan { planned, degraded }`, not a bare `Vec<PlannedFigure>`.
- `figures::Figure` carries only `bytes`, `mime`, `section`, not the design's full `Figure { candidate, bytes, mime, width, height, category, section }`: `Candidate`, `SlideCategory`, and dimensions belong to the phases that produce them. `Gif`/`Webp` variants and `section` carry `#[expect(dead_code)]` with a reason until Phase 2 constructs and reads them.
- A figure-file write failure fails the publish (`publish-failed`, created files removed) instead of "drop that figure, degrade the receipt": by the time `store` runs the note is already rendered with that figure embedded, so dropping it would publish a dangling embed. Download, classify, describe, and oversize-after-downscale failures (all before render) do degrade.
- `FigureSet`'s `## Images` section render is not in this phase: the design puts it in Phase 2 ("renders `## Images`"). Phase 1 renders only the `images:` frontmatter.
- Old `publish_failure_result` was replaced by `url_publish_failure_result`, since the one production caller now goes through `UrlPublishError`; its existing test was ported, not removed.

### Tradeoffs
- One writer function with a spec struct vs adding the gate/store/cleanup inline in `process_url_inner`: the inline form cannot be tested without driving the whole URL pipeline, which the phase's criteria forbid.
- `plan` hashes the final stored bytes (post-downscale) for `sha8` vs the downloaded bytes: the name then matches the file's content, so a reused path means identical bytes.

### Open questions
- Should a figure-file write failure degrade-and-drop instead of failing the publish? That needs `store` to run before render, which would put file writes ahead of the size gate and break the "gate fails write 0 files" criterion. Left as fail-closed.

## Phase 2: X post photos stored and embedded
### Design decisions
- `photos.rs` and its tests moved into `figures.rs` / `figures/tests.rs` (the old files are gone); `describe_x_photos` now returns `XPhotos { images, figures, degraded }`: `images` is the per-photo section list the distiller source markdown still splices (`x::render` unchanged), `figures` is the `FigureSet` to store — `borg/src/pipeline/figures.rs` — so the distiller input and the stored note cannot disagree about which photos were described.
- `describe_photo` returns a `DescribedPhoto { bytes, mime: Option<FigureMime>, section }`; the MIME is the response `Content-Type` mapped by `FigureMime::from_content_type`, never the URL — `figures.rs:describe_photo`.
- `download_photo` enforces `images.max-download-bytes` twice: a declared `Content-Length` over the ceiling bails before any read, and the body is read in chunks and bails the moment the running total crosses it (a missing or lying header cannot defeat it) — `figures.rs:download_photo`.
- The section is capped once, at describe time (`cap_section`, line boundary, trailing `…`), so the distiller input and the `## Images` block carry the same text — `figures.rs`.
- `Plan` gained `images_section` (built inside `plan` from the same loop that assigns names), and `with_images_section` appends it to the distilled body after plan and before `render_note` adds the Source footer — `figures.rs:plan`, `pipeline.rs:process_url_inner`. A dropped figure (oversize after downscale) leaves no embed, so the embed list and `images:` come from one pass and cannot diverge.
- `Figure` gained `provenance` (`In @handle's post`); the quoted post's photo carries the quoted author's handle (the vic flowchart is `@boristane`'s).
- `FetchedPost.degraded` stays the describe-stage flag (it holds with `images.enabled: false`, as before); `FigureSet.degraded` is the image-stage flag and is only set when images are enabled. `process_url_inner` ORs `FetchedPost.degraded` and the plan's flag into `fetch_degraded`, and the writer gets `figure_set.degraded || plan.degraded`.
- Success-criteria tests run through the real writer, not `process_x_post_from` alone: `vic_photo_is_stored_embedded_and_listed` and `photo_download_error_yields_no_images_section_and_degrades` (`borg/src/pipeline/tests/x.rs`) fetch through the stubs, then `plan` -> `with_images_section` -> `render_note` -> `publish_url_note`. Each was broken once (figure push skipped; download error returning non-degraded) and shown failing before restore.
- Phase 1's `#[expect(dead_code)]` markers on `Gif`/`Webp` and `Figure.section` are removed (now constructed and read).

### Deviations
- The publish-path tests assemble plan -> render -> `publish_url_note` by hand instead of driving `process_url`: a full `process_url` run needs the distiller LLM, tags, and the real XDG ledger (`ledger::append_entry`), which a test must not write to. Same helpers as production (`figures::plan`, `with_images_section`, `render_note`, `publish_url_note`); `process_url_inner`'s own glue (`figure_set = post.figures`, the `with_images_section` call) has no direct test.
- A photo that downloaded but is in a format borg does not store (avif, bmp, tiff, ...) is described for the distiller as before but not stored or embedded, and does not degrade: the design's prefilter makes those a drop, not an error. The full prefilter is Phase 4; this is the minimum Phase 2 needs to name a file extension from the MIME.
- A photo whose vision and OCR both produce nothing is still omitted entirely (not stored), as before: its section would be empty and the doc says a dropped image never publishes an empty heading.

### Tradeoffs
- Cap at describe time vs cap in `plan`: describe-time keeps one text for both the distiller and the note, at the cost of the distiller seeing the truncated form of a very long OCR dump (the design wants the cap to protect the note budget; the 1500-byte default is also what the model needs).
- Chunked read vs `response.bytes()` with a post-hoc length check: the chunked read stops a hostile body at the ceiling instead of buffering 20 MiB+ first.

### Open questions
- None.

## Phase 3: X Article figures
### Design decisions
- Serde for `entityRanges`, `entityMap` (a list of `{key, value}`), and `media_entities` on `x::Block` / `x::ArticleContent` / `x::Article`; every key and media id is read through one `key_as_string` deserializer, since a block's range key is a JSON number and the entity map's is a string — `borg/src/x.rs` — one comparison type, and a non-scalar key is a parse error (fail loudly), pinned by `x_article_entity_key_rejects_non_scalar`.
- `x::article_figures(post)` resolves `atomic` block -> `entityRanges[0].key` -> entity -> `MEDIA` -> each `mediaItems[].mediaId` -> `media_entities[].media_info.original_img_url`, caption from the entity; any break in that chain skips the block with an `info` log line and returns the rest — `x.rs:article_figures` / `resolve_atomic`.
- `DescribedImage` gained `place: Place { Photo | Figure(n) }`, `n` indexing `article_figures` of the owning post; `render_blocks` emits a placed figure at its `atomic` block as `<sub> Image N`, `*caption*`, then the section, and an atomic block with nothing placed still renders nothing — `x.rs:render_blocks` — so the distiller sees the figure where the author put it.
- `FIGURE_TAXONOMY_PROMPT` sits beside `TAXONOMY_PROMPT` with `classify_figure(bytes, mime, &FigureFilterConfig, &LlmConfig)`, same `parse_classification` and fail-closed `ClassifyError`; the prompt text was checked byte-equal against the doc's Phase 0 block (2050 bytes) — `borg/src/slides/classify.rs`.
- `keep_outcome` now delegates to `keep_outcome_for(result, keep, min_confidence)`, which the figure path calls with `images.content-filter` — `slides/classify.rs` — one keep rule for slides and figures.
- `figures::collect_classified(candidates, config, ocr, trace_id) -> Collected` is the source-agnostic classified path Phase 5 reuses: first `max-candidates` downloaded concurrently -> classify concurrently (vision pool bounds it) -> keep -> cap at `max-per-note` in source order -> describe concurrently; returns one slot per candidate, positionally aligned. Drops are tallied `prefilter / not-diagram / cap / error` and written as the design's one `info` line per call; only `error` degrades — `borg/src/pipeline/figures.rs`.
- `describe_photo` split into `download_photo` + `describe_bytes` so the classified path describes bytes it already downloaded (no second fetch) through the same OCR + vision + `image_section` + `cap_section` code as X photos.
- `describe_x_photos`/`XPhotos` became `describe_x_media`/`XMedia`: photos (unclassified, as before) and both posts' Article figures (classified) run concurrently; `FigureSet` is assembled in source order, per owner the Article's figures then its photos, post before quote. A kept figure's provenance is its caption, else `In @<handle>'s article`.
- With `images.enabled: false` no Article figure is downloaded, classified, or placed (today's behavior); with `content-filter.enabled: false` every downloaded figure is kept unclassified up to the cap. Classify uses `content-filter.model` and ignores `vision.enabled`, as `classify_slide` does.
- Success-criterion tests, each broken once and seen failing before restore: (1) `x::tests::x_article_ubereng_yields_six_figures_in_block_order_with_captions` (broken: caption dropped); (2) `x::tests::x_article_unresolvable_atomic_block_is_skipped_and_render_succeeds` (broken: an unresolvable block aborts resolution); (3) `pipeline::tests::x::article::x_article_title_card_figure_is_not_kept` (broken: `DroppedNotInKeep` treated as keep; 6 describe calls instead of 5).

### Deviations
- Criterion 1 says "each with its `Figure N` caption"; the live Article's sixth figure (block 84, the Omni MCP diagram) has no caption in fxtwitter's JSON (Phase 0 Results already calls it "uncaptioned"). The test asserts captions `Figure 1`..`Figure 5` plus `None` for the sixth, and that figure's provenance falls back to `In @UberEng's article`.
- `Candidate` is `{ url, provenance }`, not `{ url, alt, caption, origin }`: the only thing `origin` decided was "X post photos skip classify", and X photos never enter `collect_classified`, so every candidate there is classified by construction. Phase 5 adds what web articles need (alt text into provenance fits the same field).
- The fixture replaces `borg/src/x/article.json` rather than adding a second UberEng file: one Article fixture, now trimmed from the live JSON with all 93 blocks (`type`, `text`, `entityRanges`), the full `entityMap`, and `media_entities` cut to `media_id` + `media_info.{original_img_url,width,height}`. Every pre-existing test on `ARTICLE` still passes against it.
- SVG reaching the classified path is dropped as `prefilter` (`unsupported-format`): the vision API takes no svg and the rasterizer is Phase 4. X Article media is pbs JPEG, so nothing hits this today.
- `Figure` still carries no `category`/`width`/`height`: nothing reads them yet.
- Overflow past `max-candidates` is counted in the `cap` bucket of the log line (the design names only the four buckets).

### Tradeoffs
- Concurrent classify and describe fan-out via `join_all` vs a `JoinSet` like `classify_slides`: the vision permit pool already bounds in-flight calls and `join_all` keeps results in order without an index-reassembly step; a panic in one future would take the trace down rather than one figure, accepted since the futures do no unchecked indexing.
- Placing figures by index into a fresh `article_figures` call at render time vs threading block indices through `DescribedImage`: the resolution is pure and cheap, and one function stays the only place the entity chain is walked.

### Open questions
- Should X post photos also route through a shared `collect` (classify skipped) so they emit the same `figures: kept=… dropped={…}` line? Phase 2's path is unchanged and logs per photo only.

## Phase 4: The deterministic prefilter and article candidates
### Design decisions
- `prefilter(cfg, source, url, mime, dims, bytes) -> Keep | Drop(reason)` is pure and takes `&ImagesConfig` for `min-side-px`; `Source { XPhoto, XArticle, WebArticle }` decides the checks: format checks (http(s) only, stored MIMEs only, non-empty) for every source, whole-token URL match over host + path and `min-side-px` on either axis for `WebArticle` only — `borg/src/pipeline/figures/prefilter.rs` — the config knob has to come from somewhere, and a web image whose header will not decode is dropped `undecodable` (its size is unknown) while an X photo with unknown size is kept.
- The URL-only half is exposed as `prefilter_url` and `collect` runs it BEFORE the download: a `data:` URI (which reqwest cannot fetch and would have degraded the receipt) and a decoration URL are counted as `prefilter` drops and never downloaded — `figures.rs:collect`.
- sha256 dedupe is a separate `Dedupe` (first-seen set), run in `collect` after the prefilter, over the original bytes, for every source — `prefilter.rs:Dedupe` — keeps `prefilter` free of mutable state.
- `figures::collect_classified` is renamed `figures::collect` (it now also serves unclassified X photos; the old name would lie). `Candidate` gained `source: Source`; classify runs for a candidate iff `source.is_classified()` (not `XPhoto`) and `content-filter.enabled`. X photos now go through the same `collect`, so X posts emit the one `figures: kept=N dropped={prefilter, not-diagram, cap, error}` line per trace. `describe_photo` and `DescribedPhoto` are gone; `describe_bytes` returns `(Option<String> section, degraded)`. Orchestrator gap-fill 2, done: no Phase 2 test's asserted behavior changed (every multi-photo Phase 2 test uses distinct or failing photos; the stub's identical bytes would only matter with two successful photos).
- `describe_x_media` builds one candidate list in FigureSet order (per owner: Article figures, then photos; post before quote), so `collect`'s cap, the stored order, and the distiller's `DescribedImage` list all come from one pass — `figures.rs:describe_x_media`.
- Candidate parsing: `candidates::parse_markdown_images(markdown, page_url) -> Vec<MarkdownImage { alt, url, span }>`: `![alt](url)` with optional title, `<...>` destinations, Substack inner `"src"` (plain and `%22src%22` percent-encoded), relative and protocol-relative URLs joined against the page URL, `data:` URIs returned as written so the prefilter counts them, `span` so Phase 5 can splice in place — `borg/src/pipeline/figures/candidates.rs`. Unwired by design; the module carries a `cfg_attr(not(test), expect(dead_code))` that goes when Phase 5 calls it.
- SVG: `svg::rasterize(bytes, max_side_px) -> Raster { png, intrinsic }` on a white background. Lockdown: `locked_options()` sets `resources_dir: None` and BOTH `resolve_string` and `resolve_data` to `|..| None` — `figures/svg.rs`. Resolving data-URI hrefs to nothing too is stricter than the doc (which names only path hrefs): nested resources are not worth the surface, and the cost is a diagram with an inline raster loses that raster in the render sent to vision (the stored `.svg` is untouched). `rasterize_with(.., &Options)` exists only so the lockdown test can render the same SVG under `usvg::Options::default()`; production goes through `rasterize`.
- Orchestrator gap-fill 1, fonts: `fonts()` loads system fonts once (`OnceLock`) and points every generic family (serif, sans-serif, monospace, cursive, fantasy) at the first installed of DejaVu Sans / Noto Sans / Liberation Sans / Arial / Helvetica, else the first face found, because `fontdb`'s defaults ("Times New Roman", "Arial") are absent on Linux and usvg's selector falls back to the Serif generic. `Options::font_family` is set to the same. No system fonts at all logs a warning and SVG text is not drawn. Font loading touches no `<image href>` path; the lockdown tests run with the font database loaded.
- Raster sizing: longer side clamped to `[min(1024, max-side-px), max-side-px]`. Downscale is the doc's bound; the 1024 floor upscale is mine, so a 100px-wide diagram is legible to the vision model. The prefilter's `min-side-px` reads the SVG's INTRINSIC size (`Raster.intrinsic`), not the upscaled raster, so the floor cannot launder an icon past the size rule.
- A classified SVG is classified and described as the PNG raster; the `Figure` stores the original `.svg` bytes with `FigureMime::Svg` (`Fetched { bytes, mime, raster }`, `vision_bytes()` / `vision_mime()`). An SVG that will not parse is a `prefilter` drop (not an error, not degraded): the page served something unrenderable; nothing failed in borg.
- Success-criteria tests, each broken once and seen failing before restore:
  - Criterion 1 (table): `prefilter::tests::table_drops_decoration_and_unsupported_formats_and_keeps_diagrams` (plus `content_heuristics_do_not_apply_to_x_sources`, `format_checks_apply_to_every_source`, `url_tokens_match_whole_tokens_in_host_and_path_only`) and through `collect`: `collect::web_decoration_is_dropped_by_size_and_url_but_x_photos_of_the_same_size_stay`. Broken: content heuristics switched off; 6 tests failed.
  - Criterion 2 (lockdown): `svg::tests::locked_resolver_renders_a_local_file_href_absent_where_the_default_reads_it` (precondition inside the test: the default resolver DOES render the red fixture) and `locked_resolver_refuses_a_data_uri_href_too`. Broken: both resolvers set back to the defaults; both failed.
  - Criterion 3 (viewBox): `svg::tests::a_huge_viewbox_rasterizes_within_max_side_on_the_longer_side` (100000x50000 viewBox, `max-side-px` 512, raster exactly 512x256). Broken: the upper clamp removed; failed.
  - Fonts (gap-fill): `svg::tests::text_in_an_unknown_webfont_still_draws_pixels`. Broken: `load_system_fonts()` commented out; failed.

### Deviations
- `prefilter` takes `cfg: &ImagesConfig` first and dedupe lives in `Dedupe`, not in the function: the doc's `prefilter(source, url, mime, dims, bytes)` has no place for `min-side-px`, and a pure function cannot carry a seen-set. Same effect, correct seam.
- An X photo or Article figure in a format borg does not store (avif, bmp, tiff) is now dropped as `prefilter` and NOT described for the distiller; Phase 2 described it for the distiller and only skipped storing it. The doc's prefilter makes those a drop for every source, and the vision API cannot take them anyway. No test pinned the old behavior.
- Phase 3's deviation "an SVG on the classified path is dropped as `prefilter`" is resolved: SVG is now rasterized and kept.
- `Candidate` is `{ url, provenance, source }`; Phase 3 recorded it as `{ url, provenance }` because X photos never entered the classified path. They do now, so the field Phase 3 said `origin` would decide came back as `source`.

### Tradeoffs
- Intrinsic size for the SVG `min-side-px` check vs the raster size the doc names: the raster is rescaled for legibility, so only the intrinsic size says whether the author drew something small.
- Locking down data-URI hrefs as well as paths vs path-only: costs an inline-raster-in-SVG render fidelity (rare, vision only), buys "no href of any kind resolves", which is checkable by one test.
- `spawn_blocking` for the render vs inline: the render can take tens of ms on a 2048px raster; the async workers also run the vision calls.

### Open questions
- None.

## Phase 5: Web-article figures
### Design decisions
- One article stage, `pipeline::article::distill_article(url, article_md, clean_source, capture_note, config, ocr, trace_id) -> ArticleStage { distilled, figures }`, called from `process_url_inner`'s article-distiller branch (`borg/src/pipeline/article.rs`, `pipeline.rs`): whichever fetcher produced the markdown (readable, fabric, jina, or jina's browser-UA fallback) goes through the same figure step, and the thread branch (HN, Reddit, X) never does. `figure_set = stage.figures` then joins the existing plan -> render -> `publish_url_note` order, and the existing `fetch_degraded |= figure_set.degraded || plan.degraded` sets the receipt, so no new degraded plumbing.
- `figures::describe_article_media(markdown, page_url, ..) -> ArticleMedia { markdown, figures }`: every `![alt](url)` from `candidates::parse_markdown_images` becomes a `Source::WebArticle` candidate with provenance = trimmed alt text (empty alt prints no provenance line, per `image_block`), through the one `collect` (URL prefilter -> download -> prefilter + dedupe -> classify with `FIGURE_TAXONOMY_PROMPT` -> cap -> describe) — `borg/src/pipeline/figures.rs`. `images.enabled: false` returns the markdown untouched and fetches nothing. The two `dead_code` expects (`mod candidates`, `Source::WebArticle`) are removed.
- Splice, `figures/splice.rs`: each kept image becomes `### Image N`, `*alt*`, then the section (the same shape as an X Article figure). A line holding only the image, or only a linked image (`[![..](img)](href)` leaves `[](href)`), is replaced whole; an image inside prose has just its markup replaced, the block set off by blank lines. Unkept images (not a diagram, capped, failed) stay as written, which is what the distiller saw before this phase.
- Quality gate on the pre-splice source: `distill_for_publish_article` now takes `ArticleInput { markdown, quality_source, clean_source }` (`borg/src/stages/distill.rs`), and `gate_article_transcript(distilled, clean_source, quality_source)` clears the transcript only when `transcript_quality_ok(quality_source)` fails. The distiller reads, and the transcript keeps, the spliced markdown, so figure text reaches `distilled.yml` and the transcript embeddings on a clean source. `transcript_quality_ok` became `pub(crate)` so the pipeline test can assert its precondition.
- Image downloads now send `readability::BROWSER_UA` (made `pub(crate)`), for every source: the Phase 0 fetch numbers (178 of 181) were measured with that UA, and reqwest sends none by default. `download_photo` was renamed `download_image` and its errors say "image", since it now fetches web images too.
- Success-criterion tests in `borg/src/pipeline/tests/article.rs`, driven through the REAL readable handler (`process_article_readable` against a stub-served HTML page, so dom_smoothie + htmd produce the `![alt](url)` lines), then `distill_article` (no fabric binary, so the fallback distill carries the spliced markdown as its transcript), then `figures::plan` -> `render_note` -> `publish_url_note` (the X tests' `publish_post` helper generalized to `publish_figures`). The stub vision API labels each image by an id painted into its pixels. Each was broken once and seen failing before restore:
  - Criterion 1: `article_keeps_the_flowchart_and_the_chart_not_the_app_ui` (broken: `WebArticle` made unclassified; failed, along with three other article tests).
  - Criterion 2: `thirty_flowcharts_cost_thirty_classify_and_twenty_describe_calls` (broken: the `max-per-note` cap disabled; 30 describe calls, failed).
  - Criterion 3, classify error: `a_classify_error_drops_that_image_and_sets_fetch_degraded` (broken: an `ApiError` verdict kept; failed).
  - Criterion 3, quality gate: `a_readable_article_still_passes_the_quality_gate_with_twenty_figures_spliced` (broken: `quality_source` set to the spliced markdown; the transcript was cleared and the test failed). Its preconditions assert the fetched article passes `transcript_quality_ok` and the spliced text alone does not (20 sections of 150 short OCR lines, capped at `max-section-bytes`). Unit twin: `stages::distill::tests::gate_judges_the_pre_splice_source_and_keeps_the_spliced_transcript`.
  - Also: `jina_markdown_images_become_figures_and_the_transcript_is_still_cleared` (the jina path through `process_article_jina`), `images_disabled_leaves_the_article_untouched`, and six `figures::splice::tests`.

### Deviations

## Implementation audit round 1 fold-in
Source: review-panel synthesis `~/.cache/review-panel/runs/jX7Doq8g/synthesis.md` (staff detail in `staff-r1.out` beside it).

### Design decisions
- must-fix 1, candidate destinations: a bare destination now takes `\x` escapes and one level of balanced parens, and is unescaped as CommonMark does (every `\` before ASCII punctuation) — `borg/src/pipeline/figures/candidates.rs:image_re`, `unescape` — htmd 0.5.4 (`element_handler/img.rs`) escapes every `(`/`)` in an image link, so the readable path produced `diagram\(v2\` and a 404; wiki URLs carry bare `File:Foo_(bar).png`. The title arm also takes `\"`, which htmd emits for a quote in a title. The match span now reaches the real closing `)`, so `figures/splice.rs` needed no change: the splice replaces the whole markup and leaves no `.png)` residue (test `an_escaped_paren_url_is_spliced_whole_with_no_residue`).
- must-fix 1, code is not a figure: `code_ranges` marks fenced blocks (backtick or tilde, 3+, up to 3 spaces in, closed by the same char at least as long, unclosed runs to the end) and, outside them, inline code spans (a run of N backticks to the next run of exactly N; an unmatched run is literal); a match starting inside one is skipped — `candidates.rs:code_ranges`, `inline_code_ranges` — a regex cannot see context, and a scanner over the same text is the smallest thing that can.
- must-fix 2, vision bound: `figures::vision_image` produces the ONE image classify, describe, and OCR read, before the first vision call: sent as is when its longer side is within `max-side-px` and it is at most `VISION_MAX_BYTES`; otherwise downscaled to `max-side-px` and re-encoded by the same code `plan` uses (`downscale`'s `fit` / `encode_jpeg` / `encode_png`, split out of `bound`); a png still over goes as jpeg; a jpeg still over is shrunk in proportion to the overshoot, at most 3 times; still over, or undecodable over the bound, drops the figure and degrades — `borg/src/pipeline/figures.rs:vision_image`, `bound_for_vision`, `Fetched::vision` — an SVG's raster goes through the same bound and stands in for the SVG. Stored bytes keep the Phase 1 rule (`bound`: original unless over `max-bytes`).
- `VISION_MAX_BYTES` is 3/4 of 5 MiB (3,932,160), so the base64 payload is also under 5 MiB — `figures.rs` — the panel and this fold-in did not verify whether the API measures raw or base64 bytes; this bound holds under either. It is a constant, not config: it is the API's limit, not an operator tunable.
- The decode/resize runs under `spawn_blocking` (`bound_for_vision`) — a 20 MiB image decode and Lanczos resize would otherwise stall an async worker that is also running vision calls.
- cheap-win 4: `EntityRange.key`, `Entity.key`, `MediaItem.media_id`, `MediaEntity.media_id` are `Option<String>` with `#[serde(default)]`, and `key_as_string` returns `None` for anything not a string or number; `Entity.value` and `MediaEntity.media_info` go through a `lenient` deserializer (`None` when the JSON does not parse as the type) — `borg/src/x.rs` — `resolve_atomic` turns each `None` into a skip reason, so a malformed entity skips its `atomic` block and never fails the post. `MediaItem.media_id` and `Entity.key` were made tolerant too: same failure class, same struct family.
- cheap-win 5: `read_old_owned` normalizes CRLF to LF, then returns `Err` for an unterminated frontmatter block or unparseable YAML; a note that does not open with a `---` line still owns nothing (it has no frontmatter), and an empty block (`---\n---`) owns nothing — `borg/src/slides/cleanup.rs:read_old_owned` — the caller (`pipeline.rs` reingest branch) already propagates with `?`, so the reingest fails closed. CRLF is read rather than refused: it is a valid frontmatter, and refusing it would block every reingest of such a note for no reason.
- cheap-win 6: the size-gate test composes the note through the production functions (`figures::plan` + `with_images_section`), proves the body alone passes the same limit through `publish_url_note`, then shows the composed note is refused `SizeGate` with 0 files under `system/attachments` — `borg/src/pipeline/publish/tests.rs:images_section_that_pushes_a_passing_note_over_the_gate_writes_no_asset`.
- Q4, degraded-reingest rule, ordered by Scott (option B): `publish_url_note` refuses (`fetch-failed`, old note and files untouched) only when the old note owns images AND the image stage degraded AND this run keeps fewer figures (`spec.figures.len()`, the planned set) than the old note's `images:` list — `borg/src/pipeline/publish.rs:publish_url_note` — a degraded run keeping at least as many publishes with its receipt still degraded (the caller already ORs the image stage into `fetch_degraded`); a non-degraded run and a fresh ingest are unchanged. `UrlPublishError::DegradedReingest` now carries `{ owned, keeps }` so the log names both counts. Tests: `degraded_reingest_that_keeps_fewer_images_than_the_old_note_fails_fetch_failed_and_changes_nothing` (the Phase 1 test, adapted from owns-1/keeps-1 to owns-2/keeps-1), `degraded_reingest_that_keeps_as_many_images_as_the_old_note_publishes`, `clean_reingest_that_keeps_fewer_images_publishes_and_removes_the_orphan`.
- Design-doc amendment ordered by Scott (Q4 = option B): the "A degraded reingest never replaces..." paragraph, the Phase 1 bullet and success criterion, and the risk-table row now state the keeps-fewer rule; Resolved Decisions gains "2026-10-22, Scott: a degraded reingest is refused only when it would keep fewer images than the old note owns (option B over refuse-on-any-degrade); one dead candidate no longer strands a note." The rewritten paragraph also drops "store" from its degrade causes and adds `plan` drops, matching the amended Receipt bullet and the code (`image_stage_degraded = figure_set.degraded || figure_plan.degraded`).
- Doc amendments (design doc edited in place, each listed here): (Q1) the SVG sentence now says the size rule reads the SVG's intrinsic size, because the raster's 1024 px legibility floor would launder an icon past `min-side-px`, and the keyword rules apply to the URL: that is what Phase 4 built and disclosed. (Q3) the Data Model "Receipt" bullet drops "store" from the degrade causes and says a store failure fails the publish (`publish-failed`, created files removed first): disclosed in Phase 1 Deviations, the stronger invariant. (cheap-win 3) the `enabled: false` bullet now says X photos still pass the format prefilter, sha256 dedupe, and the `max-section-bytes` cap, nothing is stored, and articles are untouched: what `describe_x_media` does. Two more amendments beyond the three named, so the doc stays the source of truth for code this fold-in changed: the Web-articles candidate bullet now states the escape / balanced-paren / code-skip rules, and the Store-and-publish list gains a "Vision input is bounded before classify" bullet.

### Deviations
- Supersedes Phase 0 Deviations, second bullet ("Borg's real path will downscale at `max-bytes` (Phase 1)"): that was false for the vision call. Phase 1's downscale runs in `plan`, after classify and describe, so until this fold-in the vision API was sent the raw download, up to `max-download-bytes` (20 MiB), and a large image failed classify and degraded the receipt. The bound now runs before classify (decisions above). The Phase 0 entry is left as written; this entry corrects it.
- The vision bound also downscales an image whose bytes are under the limit but whose longer side is over `max-side-px` (an X photo at 4096 px now reaches vision at 2048 px). The fold-in instruction asked for exactly this bound ("longer side <= max-side-px"); it changes the pixels X photos are described from, a behavior change from base `photos.rs`.
- The vision bound adds progressive jpeg shrink when a downscaled image is still over the byte limit (beyond "reuse the existing downscale code"): the first fixture, incompressible noise at 1400 px, stayed over the limit as png and as jpeg at full size, and the alternative was dropping a legitimate large figure that a smaller copy would describe fine.
- `x_article_entity_key_rejects_non_scalar` was renamed and inverted to `x_article_entity_key_non_scalar_reads_as_no_key`: it pinned "a non-scalar key is a parse error", which is inconsistent with "skipped, never an error" (a parse error in one entity fails the whole `Envelope`). The skip itself is pinned by the new raw-JSON test.
- `test_read_old_owned_malformed_yaml` was renamed and inverted to `test_read_old_owned_malformed_yaml_is_an_error`: it pinned the "owns nothing" behavior finding 5 removes.
- The `collect` stub server now lifts axum's 2 MB default request-body cap (`DefaultBodyLimit::disable`): a bounded vision image is still megabytes of base64, and under the cap the stub answered 413, which read as a classify failure.

### Tradeoffs
- A context scanner for code (`code_ranges`) vs a full markdown parser (pulldown-cmark): a parser would also need to map events back to byte spans for the splice, and fenced blocks plus inline spans are the only code constructs an article extractor emits around images. Indented code blocks are not detected: htmd emits fenced blocks, and an indented-block detector misfires on list continuation lines.
- One balanced-paren level vs arbitrary nesting: the `regex` crate has no recursion, and two-level nesting in an image URL was not seen; deeper nesting stops the destination at the inner `)` and the candidate 404s and degrades, as before.
- CommonMark-wide unescape vs only `\(` `\)`: the extractors also escape `_` and `*` in some URLs, and CommonMark says every `\` before ASCII punctuation is that punctuation; unescaping only parens would leave `\_` in a URL.
- Vision bound in `collect` (before classify) vs moving `plan`'s downscale earlier: the stored bytes and the vision bytes have different limits (`max-bytes` 2 MiB for the vault, the API's 5 MB for vision) and different rules (an SVG is never resized for storage, but its raster is what vision reads), so they stay two bounds over one shared downscale.

The "never the URL's" half holds. Deferred: low impact for a vault (Obsidian renders by content for the formats kept), and a sniff would need a policy for header/bytes disagreement.
