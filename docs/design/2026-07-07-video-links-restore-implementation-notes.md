# Implementation Notes: Video Links Restore

## Phase 1: `description::extract_urls` + `merge_description_links`

### Design decisions
- `extract_urls` decomposes per-line rather than one description-wide regex pass -- `borg/src/description.rs:extract_urls` finds all URL occurrences on each line via `find_occurrences`, then derives labels per line via `line_links`, mirroring the shape-decomposition style already used by `github::extract_repo_slugs`/`slug_from_path` (helper functions composed, not one mega-regex).
- Markdown-link spans are found FIRST (`MARKDOWN_LINK_RE`) and their byte ranges recorded in `covered`, so the subsequent bare-token scan (`URL_TOKEN_RE`) skips them -- `borg/src/description.rs:find_occurrences`. This avoids double-counting a markdown-wrapped url as a second bare occurrence.
- The "sole url on line" check for label derivation counts BOTH markdown and bare occurrences together (`find_occurrences` returns one `Vec<UrlOccurrence>` per line, sorted by position) -- `borg/src/description.rs:line_links`. A line with a markdown link AND a second bare url therefore makes both bare, per the Data Model's "multiple urls on one line -> all bare" rule, read as applying uniformly regardless of markdown wrapping.
- The `www.` (scheme-less) alternative is included in `URL_TOKEN_RE` itself, not filtered out beforehand, so a scheme-less candidate is found, attempted through `Url::parse`, fails, and is counted+logged as a drop (`extract_urls`'s `dropped` counter and per-token `debug!`) -- rather than a token that is simply never considered. This matches the Data Model's "dropped-with-log, not silently lost" language literally.
- `trim_trailing_punctuation` (`borg/src/description.rs`) recomputes the open/close paren balance from the CURRENT token on every backward step, so a token like `.../Rust_(programming_language))` (theoretical double-wrap) trims exactly the unbalanced excess rather than all trailing `)` unconditionally.
- `name_url_label` uses `rfind(':')` (last colon before the url), not the first, so a `Name (owner): url` shape keeps the parenthesized qualifier as part of the label per the Data Model's "kept whole" instruction -- `borg/src/description.rs:name_url_label`.
- Dedup in both `extract_urls` and `merge_description_links` uses a plain `HashSet<String>` keyed on the exact url string (no `.to_ascii_lowercase()`), deliberately the opposite of `extract_repo_slugs`'s case-insensitive dedup, per the design's explicit finding 4.

### Deviations
- The Phase 1 success criterion (a) fixture ("the FILTERED description of `ht-4cbdf8`, returns all 10 URLs including the non-github `https://python.useinstructor.com/`") could not be sourced verbatim: the staged artifact at `~/.local/share/sb/borg/stages/ht-4cbdf8/` persists only `envelope.yml`, `body.txt` (the bare YouTube URL), and `distilled.yml` (`links: []`) -- the raw/filtered description text is not durably staged anywhere (per the design doc's own finding 6, the description is fetched a SECOND time inside `distill_for_publish_video` and not persisted as a separate artifact). Per the task's explicit fallback instruction, `test_extract_urls_ht_4cbdf8_representative_fixture` (`borg/src/description/tests.rs`) uses a CONSTRUCTED fixture instead: a numbered "10 down to 1" list built from the real staged `distilled.yml`'s `kind-specific.repos` (9 github repos: chonkie-ai/chonkie, VikParuchuri/marker, langfuse/langfuse, qdrant/qdrant, ollama/ollama, stanfordnlp/dspy, unclecode/crawl4ai, dottxt-ai/outlines, BerriAI/litellm) plus Instructor's actual non-github doc site `https://python.useinstructor.com/`, which is the concrete lost URL the design doc itself cites. This is disclosed here per the "same effect, correct seam" convention; the test comment also states the fixture is constructed, not verbatim.
- Same test also incidentally exercises the "Name: url" label rule for every line (via `N. Name: url` shape) -- not required by criterion (a) but left in as a bonus sanity check (asserted on first/last item only) since it strengthens the fixture without adding scope.

### Tradeoffs
- Decomposed per-line, imperative helper functions (`find_occurrences`/`strip_leading_marker`/`name_url_label`/`trim_trailing_punctuation`) vs. one large regex with named capture groups for the whole label-derivation rule. Chose decomposition: the label rule has multiple ordered cases with a "sole url on line" precondition that isn't expressible cleanly as a single regex, and the decomposed form matches the existing `github.rs` prior-art style this doc explicitly asks to mirror.
- `strip_leading_marker`'s "strip any leading non-alphanumeric run (emoji)" step is a general character-class strip rather than an explicit Unicode-emoji-property match. `regex`'s default (non-`unicode-perl`) build in this workspace doesn't necessarily carry Unicode property classes for every codepoint; a blanket "non-alphanumeric, non-quote" strip covers the documented "emoji/whitespace prefix stripped" case without depending on an emoji-specific character class, at the cost of also stripping a legitimate leading symbol in an unlikely edge case (not observed in the fixtures used here).

## Phase 2: Wire the merge at the video distill seam

### Design decisions
- The merge is wired inside `distill_for_publish_video` (`borg/src/stages/distill.rs`) immediately after `distilled` is built from the distiller/fallback and BEFORE the existing `links=` info log and `write_distilled_yml`. `distilled` was changed from `let` to `let mut`. This ordering is the staging-fidelity invariant: the staged `distilled.yml` and the rendered note now carry the identical merged `links`.
- The filtered description is sourced from the SAME `metadata.description` already fetched at the seam and already consumed by `crate::github::extract_repo_slugs` (`distill.rs:685`). No new fetch is introduced; `## Links` and the `github:` block ride the same second yt-dlp fetch, symmetric with the pre-existing repo-slug harvest (design finding 6).
- `filter_description` returns `Option<String>`, so `.unwrap_or_default()` collapses the None/empty-description case to an empty string, which `merge_description_links` -> `extract_urls` iterates as zero lines and adds nothing -- no `## Links` heading, no panic (criterion (d)).
- Added a function-scoped `debug!` reporting added/dropped/post-merge total counts, carrying the `trace_id` scope key per the logging rule. The pre-existing `info!` at the seam now reports `distilled.links.len()` post-merge because the merge runs above it (criterion (c), finding 1).

### Deviations
- The design's API-Design snippet writes the call as `description::filter_description(...)` / `description::merge_description_links(...)` (bare `description::`). The actual code uses the fully-qualified `crate::description::...` path, matching the existing sibling call `crate::github::extract_repo_slugs` at the same seam (`distill.rs` has no `use crate::description` import). Same effect, correct seam.

### Tradeoffs
- Fully-qualified `crate::description::...` calls at the two call sites vs. adding a `use crate::description;` import. Chose fully-qualified to match the adjacent `crate::github::extract_repo_slugs` call two lines above and avoid a single-use import; keeps the seam's style uniform.

None.

## Phase 3: Regression test

### Design decisions
- The regression test lives in `borg/src/description/tests.rs` (the existing `#[cfg(test)] mod tests;` submodule for `borg/src/description.rs`), NOT a new `borg/tests/` integration test or a new crate dependency. `borg/Cargo.toml` already carries `distillers = { path = "../distillers" }` as a normal (non-dev) dependency -- borg's production code already calls `distillers::render`/`distillers::fallback_distilled` at the `distill.rs` seam -- so `distillers::render` and `distillers::RenderOptions` are reachable from any borg test module with zero new deps, and colocating with the Phase 1 `extract_urls`/`merge_description_links` unit tests keeps the merge->render assertion next to the function it is regression-testing.
- Two new tests: `test_merge_description_links_renders_non_github_url` (positive) and `test_merge_description_links_empty_description_renders_no_links_heading` (negative), both in `borg/src/description/tests.rs`.
- The positive test builds a `vault::distilled::Distilled` the way `distill_for_publish_video` would have it BEFORE the merge (`links: vec![]`, since the transcript-only distiller cannot see description URLs -- the design's root cause), asserts that starting state via a sanity `assert!(distilled.links.is_empty())`, then calls `merge_description_links(&mut distilled.links, filtered_description)` directly (per the design's Phase 3 spec: `merge_description_links` is the load-bearing injectable step, since `distillers::VideoMetadata` carries no description field -- finding 2). It then feeds the resulting `distilled` through `distillers::render(&distilled, distillers::RenderOptions::for_url_publish(&distilled))` and asserts the rendered `body_markdown` both contains `## Links` and contains the non-github url `https://python.useinstructor.com/`, plus (April-parity per the Resolved Decisions) the github url `https://github.com/BerriAI/litellm` is also present.
- The negative test mirrors success criterion (b)/(d) from the design ("a video with no description... publishes with no `## Links` heading and no panic"): an empty filtered description merges to `(0, 0)` added/dropped, `distilled.links` stays empty, and the rendered body does not contain the `## Links` heading string at all (not merely empty urls under it -- `render.rs::push_links` returns early on an empty slice, so the heading itself never emits).
- Used `distillers::render`/`distillers::RenderOptions` (the crate's top-level re-exports from `distillers/src/lib.rs:37`) rather than the fully-qualified `distillers::render::render` module path, matching how `distill.rs` itself would call it in a real render seam.

### Deviations
- None from the Phase 3 spec's mechanics. One documented judgment call: the task's suggested test location was "`borg/tests/` or a `#[cfg(test)]` module... follow the pattern the crate already uses for cross-crate (borg->distillers) render assertions." Borg's existing render-adjacent code (`borg/src/stages/distill.rs`, `borg/src/pipeline/tests.rs`) calls `distillers::render`/`distillers::fallback_distilled` directly inside `#[cfg(test)] mod tests` submodules, not a separate `borg/tests/` integration file -- so placing the Phase 3 test in `borg/src/description/tests.rs` (the submodule already housing the load-bearing `merge_description_links` tests) matches that established in-crate pattern rather than introducing a new `borg/tests/` file for a single test pair.

### Tradeoffs
- Colocating in `borg/src/description/tests.rs` vs. a new `borg/tests/video_links_regression.rs` integration test. Chose colocation: the load-bearing function under regression (`merge_description_links`) already lives there with its Phase 1 unit tests, the crate boundary (borg->distillers) needs no new dev-dependency either way since `distillers` is already a normal dependency, and a solitary two-test integration file would be a new file for no isolation benefit `#[cfg(test)] mod tests` doesn't already provide.
- Constructing a minimal `Distilled::default()`-based fixture (`kind_specific: None`, empty `claims`/`tags`) vs. a fuller `KindPayload::Video(VideoPayload { .. })` fixture matching a real video note. Chose the minimal fixture: the test's subject is the `links` field's merge->render path specifically (Non-Goals: "No render change"), and `RenderOptions::for_url_publish` keys off `KindPayload::Thread` only (`render.rs:37-41`), so `kind_specific: None` exercises the identical `include_transcript: false` branch a real video would take without adding unused `VideoPayload` fields to the fixture.

### Open questions
None.

### Confirming the test bites
Verified by temporarily neutering `merge_description_links` (`borg/src/description.rs`) to `let _ = (&links, filtered_description); return (0, 0);` before its real body (simulating the Phase 2 merge call having no effect -- the closest reachable proxy for "the merge is reverted," since the test drives the function directly rather than through `distill_for_publish_video`), then running `cargo test --workspace --features vec --lib description::tests::test_merge_description_links_renders_non_github_url`. Result: the test FAILED at the `assert_eq!((added, dropped), (2, 0))` line with `left: (0, 0), right: (2, 0)` -- proving the positive assertion depends on the merge actually running, not merely on `render` behaving correctly with a pre-populated `links` vec. The neutering was then reverted (`description.rs` restored to its pre-edit state, verified byte-identical via `diff`) and `otto ci` re-confirmed green.
