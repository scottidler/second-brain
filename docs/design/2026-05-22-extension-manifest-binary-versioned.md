# Design Document: Binary-Versioned Extension Manifest

**Author:** Scott Idler
**Date:** 2026-05-22
**Status:** Draft (post-Architect review)
**Review Passes Completed:** 5/5 + 1 Architect round
**Supersedes (in part):** [`2026-05-21-extension-lifecycle.md`](2026-05-21-extension-lifecycle.md). The `validate` verb, `extension-validate` CI gate, and `strip_volatile_fields` shim introduced there are obsoleted.

## Summary

All version answers must come from the `sb` binary, not from libraries linked into it. The borg library stops calling `env!` for runtime-reported version values; sb passes its own `env!("GIT_DESCRIBE")` into `borg::serve` (for `/health`) and its own `env!("CARGO_PKG_VERSION")` into `extension::{stage, sign, install, show}` (for the .xpi manifest, which Mozilla constrains to semver-shaped strings). At sign and stage time, the extension is materialised into a `tempfile::TempDir`: manifest and schema regenerated from the runtime values, static assets and the AMO sidecar copied from `borg/clients/extension/`, then `web-ext sign` runs there. Committed `manifest.json` and `ingest-schema.json` are deleted; the `validate` verb, `extension-validate` otto task, `strip_volatile_fields`, `describe_drift`, `MAX_DIFF_LINES`, and the orphan `extension::current_version` helper are removed. `borg/build.rs`, `cortex/build.rs`, and `oracle/build.rs` are deleted; `sb/build.rs` stays as-is (emitting only `GIT_DESCRIBE` per the canonical scaffold pattern).

## Problem Statement

### Background

The Firefox extension manifest is generated by `borg::extension::manifest::build_manifest(&Config)`. A snapshot of the output is committed to `borg/clients/extension/manifest.json` so reviewers can see permission and CSP changes in `git diff`, so `otto ci`'s `extension-validate` task can fail on drift, and so `web-ext sign` (which reads a single source directory) has a manifest at sign time.

`build_manifest` resolves the `version` field via `env!("CARGO_PKG_VERSION")` inside the borg crate. `borg/Cargo.toml` has `version.workspace = true`, so that string matches sb's version, but only by workspace coincidence. The library is "right" about the version because every member crate inherits from the same root, not because the library knows which binary will ship it.

`bump` edits the workspace root `Cargo.toml` and amends the commit but does not regenerate `manifest.json`. The post-bump tagged commit therefore has a stale `version` in the committed manifest, which produces false drift the next time `otto ci` runs. The v0.8.14 fix taught `validate` to strip the `version` field from the comparison (`strip_volatile_fields`). The gate passes; the root cause is untouched.

Two adjacent symptoms of the same architectural problem:

- `borg/src/routes.rs:21` calls `env!("GIT_DESCRIBE")` to stamp the `/health` endpoint's version. That `env!` inside borg resolves against borg's own build script (`borg/build.rs`), which is the reason `borg/build.rs` exists. But the `/health` response should report the binary the user installed (sb), not the library's compile-time identity.
- `cortex/build.rs` and `oracle/build.rs` were copied from `borg/build.rs` back when those crates were standalone binaries. Nothing inside their crate ever reads the `GIT_DESCRIBE` env var they set. They run on every workspace build and produce nothing anyone uses.

The canonical pattern, established in `~/repos/scottidler/scaffold/build.rs` and codified in `~/repos/.claude/rules/rust.md` ("Use `GIT_DESCRIBE` from build.rs for version, not `CARGO_PKG_VERSION`"), is: a `build.rs` exists when a crate compiles into a binary that needs `GIT_DESCRIBE` for its `--version` output. Library crates don't have one.

### Problem

Three threads of the same architectural problem:

1. **The version is owned by the wrong crate.** The .xpi is produced by the `sb` binary the user installs. The `version` field on the manifest must reflect that binary's identity. Reading `env!("CARGO_PKG_VERSION")` inside the borg library means the .xpi version answers "what was the borg lib version when sb was built?" rather than "what is the sb binary's version?" The values match today only because `version.workspace = true`. If that ever changes, the .xpi silently lies about which binary built it.

2. **The committed manifest is a denormalised cache.** Nothing reads it as a source of truth. `sign::run` regenerates the manifest immediately before invoking `web-ext`, so the committed file is never the artifact that ships. Maintaining the cache requires the `validate` gate, the `strip_volatile_fields` rule, a regen ritual after every manifest edit, and a CLAUDE.md paragraph telling humans to remember it.

3. **Three library build scripts violate the scaffold pattern.** `borg/build.rs`, `cortex/build.rs`, and `oracle/build.rs` exist because those crates were once standalone binaries. They are now lib-only. The scaffold pattern says lib crates do not have a `build.rs`. `borg/build.rs` is currently "live" only because `borg/src/routes.rs` still calls `env!("GIT_DESCRIBE")` from inside the library, which is itself the version-ownership problem from thread 1.

### Goals

- The .xpi manifest `version` field is sb's `env!("CARGO_PKG_VERSION")`, threaded into the extension API explicitly. Mozilla constrains this field to a semver-shaped string; `CARGO_PKG_VERSION` is the right shape and is what `bump` keeps in sync with the release tag. The borg library does not reach into `env!` for the manifest.
- The `/health` endpoint's version field is sb's `env!("GIT_DESCRIBE")`, threaded into borg's HTTP server at startup via Axum `State`. This matches the scaffold pattern's choice of `GIT_DESCRIBE` for user-visible version reporting (the same string sb's `--version` shows). The borg library does not reach into `env!` for the health endpoint.
- `sb/build.rs` is the only build script in the workspace. It continues to do exactly what the scaffold pattern says: emit `GIT_DESCRIBE`. Nothing else.
- `borg/build.rs`, `cortex/build.rs`, and `oracle/build.rs` are deleted, along with the `build = "build.rs"` lines in their `Cargo.toml`s.
- Sign and stage regenerate the manifest at runtime with the user's actual config and sb's version, write it into a tempdir alongside the static assets and `.amo-upload-uuid`, and invoke `web-ext sign` there.
- Committed `manifest.json` and `ingest-schema.json` are deleted; gitignored to prevent re-introduction.
- The `validate` verb, `generate` verb, `extension-validate` otto task, drift tests, `strip_volatile_fields`, `describe_drift`, `MAX_DIFF_LINES`, and the orphan `extension::current_version` helper are removed.
- Reviewers retain manifest-inspection affordance via structural unit tests and a new `sb borg extension show` verb that prints the resolved manifest to stdout.

### Non-Goals

- Changes to `install::run`, policy file management, AMO API key handling, or any sign/install/uninstall semantics beyond what the new manifest sourcing requires.
- Embedding static assets (`background.js`, `options.html`, `options.js`, `icons/*`, `.amo-upload-uuid`) into the binary.
- Replacing `web-ext` with a custom signing implementation.
- Decoupling the workspace from `version.workspace = true`.
- Changing `sb/build.rs`'s existing `GIT_DESCRIBE` emission. It is consumed by `sb/src/cli.rs` (clap `--version`) and `sb/src/cli/cortex.rs` (log line). Those calls are inside the sb crate; the env var resolves correctly.
- Compile-time generation of `manifest.json` or `ingest-schema.json` into any `OUT_DIR`. An earlier draft of this design proposed it; the artifacts would be orphaned (nothing reads them) and `build.rs`'s role in the scaffold pattern is `GIT_DESCRIBE` only. See Alternative 1.
- Preserving a committed `ingest-schema.json` for external consumers (CI in unrelated repos, scripts that fetch from raw.githubusercontent.com, etc.). Consumers that need the schema now run `sb borg extension show --schema` locally. This is an accepted cost; the published-schema discipline that would be needed to make a committed artifact correct on every `IngestRequest` change is heavier than the current consumer set warrants.

## Proposed Solution

### Overview

1. **`build_manifest` signature changes** to `pub fn build_manifest(version: &str, config: &Config) -> serde_json::Value`. The `env!("CARGO_PKG_VERSION")` line inside `borg/src/extension/manifest.rs` is removed. Library is pure: inputs in, JSON out.

2. **`extension::stage(target_dir, version, config)`** is added. Writes `manifest.json` (via `build_manifest(version, config)`), `ingest-schema.json` (via `build_schema()`), and copies `background.js`, `options.html`, `options.js`, `icons/locutus-{16,48,128}.png`, and `.amo-upload-uuid` from `borg/clients/extension/` into `target_dir`. Idempotent overwrite.

3. **`sign::run` refactor.** Takes `version: &str`. Creates a `tempfile::TempDir`, calls `stage(tempdir.path(), version, config)`, runs `web-ext sign --source-dir <tempdir> --artifacts-dir <repo_root>/borg/clients/extension/web-ext-artifacts`. `TempDir` is held across the child process; `Drop` cleans up on success and on panic.

4. **CLI entry threads sb's versions.** `sb/src/cli/borg/extension.rs` resolves `let version = env!("CARGO_PKG_VERSION");` (Mozilla-shaped, for the manifest) once and passes it into every `extension::*` call. `sb/src/cli/borg.rs` (the borg server-startup dispatch) passes `env!("GIT_DESCRIBE")` into `borg::serve` (for `/health`).

5. **New CLI verbs.** `stage --to <DIR>` materialises the extension to a user-specified directory for `about:debugging` loading. `show [--schema]` prints the resolved manifest (or schema) to stdout.

6. **Removed CLI verbs.** `validate` and `generate` are deleted from `ExtensionCommand`.

7. **Removed library surface.** `extension::validate`, `extension::generate`, `extension::current_version`, `ValidateResult`, `GenerateResult`, `strip_volatile_fields`, `describe_drift`, `MAX_DIFF_LINES`.

8. **`/health` version source.** `AppState` (already in `borg/src/lib.rs:70`, already `Clone`) gains a `pub version: String` field. `pub async fn health()` in `borg/src/routes.rs` is changed to extract `State(state): State<AppState>` and pass `state.version` into the existing `health_handler` helper. `health_handler`'s `version: &'static str` parameter widens to `&str` to accept runtime-stamped values. `borg::serve_init` and `borg::serve` accept a `version: String` parameter and populate `AppState.version` when constructing the router.

9. **CI cleanup.** The `extension-validate` otto task is removed; the `extension-validate` entry in the `ci` task's `before:` list is removed.

10. **Committed-file deletion.** `borg/clients/extension/manifest.json` and `borg/clients/extension/ingest-schema.json` are deleted via `rkvr rmrf` then `git rm`. Gitignore entries added to block re-commit. `.amo-upload-uuid` remains tracked (carries the AMO listing identity).

11. **Build-script cleanup.** `borg/build.rs`, `cortex/build.rs`, `oracle/build.rs` are deleted (`rkvr rmrf`, `git rm`). `build = "build.rs"` is removed from `borg/Cargo.toml`, `cortex/Cargo.toml`, `oracle/Cargo.toml`. `sb/build.rs` is untouched.

12. **Tests.** Drift-validation tests (`validate_ignores_version_drift`, `validate_still_flags_structural_drift`) are deleted. Structural assertions on `build_manifest("0.0.0-test", &Config::default())` are strengthened in `borg/src/extension/manifest/tests.rs`. A new integration test `borg/tests/stage_produces_valid_extension_dir.rs` exercises `stage` end-to-end.

### Architecture

```
   At runtime (sb borg serve, /health endpoint):

       sb startup resolves version = env!("GIT_DESCRIBE") (resolves against sb crate)
                          |
                          v
       borg::serve(config, version) constructs Axum Router with
       AppState { ..., version }
                          |
                          v
       GET /health -> routes::health(State(state)) -> health_handler(.., &state.version)
                   -> { "service": "obsidian-borg", "version": "<sb's GIT_DESCRIBE>" }


   At runtime (sb borg extension sign):

       sb CLI dispatch resolves version = env!("CARGO_PKG_VERSION")
       (resolves against sb crate; Mozilla-shaped semver string)
                          |
                          v
       extension::sign::run(repo_root, &config, version)
                          |
                          v
                  tempfile::TempDir
                          |
                          +--> manifest.json       (build_manifest(version, &config))
                          +--> ingest-schema.json  (build_schema())
                          +--> background.js       (copied)
                          +--> options.html        (copied)
                          +--> options.js          (copied)
                          +--> icons/*             (copied)
                          +--> .amo-upload-uuid    (copied; preserves AMO listing)
                          |
                          v
       web-ext sign --source-dir <tempdir>
                   --artifacts-dir <repo>/borg/clients/extension/web-ext-artifacts
                          |
                          v
       .xpi lands in artifacts-dir; tempdir is dropped
       .xpi filename and internal manifest.version both == sb's CARGO_PKG_VERSION


   At runtime (sb borg extension stage --to ./dev-ext):

       Same staging path as sign; writes to ./dev-ext; no web-ext invocation.
       Loadable in about:debugging as a temporary add-on.


   At runtime (sb borg extension show):

       println!("{}", serde_json::to_string_pretty(&build_manifest(version, &config))?)
       No filesystem writes.
```

### Data Model

One new return type:

```rust
pub struct StageResult {
    pub target_dir: PathBuf,
}
```

`AppState` gains `pub version: String`. `build_manifest`'s signature changes to take `version: &str` as the first parameter. `health_handler`'s `version` parameter widens from `&'static str` to `&str`. `GenerateResult` and `ValidateResult` are deleted along with their consumers.

### API Design

**Removed (public surface in `borg::extension`):**

- `validate(repo_root, config) -> Result<ValidateResult>` and `ValidateResult`.
- `generate(repo_root, config) -> Result<GenerateResult>` and `GenerateResult`.
- `current_version() -> &'static str`. The orphan helper at `borg/src/extension.rs:112`. Its only call site is the `Version` CLI arm, which will print the already-resolved `version` variable instead.
- `strip_volatile_fields`, `describe_drift`, `MAX_DIFF_LINES`.

**Removed (CLI verbs in `sb borg extension`):**

- `validate`, `generate`.

**Added (public surface in `borg::extension`):**

- `stage(target_dir: &Path, version: &str, config: &Config) -> Result<StageResult>`.

**Added (CLI verbs in `sb borg extension`):**

- `stage --to <DIR>`. Materialises the full extension into `<DIR>`. Overwrite idempotent.
- `show [--schema]`. Prints the resolved manifest (or schema) to stdout.

**Changed (signatures):**

- `manifest::build_manifest(version: &str, config: &Config) -> Value`.
- `extension::sign::run(repo_root: &Path, config: &Config, version: &str) -> Result<SignResult>`.
- `extension::install::run(repo_root: &Path, config: &Config, opts: InstallOpts, version: &str) -> Result<InstallResult>` (passes `version` through to sign).
- `borg::lib::serve_init(config: Config, version: String) -> Result<(ServerStartup, ServerHandle)>`.
- `borg::lib::serve(config: Config, version: String, _verbose: bool) -> Result<()>`.
- `borg::health::health_handler(service: &'static str, version: &str) -> Json<HealthResponse>` (parameter type widens).
- `borg::routes::health(State(state): State<AppState>) -> Json<HealthResponse>` (extractor added).
- `borg::AppState { ..., pub version: String }`.

**Unchanged (CLI verbs in `sb borg extension`):**

- `sign`, `install`, `uninstall`, `version`. User-facing UX is identical.

## Alternatives Considered

### Alternative 1: `sb/build.rs` emits manifest.json into `OUT_DIR` at compile time

- **Description:** Extend `sb/build.rs` to write a defaults-config `manifest.json` (and `ingest-schema.json`) into sb's `$OUT_DIR` at every compile. Defaults-only generator factored into a leaf file shared between sb's build script and borg's runtime path via `include!`.
- **Pros:** A canonical snapshot exists somewhere on the filesystem. `cargo build` failures surface manifest-defaults breakage.
- **Cons:** The `$OUT_DIR` artifacts are orphaned. Nothing reads them. `web-ext sign` reads from a tempdir (which is regenerated from sb's runtime version anyway), `show` regenerates at runtime, unit tests call `build_manifest` directly. The `include!` strategy for `IngestRequest` would fail to compile because `IngestRequest` depends on `IngestMethod`, which implements `From<IngestMethod> for vault::schema::Method`. `sb/build.rs` would need `vault` in `[build-dependencies]`, propagating the build-script dependency surface into the entire workspace's type graph. The schema (`schemars::schema_for!(IngestRequest)`) also has zero dependency on the binary's version, so the binary's build script has no architectural claim on emitting it. And the scaffold pattern (`~/repos/scottidler/scaffold/build.rs`) is explicit: `build.rs` exists for `GIT_DESCRIBE` and nothing else.
- **Why not chosen:** Solves no problem the runtime regen doesn't already solve; introduces a build-time dependency surface that escalates fast; violates the established scaffold pattern. This alternative was proposed and then withdrawn after Architect review.

### Alternative 2: `borg/build.rs` writes the manifest instead of `sb/build.rs`

- **Description:** Extend `borg/build.rs` (existed for `GIT_DESCRIBE`) to emit `manifest.json` to borg's `OUT_DIR`. Borg's `env!("CARGO_PKG_VERSION")` stamps the version.
- **Pros:** Smaller change to an existing build script.
- **Cons:** The version baked into the manifest is borg's, not sb's. They match today only because `version.workspace = true`. The .xpi would be correct by workspace coincidence, not by design. The library would still be reaching into `env!` for a value it shouldn't authoritatively own. A future workspace split would silently break the .xpi version.
- **Why not chosen:** Wrong crate owns the answer. The binary's version is what ships.

### Alternative 3: build.rs writes to source tree instead of `OUT_DIR`

- **Description:** Some `build.rs` writes `manifest.json` into `borg/clients/extension/manifest.json` (gitignored) so `web-ext sign` reads it from the source tree.
- **Pros:** `sign::run` does not need tempdir staging.
- **Cons:** Build scripts writing to the source tree is a mild Cargo antipattern: `cargo clean` does not remove the file, parallel cargo runs could race, fresh clones have a "missing file" until the first build. `cargo:rerun-if-changed` rules must be precise to avoid loops. And the runtime path needs tempdir-or-equivalent anyway for the user-config-overridden manifest at sign time.
- **Why not chosen:** Source-tree pollution for no real win; the tempdir staging in `sign::run` is small.

### Alternative 4: Keep the committed file, fix `bump` to regenerate it

- **Description:** Teach `bump` to run a generate verb after editing `Cargo.toml` and amend both files into the same commit.
- **Pros:** Minimal architectural change.
- **Cons:** Couples `bump` to extension-specific logic across every repo it runs on. Every future bump-like tool (auto-release CI, dependabot for cargo) has to learn the same dance. Every non-version edit to `manifest.rs` still needs the regen ritual. The committed file remains a denormalised cache.
- **Why not chosen:** Fixes a symptom; adds coupling instead of removing it.

### Alternative 5: `include_str!` / `include_bytes!` everything into the binary

- **Description:** Embed `background.js`, `options.html`, `options.js`, icons, and `.amo-upload-uuid` into the `sb` binary at compile time.
- **Pros:** Hermetic binary; sign works without source tree access.
- **Cons:** Couples binary size to static assets; editing JS requires a rebuild. Binary already requires the source tree via `extension::extension_dir(repo_root)`, so embedding gains nothing operational.
- **Why not chosen:** Cost for no current win.

### Alternative 6: Status quo, keep `strip_volatile_fields`

- **Description:** Leave the v0.8.14 fix in place.
- **Pros:** Zero change.
- **Cons:** Every future non-version edit to the manifest still needs the regen ritual; the special-case rule sits in the code as a tax on understanding; CLAUDE.md continues to dedicate a paragraph to it; the library still owns the version field via `env!`.
- **Why not chosen:** The workaround works; the architecture does not.

## Technical Considerations

### Dependencies

- **Added:** `tempfile` in `borg/Cargo.toml` `[dependencies]`.
- **Removed:** None at the crate level. `schemars` continues to be a runtime dependency of borg.
- **Not added:** No new `[build-dependencies]` anywhere. The build-script surface in the workspace shrinks (three library build scripts deleted) rather than grows.

### Performance

- Build time: shrinks. Three fewer build scripts run per workspace build. Marginal but measurable in `otto ci` parallelism.
- Sign time: copying static assets adds a handful of `std::fs::copy` calls (~5 files plus 3 icons plus `.amo-upload-uuid`). Sub-50 ms on warm disk; negligible next to the AMO network round-trip.
- CI: `otto ci` drops `extension-validate` (one fewer parallel cargo invocation).

### Security

No change to attack surface. Manifest contents are deterministic functions of `(version, Config)`. AMO signing is unchanged. `TempDir` is created with `0700` permissions on Unix via the `tempfile` crate. `.amo-upload-uuid` carries the AMO listing identity into the tempdir so re-signs continue to target the same listing.

### Testing Strategy

- **Unit tests** (`borg/src/extension/manifest/tests.rs`): structural assertions on `build_manifest("0.0.0-test", &Config::default())` per Phase 4. These are the durable contract.
- **Integration test** (`borg/tests/extension_body_matches_ingest_request.rs`): unchanged; does not depend on any committed file.
- **New integration test** (`borg/tests/stage_produces_valid_extension_dir.rs`): per Phase 4.
- **CI:** `extension-validate` removed; `otto ci` becomes `[lint, bloat, check, test]`.
- **Manual smoke test before merging:** `sb borg extension sign` produces a .xpi whose internal `manifest.version` equals `sb --version`'s tagged-portion (i.e. sb's `CARGO_PKG_VERSION`). `/health` on a running borg server returns sb's `GIT_DESCRIBE`. Both confirm binary-versioned threading end-to-end.

### Rollout Plan

One-shot. The change is internal to the build/sign flow and HTTP server startup; users see only the new `stage` and `show` verbs.

Step ordering within the implementing PR:

1. Phase 0: thread version through borg's HTTP server. `/health` still reports sb's `GIT_DESCRIBE`; the plumbing path changes.
2. Phase 1: thread `version` through the extension manifest API. Existing tests pass with temporary `env!` plumbing in call sites.
3. Phase 2: implement `stage`, refactor `sign::run`, rewire sb CLI. Sign now uses tempdir staging.
4. Phase 3: delete validate/generate/current_version machinery and CI gate. Must follow Phase 2 so there is no window where the gate fires against missing committed files.
5. Phase 4: strengthen tests.
6. Phase 5: delete committed artifacts; delete `borg/build.rs`, `cortex/build.rs`, `oracle/build.rs`.
7. Phase 6: documentation.

Post-merge, `bump && otto deploy` produces a .xpi whose `version` equals sb's authoritative version with no committed snapshot to drift against and no extension-specific coordination needed during bumps.

## Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| `TempDir` is dropped before `web-ext` finishes (lifetime race). | Very Low | High | `sign::run` is synchronous; the `TempDir` is bound to a local variable that lives across `Command::status()`. `into_path()` is not used; `Drop` runs on return. |
| `.amo-upload-uuid` is omitted from the staging copy, causing web-ext to create a new AMO listing per sign. | Low | High | Phase 2 enumerates `.amo-upload-uuid` in the copy list; the integration test asserts byte-equality after staging; the post-merge smoke test confirms AMO listing continuity on first sign. |
| `--artifacts-dir` flag spelling or semantics in `web-ext` differs from current implicit behaviour. | Low | Medium | Phase 2 validates against `web-ext --help`; creates `borg/clients/extension/web-ext-artifacts/` via `create_dir_all` before invoking. |
| Threading `version` through call sites is intrusive. | Low | Low | Three extension call sites (`stage`, `sign::run`, `install::run`) and two borg-server call sites (`serve`, `serve_init`). sb CLI resolves `env!` once per dispatch. Cleaner than library functions reaching into `env!`. |
| Fresh clone cannot dev-load the extension because `borg/clients/extension/` has no manifest. | Medium | Low | Documented in CLAUDE.md and `sb borg extension --help`: `sb borg extension stage --to ./dev-ext`, then load that directory in `about:debugging`. |
| Reviewers lose the `git diff` affordance for manifest changes. | Certain | Low | `sb borg extension show` prints the resolved manifest; structural unit tests in Phase 4 are the durable contract. Reviewers verify behaviour by reading tests rather than JSON. |
| External consumers of `ingest-schema.json` (downloading from raw.githubusercontent.com) lose access. | Low | Low | Accepted as a non-goal; consumers run `sb borg extension show --schema` locally. If a consumer surfaces post-merge, revisit by either republishing the schema or shipping it as a release artifact. |
| Future workspace refactor splits `borg` and `sb` versions. | Low (no plan exists) | Zero with this design | This design takes the binary's version explicitly; a workspace refactor that splits versions cannot regress either the .xpi version or the `/health` version unless the CLI is changed to read borg's version. |

## Open Questions

- [ ] Should `sb borg extension show` accept `--config <path>` and `--version <str>` for what-if inspection? Recommendation: defer. Default to the running binary's version and the loaded config; add flags only if a use case emerges.
- [ ] Should `stage --to <DIR>` warn when `<DIR>` already contains content, or silently overwrite? Recommendation: overwrite. Idempotency beats caution here.
- [ ] Should `sb borg extension stage` accept a default path when `--to` is omitted? Recommendation: require `--to`. Explicit beats implicit for a verb that writes files.
