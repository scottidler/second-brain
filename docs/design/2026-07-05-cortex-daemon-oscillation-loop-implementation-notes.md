# Implementation Notes: Fix the cortex daemon self-write oscillation loop

Design doc: `docs/design/2026-07-05-cortex-daemon-oscillation-loop.md`

## Phase 0: Reproduce the fight + author the failing regression test

### Design decisions
- Reproduced the intel<->sweep two-writer fight by calling `crate::intel::run` then `crate::sweep::migrate` directly (bypassing the daemon), rather than going through `configured_actions` - `cortex/src/daemon/tests.rs::intel_sweep_two_writer_fight_reproduces_across_two_cycles` - matches the task's literal instruction ("run intel then sweep, twice") and avoids `HashMap`-iteration-order nondeterminism between two competing daemon actions.
- Built a minimal, isolated fixture (a fresh empty `tempfile::TempDir` vault plus a from-scratch `SweepConfig` pointed at temp `canonical-tags.yml`/`tag-mapping.yml`/`tag-proposals.yml` files that contain no `digest` entry) rather than reusing `TestVault` - `cortex/src/daemon/tests.rs::sweep_config_without_digest` - `TestVault`'s 15+ fixture notes carry tags (`sre`, `tatari`, `obscure-hobby`, etc.) that are non-canonical against a narrow test vocabulary, which would have added unrelated fingerprint noise to the phantom-fingerprint test and made its assertions harder to reason about.
- Pinned `IntelOpts.as_of` to a fixed date with no notes dated "yesterday" relative to it, so `generate_daily_digest` takes the empty-input branch and never calls the LLM - `cortex/src/daemon/tests.rs::intel_sweep_two_writer_fight_reproduces_across_two_cycles` - keeps the test deterministic and network-free without stubbing the LLM client.
- Authored the Phase 7 empty-fingerprint regression test (`periodic_sweep_fingerprint_does_not_converge_pre_phase1_and_2`) against `configured_actions` (private to `daemon.rs`) via the `daemon/tests.rs` submodule's `use super::*` privilege, calling it twice with only `intel` + `sweep` enabled in a minimal `DaemonConfig` and asserting the second call's fingerprint is non-empty - `cortex/src/daemon/tests.rs` - traced both possible `HashMap` iteration orders of the two-entry `actions` map by hand (intel-before-sweep and sweep-before-intel) and confirmed the second call's fingerprint is non-empty either way, so the test is not flaky across process runs despite `HashMap`'s per-instance random seed.

### Deviations
- Success criterion (b) in the design doc reads "the empty-fingerprint test FAILS on current `main` (the phantom fingerprint is non-empty)." The invoking instructions offered an explicit alternative - "structure it as a test that asserts the CURRENT (buggy) non-empty behavior and will be inverted in Phase 7" - and this implementation took that path: `periodic_sweep_fingerprint_does_not_converge_pre_phase1_and_2` asserts `!fp2.is_empty()` and currently PASSES (proving the bug is real), rather than asserting `fp2.is_empty()` and failing outright. The doc's literal wording ("FAILS") is not met by a `cargo test` exit code; the doc's underlying intent (a test that demonstrably captures today's phantom/non-converging fingerprint and gets inverted once Phases 1-2 land) is met. Phase 7 will flip the assertion to `fp2.is_empty()`, at which point a reversion of Phases 1-2 would make this test fail again - same net effect as the doc's literal ask, achieved via "pin then invert" instead of "author failing then flip."
- No production code was touched in this phase (per the phase's own scope and the task's explicit constraint); the "single scan_vault per cycle" and "lint fingerprint = detections not writes" defects described in the design doc's root-cause section were read and confirmed by inspection (`cortex/src/daemon.rs` `configured_actions`, the `lint`/`link` arms) but are Phase 1's responsibility, not reproduced by a dedicated fixture here - the intel<->sweep fight alone was sufficient to make the Phase 7 test bite deterministically, so a second, more elaborate lint-corpus fixture was not built.

### Tradeoffs
- Placed both new tests in `cortex/src/daemon/tests.rs` rather than splitting the intel<->sweep repro into `cortex/src/intel/tests.rs` or `cortex/src/sweep/tests.rs` - the Phase 7 fingerprint test *must* live in `daemon/tests.rs` (private-fn access to `configured_actions`), and keeping both Phase 0 tests together in one file preserves the narrative link between "here is the fight" and "here is why it breaks the fingerprint invariant" for the next phase's reader.
- Asserted only on the second call's fingerprint (`fp2`) in the convergence test, not on `fp1 == fp2` (byte-identical oscillation) - the exact fingerprint *contents* depend on `HashMap` iteration order between "intel" and "sweep" (traced by hand above), but "second call non-empty" holds under both orders, which is the more robust, order-independent invariant to pin. `fp1`/`fp2` are still included in the panic message for diagnosis if the assumption ever breaks.

### Open questions
- None.

## Phase 1: Fingerprint only actually-written paths

### Design decisions
- Introduced `LintApplyReport { written_paths: Vec<String>, remaining_violations: usize }` in `cortex/src/report.rs`, aggregated inside `lib::lint` from the real return values of all four appliers (`naming::apply_naming`, `frontmatter::apply_frontmatter`, `tags::apply_tags`, `scope::apply_scope` - naming included, per the review-panel finding) plus `duplicates::apply_duplicates`/`quality::apply_quality`/`autotag::apply_autotag` when those rules are explicitly selected via `--rule` - `cortex/src/lib.rs::lint`. `remaining_violations` is `report.violations.len()` after the full rule dispatch, matching the pre-existing "unfixable violation(s) remain" log semantics.
- Changed all four lint appliers' return type from `usize`/`Vec<(PathBuf,PathBuf)>` to `Vec<String>` (the real, byte-changed relative paths each call wrote) - `cortex/src/naming.rs::apply_naming`, `cortex/src/frontmatter.rs::apply_frontmatter`, `cortex/src/tags.rs::apply_tags`, `cortex/src/scope.rs::apply_scope` - matches the already-correct pattern `duplicates::apply_duplicates`/`quality::apply_quality`/`autotag::apply_autotag` used before this phase, so all seven lint/link/sweep appliers now share one contract: "return what you actually wrote, not what you found."
- `naming::apply_naming`'s written-paths list is the union of the NEW path of every rename that landed plus every other note `update_wikilinks_batch` actually rewrote to follow those renames - both `apply_naming` and `update_wikilinks_batch` (`cortex/src/naming.rs`) changed return type from `()`/tuple-list to `Vec<String>` so the rename-following relink writes are visible to the fingerprint too (a rename with zero relink writes was previously invisible to any caller wanting real written paths).
- `linking::apply_linking` now returns `Vec<String>` (the paths it actually inserted a wikilink into) instead of a `usize` count - `cortex/src/linking.rs::apply_linking`. Threaded through `lib::link()` via a new `Report.applied_paths: Vec<String>` field (`cortex/src/report.rs`) alongside the pre-existing `applied: usize` count, so the CLI's "N file(s)" text and the daemon's fingerprint both derive from the one real write-list instead of the CLI-facing count and a separately-sourced (and wrong) lint-suggestion list.
- `sweep::migrate`'s real-write branch (`dry_run == false`) now only records a path in its `modified` return when `rewrite_note_tags` (renamed contract: now returns `Result<bool>`, `true` iff a write landed) actually wrote - `cortex/src/sweep.rs`. The prior code recorded any path where `new_tags != tags`, even when `replace_tags_in_frontmatter` returned `None` (malformed/missing frontmatter block) and no write happened.
- `cortex/src/daemon.rs::configured_actions`: the `lint` arm now fingerprints `lint_apply.written_paths` (never `report.violations` paths); the `link` arm now fingerprints the apply call's `Report.applied_paths` (never the pre-apply lint-suggestion paths); the `sweep` arm needed no code change (it already threaded `sweep::migrate`'s return through `fingerprint.add`) - the fix there is entirely inside `sweep::migrate`'s tightened write-guard.
- `sb/src/cli/cortex.rs`'s `Command::Lint` arm updated for `lib::lint`'s new `(Report, LintApplyReport)` return; the CLI ignores the `LintApplyReport` half (`_lint_apply`) since `sb cortex lint` prints `Report` via `format_human`/`format_json`, unaffected by this phase.

### Deviations
- The design doc's Data Model section says `LintApplyReport` is "new return from the lint apply path" and API Design says "no new cross-crate types beyond that." Implemented at the correct seam: rather than inventing a second channel, `lib::lint`'s signature changed from `Result<Report>` to `Result<(Report, LintApplyReport)>` (one call site to update: `sb/src/cli/cortex.rs`), and `link()`'s pre-existing `Report` gained one field (`applied_paths: Vec<String>`) rather than introducing a second new type for the link seam. Same effect (the daemon draws the fingerprint from a dedicated written-paths value, never from violation/suggestion paths), correct seam (no duplicate scan/dispatch, no parallel "shadow" report threaded alongside the one CLI already prints).
- `periodic_sweep_fingerprint_does_not_converge_pre_phase1_and_2` (Phase 0) is unaffected by this phase's actual code paths (that test only enables `intel`+`sweep`, and the `sweep` fix only changes behavior when a write genuinely fails, which does not occur for the digest note's well-formed frontmatter) - it still asserts `!fp2.is_empty()` and still passes under single-threaded execution. However, running `cargo test -p cortex --lib` under the default *parallel* test runner intermittently makes this test observe an EMPTY `fp1`/`fp2` on both pre-Phase-1 `main` (confirmed via `git stash`) and this phase's code, roughly 1 run in 6-8. Root cause isolated: `cortex/src/startup/tests.rs` mutates the process-global `XDG_CONFIG_HOME` env var (guarded only by that file's own private `ENV_LOCK`, which nothing outside `startup/tests.rs` acquires) while other threads concurrently call `crate::startup::validate_canonical_assets()` (invoked by both `intel::run` and `sweep::migrate`) against the REAL, unrelated `vault::paths::canonical_tags()` path - not the test's own `SweepConfig.canonical_path`. When the race hits mid-cycle, `validate_canonical_assets` transiently errors, the daemon arm logs and skips, and that cycle contributes nothing to the fingerprint - independent of Phase 1's write-guard. This is a **pre-existing test-isolation defect** in `main`, not introduced by this phase; documented here rather than fixed, since it lives entirely in `startup/tests.rs` (out of this phase's scope) and would need a shared, suite-wide env lock to close properly. `otto ci`'s own test run for this phase passed clean (no flake hit).

### Tradeoffs
- Kept `apply_naming`'s internal `Vec<(PathBuf, PathBuf)>` rename-pair bookkeeping (needed by `update_wikilinks_batch`'s rename-map construction) and only converted the PUBLIC return to `Vec<String>` at the function boundary, rather than changing the internal representation too - the tuple shape is the natural type for "what renamed to what" and forcing it to strings earlier would just require re-parsing for the wikilink-rewrite step.
- Extended `Report` with `applied_paths` (a sibling field to the existing `applied: usize`) instead of making `link()`/`lint()` return a second dedicated type for the link seam - `LintApplyReport` is the one new type the doc calls for; reusing `Report` for the `link` seam keeps the "one written-paths carrier per existing report type" pattern consistent and avoids a second parallel type doing the same job.
- Left `duplicates`/`quality`/`auto-tag` folded into `LintApplyReport.written_paths` inside `lib::lint` even though the design doc's Phase 1 bullet names only naming/frontmatter/tags/scope - those three appliers already returned real written paths before this phase (confirmed by inspection) and were previously discarded by `lint()` with `?;` alone; folding them in costs nothing and makes `LintApplyReport` correct for every `--rule` combination `sb cortex lint --apply` can be given, not just the daemon's default four-rule set.

### Open questions
- The pre-existing `startup/tests.rs` env-var race (see Deviations) will keep intermittently flaking `periodic_sweep_fingerprint_does_not_converge_pre_phase1_and_2` (and, after Phase 7 inverts its assertion, could flake the OTHER direction) under parallel `cargo test`/`otto ci` runs. Recommend a follow-up: either give `startup/tests.rs` a suite-wide `ENV_LOCK` that `daemon/tests.rs`'s canonical-assets-dependent tests also acquire, or stop mutating `XDG_CONFIG_HOME` process-globally in `startup/tests.rs` (e.g. inject the resolved path instead of reading `vault::paths::canonical_tags()` from real env at call time). Scott to confirm whether to fold this into Phase 7 (where the same test's assertion flips) or track separately.

## Phase 2: End the intel↔sweep fight + contain scheduled-intel self-writes

### Design decisions
- Input-side idempotency key is a stable **SHA-256** (`cargo add sha2`, resolved v0.11) over the input note set + model id + system prompt, computed BEFORE any LLM call — `cortex/src/intel.rs::compute_input_hash` / `note_signature`. Deliberately NOT `DefaultHasher` (not stable across Rust releases per rules/rust.md; a toolchain bump would silently invalidate every persisted hash). Each note contributes `path\u{1f}date\u{1f}type\u{1f}tags\u{1f}title\u{1f}body`; the `0x1f` unit separator never appears in UTF-8 note text, so field concatenation can't alias. Note signatures are sorted before hashing so `scan_vault` order can't perturb the key.
- The key is persisted as an **`intel-input-hash` frontmatter field on the digest/review note itself** (recommended option from the doc). It rides `Frontmatter.extra` and round-trips deterministically. It is read back at the top of `generate_daily_digest` / `generate_weekly_review` via `persisted_input_hash` (`vault::frontmatter::parse_frontmatter` → `extra["intel-input-hash"]`); when the freshly-computed key matches, the function returns the output path with NO LLM call and NO write — `cortex/src/intel.rs`.
- Emit **no tag** on generated digests/reviews. Removed the hardcoded `tags: [digest]` (daily) and `tags: [review]` (weekly) from the frontmatter strings — `cortex/src/intel.rs::generate_daily_digest` / `generate_weekly_review`. `digest`/`review` are `NoteType` variants, not canonical tags; `type: digest`/`type: review` frontmatter is retained (that IS the schema signal). Grep result: NO downstream consumer keys off `tags: [digest]`/`tags: [review]` — oracle's browse/quality tools filter by `note_type`/domain/status (never tag value `digest`/`review`); no `.base` view under `system/views/` references them; the only repo hits are the `NoteType` schema (`vault/src/schema.rs` FromStr, `config/tests.rs`, `quality/tests.rs` `.note_type(...)`) and the tests being updated here. Safe to remove.
- LLM seam: introduced a small `IntelLlm` trait (port) with a production `AnthropicLlm` adapter over `crate::llm::complete` — `cortex/src/intel.rs`. `generate`/`generate_daily_digest`/`generate_weekly_review` are now generic over `L: IntelLlm` (generics-not-`dyn`, per rules/rust.md DI). `run` constructs `&AnthropicLlm` internally, so its public signature and every caller (`daemon.rs` ×3, `sb/src/cli/cortex.rs`) are unchanged. The test injects a `CountingLlm` fake to assert zero LLM calls on unchanged inputs.
- Weekly key also folds in `notes.len()` (total vault size), because the review renders the total even though only `week_notes` feed the LLM — a whole-vault size change correctly re-qualifies the review.
- daemon: wrapped both scheduled intel arms (`daily`, `weekly`) in the existing `applying.store(true/false)` guard the periodic sweep uses — `cortex/src/daemon.rs`. Captures the `intel::run` result, flips the flag false, THEN logs the error, so the guard bracket is exact.

### Deviations
- The `intel-input-hash` is stamped **unconditionally** whenever the digest is regenerated — including the LLM-failure fallback path and the empty-input path — not only on LLM success. Rationale: success criterion (a) demands ZERO writes on unchanged inputs as a hard invariant, and the daemon's periodic `intel` arm runs every ~5 min; stamping only on success would rewrite a fallback digest on every cycle during an LLM outage (churn that fires the watcher). The tradeoff: a day whose digest was generated during an LLM outage keeps the fallback text until its inputs change (it does heal on any input change — a new note dated yesterday, or the next day's fresh file). Same effect the doc intends (input-unchanged ⇒ no work), documented because "skip regeneration" could be read as "only skip a healthy digest."
- **Forced early inversion of `periodic_sweep_fingerprint_does_not_converge_pre_phase1_and_2`** (renamed → `periodic_sweep_fingerprint_converges_after_phase2`, assertion flipped `!fp2.is_empty()` → `fp2.is_empty()`). The task said to leave this inversion for Phase 7, but that is infeasible: this fixture enables ONLY `intel`+`sweep`, and the mandated tag removal makes the digest tagless, so `sweep::migrate` has nothing to strip and cycle-2's fingerprint is empty — the test's `!fp2.is_empty()` assertion cannot hold after Phase 2 and would leave CI red. The doc's Phase 7 note anticipated exactly this inversion (its own comment said "invert this assertion to `fp2.is_empty()`"); it scheduled it for Phase 7 on the assumption the FULL action-set fixture only converges after Phase 4's link reconciliation. The narrow intel+sweep-only fixture converges at Phase 2. Phase 7 still owns the full-action-set empty-fingerprint invariant. See open question.
- Updated (not deleted) the Phase 0 `intel_sweep_two_writer_fight_reproduces_across_two_cycles` → `intel_sweep_two_writer_fight_no_longer_reproduces`: it now asserts the digest is tagless, `sweep::migrate` reports 0 for the digest across two runs (criterion b), and the second intel run is a byte-for-byte no-op (idempotent skip). This is the explicitly-permitted update of "that test."

### Tradeoffs
- Persisted the key in the note's own frontmatter vs. a separate state entry: chosen because it is self-describing (the note carries the reason it wasn't rewritten), needs no new state file/schema, and round-trips deterministically through the existing frontmatter parser — at the cost of one extra 64-char hex line in each digest.
- Kept the `generate` seam generic and left `run` non-generic (constructs the real client) so no production caller changed — vs. threading `IntelLlm` all the way up through `run`/daemon/sb, which would have rippled the port into three crates for no test benefit (the idempotency contract is fully exercisable at the `generate` seam).
- The criterion-(c) test asserts the guard's *consequence* (a guarded write produces no `VaultChange`, so the latch — modeled locally as the daemon models it — is never cleared) using the real `VaultWatcher` + real `intel::run`, rather than driving the full `start_watching` select-loop. Driving the whole loop would add a long-running-daemon harness for no extra coverage of the specific guard behavior.

### Open questions
- Phase 7 ownership: `periodic_sweep_fingerprint_converges_after_phase2` was inverted here (forced by the mandated tag removal, see Deviations). Phase 7 should confirm this is acceptable and decide whether to additionally author a FULL action-set (`lint`/`link`/`classify`/…) empty-fingerprint regression, which is the invariant its plan actually targets and which only converges after Phase 4. The pre-existing `startup/tests.rs` `XDG_CONFIG_HOME` env race flagged in Phase 1 still applies to this test under parallel runs.

## Phase 3: Embed "examined" marker

### Design decisions
- Chose a **dedicated side table `embedding_examined`** (NOT a watermark column on `notes`, NOT a row in `note_embeddings`) — `vault/src/search/schema.rs::ensure_vec_schema`. Shape: `(note_path, kind, model_version, examined_at INTEGER, PRIMARY KEY(note_path, kind, model_version), FK note_path REFERENCES notes(path) ON DELETE CASCADE)`. It directly mirrors the existing `edge_build_state` side-table precedent (`vault/src/search/graph.rs`) and keeps the sentinel out of both the `notes` row (which oracle's `index_vault` overwrites wholesale on every reindex) and `note_embeddings` (whose NOT NULL `embedding`/`dim` and sentinel-blind `search_vector` scan would let a tombstone poison cosine similarity — the specific review-panel finding). Keyed per `(note_path, kind, model_version)` so a model swap re-examines from scratch, matching the `note_embeddings.model_version` staleness contract.
- `examined_at` stores the note's **indexed `notes.modified_at`** captured at examine time (`StaleTarget.modified_at`), never raw filesystem mtime — `cortex/src/embed.rs`. Re-qualification is a pure SQL comparison against the same indexed column.
- `stale_embedding_targets` gained a uniform `LEFT JOIN embedding_examined x … AND (x.note_path IS NULL OR x.examined_at < n.modified_at)` clause on **all three arms** (summary, transcript-chunk, claim), reusing the existing `?1`/`?2` bound params (no new params) — `vault/src/search/vector.rs`. A note is excluded exactly while its sentinel is current (`examined_at >= n.modified_at`); it re-qualifies the instant the indexed `modified_at` advances. When a re-qualified note then embeds successfully, the `note_embeddings` staleness condition (`e.source_modified_at < n.modified_at`) keeps it out; the stale sentinel row is inert (never wins over a current embedding).
- New vault write/read API — `vault/src/search/vector.rs`: `mark_embedding_examined_batch(&mut self, kind, model_version, &[(String, i64)])` writes the sentinel set in ONE `BEGIN IMMEDIATE` transaction (upsert per row via `ON CONFLICT … DO UPDATE`), mirroring `upsert_embeddings_batch`'s discipline (short write txn, no CPU work inside); `examined_watermark(&self, …) -> Option<i64>` is the read/diagnostic probe. Cortex stays the only writer to embedding-adjacent tables; oracle never calls either.
- Cortex writes the sentinel at every `skipped_empty++` site — the real defect in `process_transcript_batch` (no `## Transcript` / 0 chunks) plus the two defensive skips in `process_summary_batch` / `process_claim_batch` (SQL already excludes those, but marking keeps the "examined, nothing to embed" invariant coherent across all kinds) — `cortex/src/embed.rs`. The batch is flushed BEFORE the `if work.is_empty() { return }` early return so the all-skipped tick still persists its sentinels.

### Deviations
- **Success criterion (a) verified at the `process_batch(TranscriptChunk)` seam, not `daemon_tick_with_model` directly** — `cortex/src/embed/tests.rs::process_transcript_batch_marks_unembeddable_notes_examined_and_converges`. Same effect, correct seam: `process_batch` is the exact body of `daemon_tick_with_model`'s inner loop, but the tick opens its DB from `config.oracle_db_path()` which resolves to a fixed global path (`vault::paths::oracle_db_path()`, not a config field), so a hermetic tick test cannot be redirected to temp SQLite without touching the live embeddings DB — forbidden by the task. Two consecutive `process_batch` calls prove tick-2 `scanned == 0` for the previously-skipped note.
- **No `user_version`/schema-version bump.** `vault/src/search/` has NO version infrastructure by established design (documented verbatim in `schema.rs::ensure_trace_columns`); the crate's migration discipline here is idempotent `CREATE TABLE IF NOT EXISTS` in `ensure_vec_schema`, which cannot half-apply. Introducing `user_version` infra for one additive table would be a larger, out-of-scope deviation from the surrounding pattern. Verified via `embedding_examined_table_created_and_schema_ensure_is_idempotent` (`vault/src/search/schema/tests.rs`): fresh open creates the table; re-ensuring is a no-op.

### Tradeoffs
- Applied the exclusion clause + sentinel write to **all three kinds** rather than transcript-only: costs three near-identical SQL edits and two defensive (currently-unreachable) write sites, but makes the mechanism uniform and drift-proof — if a future schema change ever lets an empty summary/claim slip past the SQL filter, that path already converges instead of re-introducing the oscillation. The alternative (transcript-only) is narrower but leaves the other kinds structurally able to spin.
- Batched sentinel writes in a separate short transaction from the embedding upsert (two txns per batch when both skips and embeds occur) rather than folding them into one: keeps each write window minimal and the two concerns (mark-examined vs. persist-embedding) independently correct, at the cost of one extra `BEGIN IMMEDIATE` on mixed batches.

### Open questions
- None.

## Phase 4: Reconcile link detection↔mutation

### Design decisions
- Chose the shared-matcher approach (not the feasibility-gate approach) — added `is_word_char`/`is_clean_mention` (`cortex/src/linking.rs`) as THE single arbiter of "is this surface linkable here," combining a Unicode-aware word-boundary check (alphanumeric or underscore, matching the `regex` crate's default `\b`/`\w` semantics), the existing-wikilink guard (`in_wikilink` + a trailing-`]]` check), and the existing structural guard (`inside_structure`). Both `LoweredBody::find_mention` (detection, called from `lint_linking`) and `insert_first_wikilink` (mutation) now call this one function on every candidate position instead of each independently re-deriving boundary/wikilink logic.
- Fixed the second, independent source of disagreement: `insert_first_wikilink`'s frontmatter/body split used to be a bare `content.find("\n---")` — a second, buggier reimplementation of the split that already lives at `vault::frontmatter::split_raw` (the exact splitter `parse_frontmatter` uses to produce `Note::body`, i.e. the text detection scans). Swapped `insert_first_wikilink` to call `vault::frontmatter::split_raw` directly (`cortex/src/linking.rs::insert_first_wikilink`), using pointer arithmetic (`body.as_ptr() as usize - content.as_ptr() as usize`) to recover the body's absolute offset from the returned subslice rather than re-deriving the split-point math. `split_raw` requires the closing `---` to be a full, otherwise-blank line, so it does not mis-split on a frontmatter value that itself contains a bare `---` substring (the case the old ad hoc search got wrong).
- Dropped the `\b…\b` regex boundary from `insert_first_wikilink`'s search pattern (now a plain case-insensitive literal match); the boundary decision is made once, uniformly, by `is_clean_mention` on every candidate regardless of which side (substring scan vs. regex `find_iter`) located it.
- Removed the two now-redundant inline checks this refactor superseded: `LoweredBody::find_mention`'s ad hoc `(Some(open), Some(close)) && open > close` / `ends_with("[[")` wikilink check (a strict subset of `in_wikilink`, which also correctly handles the "opened but never closed" case that this ad hoc check missed — the exact hole `in_wikilink`'s own doc comment already flagged) and `insert_first_wikilink`'s duplicate `before.ends_with("[[") || content[abs_end..].starts_with("]]")` check (now folded into `is_clean_mention`).

### Deviations
- None. Implemented exactly as the doc's Architecture bullet specifies ("one shared matcher... extract the boundary+structure logic used by `insert_first_wikilink` into a shared fn that `find_mention`/`lint_linking` also calls"), at the same seam the doc names.

### Tradeoffs
- Shared-matcher over feasibility-gate: the feasibility-gate approach (call `insert_first_wikilink` speculatively inside `lint_linking` just to decide whether to report a violation) would have made detection twice as expensive (every suggestion re-parsed the frontmatter split and re-ran a regex search) and left the two boundary/structure implementations to drift apart again the next time either one is touched. The shared-matcher approach costs one small function extraction and pays it back as a genuine single source of truth — matches the taste rule ("recurring cross-page inconsistency demands shared code that kills the class").
- Kept `find_mention`'s fast lowercase-once-per-note substring scan (`LoweredBody`) for LOCATING candidate positions rather than switching detection to regex-per-term (which would revert the O(notes × terms × body) optimization the struct's own doc comment describes fixing) — only the boundary/structure DECISION at each candidate is now shared, not the scanning mechanism. `insert_first_wikilink` keeps its regex-based scan (needed there regardless, since it operates on one term per call, not the whole title/entity/glossary set); the two scanning mechanisms are still independent, but they now hand every candidate to the identical acceptance predicate, so they can no longer disagree on the answer.

### Open questions
- None.

## Phase 5: Single scan per cycle with explicit rescan boundaries

### Design decisions
- Injected the scan seam as a **generic closure parameter** (`S: FnMut(&Path, &VaultConfig) -> Result<Vec<Note>>`), not a `dyn` trait object or a purpose-built `VaultScanner` port — `cortex/src/daemon.rs::configured_actions_with_scanner`. Matches rules/rust.md's "generics for DI, never `dyn`"; the production entry point `configured_actions` is a one-line wrapper passing the real `crate::vault::scan_vault` fn item (which coerces directly to the closure bound), and tests inject a counting closure over an `Rc<Cell<usize>>` — no new trait, no new module, the smallest seam that makes the call count observable.
- Implemented the rescan rule as a single `dirty: bool` flag threaded through the action loop, not a per-action rescan schedule: before any action consumes the shared `notes`, `if dirty { rescan; dirty = false }`; after an action's apply step reports a non-empty written-paths list, `dirty = true`. This exactly reproduces pre-Phase-5 behavior (every action always re-scanned unconditionally, so every action always saw the freshest on-disk state) while collapsing to zero extra scans whenever nothing changed — `cortex/src/daemon.rs::configured_actions_with_scanner`.
- Threaded the shared `&[Note]` through the full set of actions that read vault-wide note state today: `classify` (new `classify::run_with_notes`), `lint` (new `lib::lint_with_notes`), `link` (new `lib::link_with_notes`), `broken-links`/`duplicates`/`auto-tag`/`quality`/`sweep` (already took `&[Note]` from their own local `scan_vault` call in `daemon.rs`; that local call was deleted and the shared list substituted). Each `_with_notes` function is a thin extraction of the existing scan-then-dispatch body; the original `run`/`lint`/`link` entry points became one-line scan-then-delegate wrappers so every OTHER caller (CLI, existing tests) is unaffected — `cortex/src/classify.rs`, `cortex/src/lib.rs`.
- `classify` runs first by design (it MOVES notes to their final locations via promotion) — the design doc's example boundary. A non-empty `promoted` list sets `dirty = true` immediately after the classify arm, so the very next action to touch `notes` forces a rescan before reading, deterministically covering the doc's mandated boundary — `cortex/src/daemon.rs`.
- Deliberately scoped `intel` and `state` OUT of the shared-notes cache. `state` never calls `scan_vault` at all (confirmed by inspection — it only reads/writes its own manifest cache under `config.state.cache_dir`), so there is nothing to share. `intel` keeps its own independent `scan_vault` call inside `intel::run` (unchanged): folding it into the shared cache would touch Phase 2's input-hash idempotency machinery, which is a different phase's concern and carries regression risk for no scan-count benefit proportional to the risk (intel's own scan is one call, gated by expensive LLM work either way). Because `daemon_config.configured_actions()` iterates a `HashMap` (order not guaranteed), `intel`'s own write could in principle land before a cache-consuming action in the SAME cycle — the `"intel"` arm therefore sets `dirty = true` unconditionally on `Ok(_)`, conservatively protecting every cache-consuming reader that might run after it, at the cost of one possibly-unneeded rescan on a cycle where both `intel` and another writer are enabled.
- Success criterion (a)'s test (`configured_actions_no_mutation_scans_vault_exactly_once`) enables every scan-consuming action (`classify`, `lint`, `link`, `broken-links`, `duplicates`, `auto-tag`, `quality`, `sweep`) in report-only mode over an empty vault, guaranteeing zero writes categorically (report-only `apply: false`/`auto: false` never reaches a write call; an empty note list gives `classify` nothing to promote) rather than hand-crafting a "perfectly clean but non-empty" fixture — deterministic and robust to any future violation-detection change. Criterion (b)'s test (`configured_actions_rescans_once_after_classify_promotion`) uses exactly two configured actions (`classify` + `lint` in report-only mode) so there is no `HashMap`-order ambiguity about which non-classify action runs — asserts exactly 2 scan calls (initial + the one mandated rescan after classify's promotion) and that the promoted note actually landed at `notes/thing.md` — `cortex/src/daemon/tests.rs`.
- Verified both new tests bite: temporarily removed the `dirty = true` line after classify's promotion and reran `configured_actions_rescans_once_after_classify_promotion` — it failed (`left: 1, right: 2`), confirming the rescan boundary is load-bearing and not a tautology; reverted before running the final `otto ci`.

### Deviations
- The design doc's defect description (#4) names "up to 6" scanning actions (`broken-links`, `link`, `duplicates`, `auto-tag`, `quality`, `sweep`); it omits `classify` and `lint`, both of which also independently called `scan_vault` every cycle (via `classify::run`/`lib::lint`'s internal scan). Implemented at the correct, broader seam matching the doc's actual goal ("One `scan_vault` per cycle...") rather than the doc's literal enumeration: `classify` and `lint` were also threaded onto the shared cache, since leaving either out would have made success criterion (a) — "exactly ONE `scan_vault` call" — false whenever those actions are enabled (which they are on the real system: `lint` is one of only two actions the default `DaemonConfig` ships). Same effect the doc intends, correct seam.
- On a scan failure at the TOP of the cycle (the single initial scan), the cycle now returns an empty fingerprint immediately rather than letting each action independently attempt (and independently fail) its own scan as before. Pre-Phase-5, a transient failure in one action's scan did not stop other actions from trying their own fresh scan; post-Phase-5, there is only one scan attempt to fail. In every realistic failure mode (vault root unreadable, permission denied, path gone) a fresh attempt would fail identically for every action anyway, so the user-visible outcome (no fixes applied, one error logged instead of several near-identical ones) is materially the same — documented as a deviation because it is a real, if narrow, behavior change from "always independently retry" to "fail once for the whole cycle."
- On a MID-CYCLE rescan failure (the `dirty` boundary rescan), the implementation logs and continues the cycle using the last-known (stale) `notes` list rather than aborting the remaining actions. This is the closest available approximation to "skip just this action and let the next one try its own fresh scan" (the pre-Phase-5 per-action behavior) now that there is only one shared scan; continuing with stale data lets later, unrelated actions still run instead of abandoning the whole cycle on a transient hiccup.

### Tradeoffs
- Generic closure (`FnMut`) over a purpose-built one-method trait (`VaultScanner`): the closure form needed zero new types and reused the exact signature `crate::vault::scan_vault` already has, so the production wrapper is a one-argument passthrough; a trait would have required a production impl struct plus a test fake struct for the same amount of behavior. Chosen per rules/rust.md's explicit preference for generics/small closures over ceremony when a single-method port would otherwise be introduced.
- `intel`/`state` exclusion (see Deviations/Design decisions) trades a small amount of scan-sharing (intel's own scan, when intel is enabled) for zero risk to Phase 2's already-shipped, already-tested idempotency contract. Wiring intel's `generate` (which already accepts `&[Note]`) onto the shared cache was considered and rejected for this phase: it would require re-verifying Phase 2's zero-LLM-calls-on-unchanged-input invariant against a note list that may now be fresher or staler than intel's own scan would have produced, for a benefit (one fewer scan on ticks where intel actually runs) that is marginal next to intel's own LLM-call cost.
- Chose NOT to eliminate the rescan-on-failure `continue`-with-stale-data path's slight behavior change (see Deviations) by, e.g., propagating the scan error up and aborting the whole daemon tick — a single vault-scan hiccup mid-cycle should not take down every other governance action for the rest of that cycle; logging and proceeding with the last-known state is the same fail-soft philosophy the surrounding per-action `Err(e) => log::error!(...)` arms already use everywhere else in this function.

### Open questions
- None.

## Phase 6: Correct the live unit + complete the install template

### Design decisions
- Extracted a **pure `render_systemd_unit(home, binary, vault_root, config) -> String`** seam (`cortex/src/daemon.rs`) out of `install_systemd_service`, rather than adding the new directives inline into the existing function. `install_systemd_service` now only resolves `home`/`binary`/`service_dir`, calls the pure renderer, and writes the result to disk. This lets the success-criteria tests assert on the generated STRING directly (per the task's explicit instruction) without ever touching the real `~/.config/systemd/user/` — a test calling the old, impure function would have written into the operator's actual systemd config dir on every `cargo test` run.
- Two new `DaemonConfig` fields, both fail-closed/optional (`cortex/src/config.rs`):
  - `rayon-threads: usize` (default `0`) — emits `Environment="RAYON_NUM_THREADS=N"` (plus the explanatory comment line the live unit already carries) only when `> 0`. `0` is a legal sentinel meaning "omit the line, let rayon pick its own default" — not an invalid zero value needing a hand-written `Default`, since `0` IS the intended default behavior (no cap).
  - `env-bootstrap: Option<EnvBootstrapConfig>` (default `None`) — a new struct `{ command: String, env_file: PathBuf }` (kebab-case `env-file`, tilde-expanded via `vault::paths::deserialize_tilde_pathbuf` per the vault path-boundary rule). When present, the renderer emits `ExecStartPre=/bin/sh -c '<command> > <env_file>'` followed by `EnvironmentFile=-<env_file>`, reproducing the live unit's `manifest age decrypt ... > /run/user/1000/cortex.env` bootstrap exactly — but with the UID and secrets path living in the operator's `cortex.yml`, never in Rust source.
- Directive ORDER in the rendered unit matches the live hand-customized file exactly: `ExecStartPre` → `EnvironmentFile` → `Environment="PATH=..."` → (optional) rayon comment + `Environment="RAYON_NUM_THREADS=..."` → `ExecStart`. Verified line-for-line against `cat ~/.config/systemd/user/cortex.service` before writing the renderer, so a `cortex.yml` carrying the real host's `rayon-threads: 8` + `env-bootstrap` block reproduces the live unit byte-for-byte (modulo the `--log-level` value, which the template already threaded from `config.log_level` before this phase).
- Documented both new fields with commented-out examples in `config/templates/cortex.yml.example`, including the exact live-host shape (`manifest age decrypt ~/repos/scottidler/secrets/.secrets -f env` / `/run/user/1000/cortex.env`) so a fresh bootstrap or a re-install on this host can be reproduced by uncommenting, not re-deriving.
- Log rotation: added the `file-rotate` crate (`cargo add -p vault file-rotate`, resolved v0.8.0) at the ONE shared logging seam both borg and cortex already go through — `vault::logging::setup_logging` (`vault/src/logging.rs`). Extracted a pure `rotating_log_writer(path) -> FileRotate<AppendCount>` helper (mirrors the `render_systemd_unit` pattern above: no `env_logger::Builder::init()` call inside it, so tests can drive rotation directly without touching the process-global `log` singleton) and swapped `DualWriter`'s file half from a raw `fs::File` to `FileRotate<AppendCount>`. `FileRotate::new` opens the file in the same `create(true).append(true)` mode the old code used, so behavior is unchanged until the byte cap is crossed.
- **Chosen rotation size + retention: 50 MiB per file (`LOG_ROTATE_MAX_BYTES`), 5 rotated backups retained (`LOG_ROTATE_MAX_FILES`)** — both named consts in `vault/src/logging.rs`, no magic numbers. Total on-disk cap = 6 × 50 MiB ≈ 300 MiB, versus the pre-fix unrotated 16 GB (46 days at `--log-level debug`, ~350 MB/day). At the post-fix `--log-level info` default this leaves days of history on disk rather than hours; the exact info-level rate was not separately measured (the daemon has not run a full day at `info` yet post-fix), so 50 MiB/5 was chosen as a round, generous-but-bounded number rather than tuned against a measured info-level rate — flagged as an open question below in case the operator wants to tighten or loosen it once real info-level volume is observed.
- `FileRotate::new` re-scans the target file's existing size on open and continues counting from there (confirmed by reading `file-rotate` 0.8.0's `ensure_log_directory_exists`); on the real host, the first post-Phase-6 start against the existing 16 GB `cortex.log` will therefore rotate it out (to `.1`) on the very next write past the 50 MiB mark — a natural, code-driven equivalent of the Rollout Plan's "one-time operator step: truncate/rotate the existing 16 GB log," rather than something this phase needed to script separately.

### Deviations
- **Correct-seam extraction, not an in-place edit of `install_systemd_service`** (see Design decisions). Same effect the doc specifies (the installed unit carries the bootstrap/rayon/log-level directives); different, testable seam. Also applies to logging: the doc says "wire a rotating-file appender crate into the logger init"; the actual edit is inside `vault::logging::setup_logging` (the ONE shared init both borg and cortex call), not a cortex-only site — this is still squarely in-scope (the Non-Goals bullet excludes touching `borg.service`'s systemd unit, not the shared library logging code both binaries already depend on), and fixing the shared seam once is strictly better than duplicating rotation logic per-binary.
- The design doc's success criterion (b) as literally written ("after re-install + restart, the live unit no longer contains `--log-level debug`...") describes the FINALIZATION step (an actual `sb cortex daemon --install` + `systemctl` restart against the real host), which is explicitly out of this phase's scope per the task's constraints. Verified instead via `test_render_systemd_unit_excludes_debug_when_config_is_info` / `test_render_systemd_unit_keeps_bootstrap_and_rayon_regardless_of_log_level` — unit tests on the generated STRING, exactly as the task's own restated criteria (a)/(b)/(c) direct. The literal live re-install remains a human/finalization step (see Open questions).

### Tradeoffs
- `usize::0` as the rayon-cap "off" sentinel vs. wrapping it in `Option<usize>`: chosen because `RAYON_NUM_THREADS` is inherently a positive thread count with no meaningful zero value to a real caller, so `0` unambiguously means "unset" without needing an `Option` layer — matches the existing codebase convention of using `0` as an "auto"/"unset" sentinel for tunable counts (e.g. `EmbedConfig.workers: 0` = "let the backend pick its own default", `AutoTagConfig` uses `Option` only where a *string* value, not a count, is optional).
- Rotation mechanism: `file-rotate` (a `Write`-implementing drop-in for the existing `DualWriter` file slot) over `flexi_logger` (a full env_logger-replacement) or routing to journald. `file-rotate` was the smallest correct change — it slots into the exact spot the raw `fs::File` occupied with no change to `env_logger::Builder`, the custom timestamp format, or the dual stderr+file write path; `flexi_logger` would have meant replacing the whole logging stack (out of proportion to "bound a log file"), and journald routing would have meant giving up the DualWriter's synchronous stderr mirror that inspection verbs currently rely on (`setup_logging_stderr`'s sibling contract) — a bigger behavioral change than this phase's scope.
- 50 MiB / 5 backups over a tighter or journald-delegated cap: chosen to be generous enough that normal operator log-reading (`tail`/`grep` across recent history) is not made painful, while still being ~50x smaller than the observed pre-fix growth rate over any comparable window. See the flagged open question about tuning against measured info-level volume.

### Open questions
- **The chosen 50 MiB/5-backup rotation cap is a reasoned default, not a measured one** (no full day of `--log-level info` daemon activity has been observed post-fix at the time of this phase). Scott may want to revisit the exact numbers once a real info-level day/week of `cortex.log` growth is on disk — tightening (if 300 MiB is still more than needed) or loosening (if `info` output is noisier than expected) is a one-line const change in `vault/src/logging.rs`.
- **The actual live re-install (`sb cortex daemon --install` + `systemctl --user daemon-reload` + `systemctl --user restart cortex`) against the real `~/.config/systemd/user/cortex.service`, and populating the real host's `cortex.yml` with `daemon.rayon-threads: 8` + the real `daemon.env-bootstrap` block, is explicitly NOT done by this phase** (task constraint) and remains a human/finalization step. Until that step runs, the live unit is unchanged (still hand-drifted, still `--log-level debug`, still the 16 GB log) — this phase only makes a future `--install` SAFE to run.
- **`borg.service`'s identical drift is out of scope here** per the doc's explicit Non-Goals and the task's constraints, confirmed unchanged. The design doc's Rollout Plan flags it as a Scott-to-confirm follow-up; this phase does not touch `borg/src/lib.rs`'s `install_systemd`, and the shared `vault::logging::setup_logging` rotation fix benefits borg's log automatically (same seam, no separate borg-specific work needed for that half).

## Phase 7: Regression harness green (the structural guard)

### Design decisions
- Authored `full_action_set_periodic_sweep_fingerprint_converges_after_all_phases` (`cortex/src/daemon/tests.rs`) — a single fixture vault exercising ALL 10 default daemon actions (classify, lint, link, duplicates, intel, auto-tag, sweep, broken-links, state, quality) enabled simultaneously via `configured_actions`, asserting the second of two consecutive calls produces an EMPTY `SweepFingerprint`. Concretely: an inbox note gets promoted (classify); a badly-named file gets renamed and a title-less note gets its title filled in (lint naming/frontmatter); a note tagged with the alias `k8s` gets rewritten toward `kubernetes` (lint tags.alias); a note mentioning a glossary concept gets a wikilink inserted at first mention (link); an exact-body-hash pair gets `cortex-duplicate` fields stamped (duplicates); a low-tag-count assisted note gets `cortex-suggested-tags`/`cortex-tagged` stamped (auto-tag, `enabled: true` + a `canonical-tags` list so no Fabric/LLM call happens); one deliberately non-canonical, non-aliased tag gets stripped by sweep's own (non-empty, unlike `sweep_config_without_digest`) canonical vocabulary; `broken-links` and `state` are enabled but, by design, never feed the fingerprint (read-only lint; never touches vault notes).
- Sweep's canonical-tags.yml for this fixture is deliberately **non-empty** (`tags: {tech: [rust, programming, kubernetes]}`), unlike the pre-existing `sweep_config_without_digest` helper's empty vocabulary — `cortex/src/daemon/tests.rs`. An empty canonical set would strip every tag on every note in the vault (since none would match), masking whether sweep is doing real, targeted work versus blanket-wiping; a populated vocabulary that legitimately covers every tag this fixture uses (except the one deliberately-foreign tag) makes sweep's contribution to cycle 1 an observable, targeted write.
- Every quality-eligible (non-authored / assisted-origin) note's body in the fixture carries a wikilink from the moment it is written (`see [[langchain]] ...`), rather than relying on the `link` action to insert one during the cycle. `quality::assess_note`'s `no-outbound-links` issue is otherwise VOLATILE within a single cycle: if `quality`'s arm runs before `link`'s arm (or before this machine's real, machine-local `~/.config/sb/glossary.yml` — `link_with_notes` unconditionally consults `vault::paths::glossary()` — happens to match some other word in the body), `quality` stamps `cortex-quality-issues` based on the pre-link body, and cycle 2 (now with the link present) recomputes a DIFFERENT issue list and rewrites. This is not a lingering bug in `cortex` — it is a genuine sensitivity of `quality`'s per-cycle snapshot to what ELSE happened earlier that same cycle — so the fixture is built to be order-independent instead of asserting one particular `HashMap` iteration order.
- Placed the test immediately after `periodic_sweep_fingerprint_converges_after_phase2` in `cortex/src/daemon/tests.rs`, since that test's own doc comment explicitly deferred "the FULL action-set empty-fingerprint invariant" to Phase 7 (see its Open Questions bucket in the Phase 2 notes above).
- **Bite evidence, verified directly (not inferred):** created a throwaway `git worktree` at commit `803255e` (the Phase 0 repro commit — the last commit before Phase 1's fingerprint fix landed), pasted this exact fixture and assertion into that commit's `cortex/src/daemon/tests.rs` (swapping the shared `ENV_LOCK` for a local throwaway `Mutex`, since `testutil::ENV_LOCK` did not exist yet at that commit), and ran it. It panics: `fp2` is non-empty, containing `("lint", ["(vault-wide)", "k8s-notes.md", "no-title-note.md", "notes/thing.md"])` (the pre-Phase-1 lint arm fingerprinting `report.violations` paths — including permanently-unfixable ones — instead of `LintApplyReport.written_paths`) and `("sweep", ["notes/ai/daily/<date>.md"])` (the pre-Phase-2 intel↔sweep fight re-migrating the daily digest every cycle, since intel still stamped `tags: [digest]` at that commit). The worktree was removed after capturing the panic output; no code from that checkout was carried forward.
- **Fixed the pre-existing `XDG_CONFIG_HOME` env-var race suite-wide, not just locally in `startup/tests.rs`.** Moved the lock from a private `static ENV_LOCK` inside `cortex/src/startup/tests.rs` to a shared `pub static ENV_LOCK: Mutex<()>` in `cortex/src/testutil.rs` (already the crate's shared test-fixture module, already `#[cfg(test)]`-gated). `startup/tests.rs`'s four existing tests now import and acquire `crate::testutil::ENV_LOCK` instead of their own private one — same call sites, same behavior, just a shared lock. Every OTHER test in the crate whose code path calls `crate::startup::validate_canonical_assets()` (which resolves the REAL, process-global `XDG_CONFIG_HOME`-relative canonical-tags/tag-mapping files, independent of any config the test itself constructs) now ALSO acquires this same lock before running: `daemon::tests::{intel_sweep_two_writer_fight_no_longer_reproduces, periodic_sweep_fingerprint_converges_after_phase2, configured_actions_no_mutation_scans_vault_exactly_once, full_action_set_periodic_sweep_fingerprint_converges_after_all_phases}` (via `intel::run`/`sweep::migrate`/`sweep::scan_proposals`), `daemon::tests::scheduled_intel_write_under_applying_guard_does_not_clear_latch` (via `intel::run`, scoped to drop BEFORE the test's first `.await` per rules/rust.md's "never hold a `std::sync::Mutex` guard across `.await`"), and `sweep::tests::{test_scan_proposals_finds_non_canonical, test_scan_proposals_mapped_tags_not_proposed, migrate_excludes_paths_rewrite_note_tags_could_not_write, migrate_includes_paths_actually_rewritten}` (direct `scan_proposals`/`migrate` calls). Audited every OTHER test file in the crate for the same class of exposure (`classify/tests.rs`, `intel/tests.rs` — both call only the non-validating `run_with_notes`/`generate` seams, not `run`) and found no further instances.
- Verified determinism empirically, not just by code inspection: 25 consecutive solo runs of the new full-action-set test, 15 consecutive full `cargo test -p cortex --lib` runs (default parallel test threads), a full `cargo test --workspace --features vec`, and three consecutive `otto ci` runs — all green, zero flakes, after the `ENV_LOCK` sharing fix.

### Deviations
- None from the doc's Phase 7 text itself. The one deviation worth flagging is inherited from Phase 2's notes: Phase 2 already inverted `periodic_sweep_fingerprint_does_not_converge_pre_phase1_and_2` → `periodic_sweep_fingerprint_converges_after_phase2` (forced early by the mandated tag removal), rather than leaving that inversion for Phase 7 as the doc's plan literally scheduled. This phase does not touch that test further (it already asserts the correct, converged behavior) and instead adds the FULL action-set test the doc's Phase 7 bullet actually targets, exactly as Phase 2's own Open Questions bucket anticipated.
- The task's phrasing for the env-race fix said "add the static `ENV_LOCK`... pattern to every env-var-mutating test in that file" (i.e. `startup/tests.rs`). `startup/tests.rs` already had a private `static ENV_LOCK` on every one of its four tests (added in an earlier phase) — the actual defect was that it was *private to that file*, so nothing outside it could serialize against it. Implemented at the correct seam: promoted the lock to `pub static` in the crate's existing shared test-fixture module (`testutil.rs`) and pointed every affected test, in every affected file, at the one shared instance. Same effect (a suite-wide serialization lock for `XDG_CONFIG_HOME`-touching tests), correct seam (the crate already has exactly one shared test-utility module; inventing a second cross-file lock location would have been redundant).

### Tradeoffs
- `testutil.rs` (already `#![cfg(test)]`, already the crate's one shared test-fixture module) over a brand-new `env_lock.rs` test-support module: zero new files, and every test file that would need the lock already either imports from `testutil` or can trivially add one `use` line — a dedicated module would have been ceremony for a single `static`.
- The full-action-set fixture intentionally does NOT try to pin the exact contents of `fp1` (which action wrote what, and in what combination) — only that `fp2.is_empty()`. `daemon_config.actions` is a `HashMap`, so cycle-1 action order is not guaranteed, and several of this fixture's writes are legitimately order-insensitive in OUTCOME (converged either way) but order-sensitive in which specific action's arm performs the final write (e.g. the `k8s`-tagged note settles to `kubernetes` via lint-then-kept-by-sweep in one order, or via sweep-strips-then-lint-has-nothing-left in the other). Asserting only the order-independent invariant (fp2 empty) is deliberately the more robust pin, matching the same choice `periodic_sweep_fingerprint_converges_after_phase2` (Phase 2) and `configured_actions_rescans_once_after_classify_promotion` (Phase 5) already made for the same reason.
- Reused the already-proven `glossary_config`/concept-linking pattern from `linking/tests.rs::two_consecutive_link_passes_converge_to_zero_writes` (Phase 4) for the fixture's `link` coverage, rather than the `entities.people`/`entities.projects` pattern from `testutil::TestVault`'s config — the concepts pattern needed no target note beyond the self-link-excluded hub, and Phase 4's own test already independently proves the class of writes it produces converges, so this test only needed to prove it converges TOGETHER WITH the other nine actions, not re-prove convergence in isolation.

### Open questions
- **`link_with_notes` unconditionally reads the REAL, machine-local `~/.config/sb/glossary.yml`** (`vault::paths::glossary()`), with no config knob to redirect it to a test-controlled path the way `sweep`'s canonical-tags/tag-mapping paths are already redirectable via `SweepConfig`. This is a pre-existing production behavior (not introduced by this phase) that this phase's fixture had to design AROUND (see the "pre-baked outbound wikilink" design decision above) rather than being able to fully isolate from. It did not block this phase (the fixture is robust to whatever the real glossary contains), but it means `link_with_notes`-exercising tests in this crate are not fully hermetic with respect to the operator's real vault config. Recommend a follow-up: thread the glossary path through `LinkingConfig` (or a `link_with_notes`-level parameter) the same way `SweepConfig` already threads its three asset paths, so tests (and any future non-default-vault invocation) can fully isolate it.
- The `sccache` build-cache daemon on this development machine intermittently failed with `sccache: error: Operation not permitted (os error 1)` during this phase's verification (both inside and outside the harness's sandbox, and both via direct `cargo`/`otto` invocation) — traced to the local disk cache having filled to its configured 20 GiB cap, and recurring afterward under rapid repeated invocation even after a cache purge and server restart. This is a pre-existing, machine-local build-tooling issue, unrelated to this phase's code (every actual test run that got past the `sccache` client crash passed 100% of the time — 25+15+15 consecutive clean runs). Worked around for verification by running with `RUSTC_WRAPPER=""`/`CARGO_BUILD_RUSTC_WRAPPER=""` when the flake was live; the final `otto ci` and `cargo test` confirmations in this report are genuinely green. Flagging so Scott can decide whether to raise `sccache`'s cache cap, prune it, or investigate the crash further — out of scope for this repo's Phase 7.

## Phase 8: Fix-forward — classify writes idempotent + fingerprinted (implementation-audit findings #1, #2)

### Design decisions
- **`mark_needs_review` made idempotent and now returns `bool` (wrote / did-not-write)** — `cortex/src/classify.rs::mark_needs_review` — two guards, both load-bearing. (1) Semantic guard: if the note already carries `cortex-needs-review: true` in its scanned frontmatter, skip entirely and return `false`. No-signal/low-confidence inbox notes are never marked `cortex-classified`, so `filter_inbox_notes` re-selects them every cycle; this is the primary fix. (2) Byte guard: even on the first mark, only `write_atomic` when `new_content != content`, because `insert_frontmatter_fields` does remove-then-reappend with no value comparison and can re-emit byte-identical content.

### Deviations
- **Signature shape: `(Report, Vec<String>)` rather than a named `ClassifyApplyReport` struct.** The doc/task allowed either; the four lint appliers already return bare `Vec<String>` of written paths, so the tuple matches the closest existing seam and avoids a one-field wrapper. Same effect, correct seam.
- **Snapshot asserts on `(bytes, mtime)` scoped to `*.md`, not literally "every vault file."** The `state` action rewrites its own `.cortex/manifest.yml` cache (a timestamped, non-note artifact) every cycle by design; that is not a vault note and not part of the "writes zero note files" invariant. Scoping to `*.md` matches the design doc's Acceptance Criterion wording ("writes zero note files") exactly. Documented in the helper's doc comment.

### Tradeoffs
- **mtime comparison (not just byte comparison) is the load-bearing signal.** The pre-Phase-8 `mark_needs_review` rewrite is BYTE-IDENTICAL (remove-then-reappend of the last frontmatter line), so a bytes-only snapshot would NOT bite. The design doc's whole thesis (defect 2) is that a byte-identical write still fires the daemon watcher via the mtime bump, so mtime is the correct thing to assert. Kept the byte assertion too (defense against a genuinely non-idempotent write) but the bite lives in the mtime check.
- **Only report/fingerprint writes that actually changed bytes**, at the cost of no longer emitting a `Report` violation for a catch-up/reclassify that produced identical bytes. That case does not occur in practice (catch-up writes a `domain` that was absent), and honesty of `report.applied` (writes ⊇ report) is worth more than a phantom info line.

### Zero-writes bite evidence (finding #2)
- Confirmed the strengthened test BITES on pre-Phase-8 classify behavior via a scoped revert: temporarily reverted `mark_needs_review` to the pre-Phase-8 form (write unconditionally, no guards) AND returned `false` so the write stays invisible to the fingerprint — i.e. exactly the audited defect (write happens, fingerprint stays empty). Result: `cargo test -p cortex --lib full_action_set_periodic_sweep_fingerprint_converges_after_all_phases` FAILED at the mtime assertion:
  `assertion left == right failed: cycle 2 TOUCHED <tmp>/inbox/mystery.md (mtime moved even if bytes are identical) ... a write happened without a fingerprint entry` — `left.tv_nsec=76333496`, `right.tv_nsec=151335341` (same `tv_sec`, only the nanosecond mtime moved, proving the write was byte-identical).
- The byte assertion PASSED and `fp2.is_empty()` would have PASSED in that reverted state — precisely why the old `fp2.is_empty()`-only guard could not catch the defect and the mtime snapshot can. Restored the Phase 8 `mark_needs_review`; the test then passes deterministically (3 consecutive solo runs + full 323-test `cargo test -p cortex --lib` all green).
