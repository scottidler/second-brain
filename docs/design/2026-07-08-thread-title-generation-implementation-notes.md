# Implementation Notes: Thread Title Generation

Design doc: `docs/design/2026-07-08-thread-title-generation.md`

## Phase 1: `thread::title_for_thread` + `title_snippet` + `platform_label`

### Design decisions
- `platform_label` matches `"x"|"reddit"|"hn"` explicitly and falls through to a defensive `capitalize()` for any other identifier — `borg/src/thread.rs::platform_label` — the doc calls this out as defensive-only since `ThreadPayload::platform` is currently always one of the three known values, but a stray fourth string still produces a readable label instead of an empty/garbage one.
- `title_snippet`'s whitespace collapse and word-boundary truncation are both hand-rolled on `chars()` (never `&str` byte-slicing) — `borg/src/thread.rs::collapse_whitespace`, `truncate_at_word_boundary` — per the repo's UTF-8/char-boundary footgun rule; a byte-index truncation would panic the moment a multibyte character (e.g. an em dash or emoji in a tldr) straddled the 80-char cut point.
- `title_for_thread` decides its 4-way priority order via a single `match (author, snippet)` tuple rather than nested `if`/`else` — `borg/src/thread.rs::title_for_thread` — makes all four shapes from the API Design table exhaustively visible in one place and unreachable-by-construction for a 5th case.
- An `Some("")` author is treated as absent (`author.filter(|s| !s.is_empty())`) so an upstream extractor returning an empty string degrades to the platform-only shapes instead of emitting `" on X"` — not explicitly required by the doc's 4 priority-order shapes, but implied by shape 3/4 existing at all (there would be no way to reach them if empty-string authors weren't filtered).

### Deviations
- None. Implemented exactly per the API Design section (function signatures, doc comments, and priority-order shapes match verbatim), including the explicit instruction to use a local `split_whitespace().join(" ")` helper instead of `hygiene::normalize_text_input`.

### Tradeoffs
- Pure formatters/helpers (`platform_label`, `capitalize`, `collapse_whitespace`, `truncate_at_word_boundary`, `title_snippet`, `title_for_thread`) carry no `log::debug!` entry/exit logging, unlike the `github::extract_repo_slugs` sibling this module mirrors in shape — chosen per the phase instructions' explicit carve-out for trivial/pure formatters, and because these functions have no I/O, no failure mode, and are fully covered by the doc's own success-criteria unit tests; a caller that wants visibility into the *result* logs it once at the `pipeline.rs` seam (Phase 2), not at every pure helper call.
- `title_snippet`'s summary-fallback truncation caps at a `SNIPPET_MAX_CHARS = 80` module constant rather than inlining the literal, per the repo's no-magic-numbers convention, even though the doc's prose only says "~80 chars" — a named constant makes the exact boundary testable and grep-able rather than an implicit magic number buried in a call site.

### Open questions
- None.

## Phase 2: Wire the override at the thread distill seam

### Design decisions
- Extracted the seam into two pure, unit-testable functions — `borg/src/thread.rs::thread_title(&Distilled, trace_id)` and `borg/src/thread.rs::resolve_title(is_thread, article_title, &Distilled, trace_id)` — instead of inlining the doc's `let title = if is_thread { … }` block into `pipeline.rs`. The pipeline seam is a single call: `let title = crate::thread::resolve_title(is_thread, title, &distilled, trace_id);` (`borg/src/pipeline.rs`, right after the Gate-2 call, before the tuple return). This is the phase instructions' sanctioned "extract the minimal seam into a testable helper" — the seam logic is now covered by in-process synthetic-`Distilled` tests without a live pipeline run.
- The fallback branch keys on `distilled.meta.validation.fallback_reason.is_some()`, NOT on `distilled.kind_specific.is_none()` — `borg/src/thread.rs::thread_title` — because `fallback_reason` is the typed, authoritative "degraded distillation" signal. It (a) never reads `summary` on the fallback path, so a `fallback_distilled` `"[reason]\n\n<snippet>"` string can never leak into a title, and (b) still recovers the platform from the payload that `attach_platform` left present, so an x-platform fallback titles as `"X thread"` rather than `"Thread thread"`.
- `thread_title` carries the function-level `log::debug!` entry line (payload presence, platform, author presence, tldr presence, fallback flag) and a `log::warn!` on the generic-title path, per the logging rule — the degraded case is visible, not silent.

### Deviations
- **The doc's core premise about the fallback shape is factually wrong, and the literal wiring in its code block would leak `[fabric-timeout]` into a title.** The doc (Proposed Solution, Architecture diagram, Resolved Decisions) asserts that a distiller fallback leaves `distilled.kind_specific = None`, and its wiring detects fallbacks by matching `kind_specific`. In the actual code, `ThreadDistiller::distill` (`distillers/src/thread.rs:127`) calls `attach_platform` UNCONDITIONALLY on the value returned from `distill_short`/`distill_long` — including their `fallback_distilled` returns. So a fabric-timeout / yaml-parse-error / missing-summary fallback exits with `kind_specific = Some(Thread { author: None, post_count: 0, platform })` and a `"[reason]\n\n<snippet>"` summary. Under the doc's literal wiring, `thread_payload` would be `Some(...)`, the builder would read that summary as snippet material, and the title would become `X thread: "[fabric-timeout] …"` — the exact leak the design exists to prevent. Same effect, correct seam: I detect fallbacks via the typed `fallback_reason` signal instead. The doc's stated behavior and all acceptance criteria are satisfied; only the mechanism differs. (The doc's "three `fallback_distilled` call sites don't call `attach_platform`" observation is true but irrelevant — `attach_platform` runs later, in the shared `distill` exit, over whatever those sites returned.)
- Success-criterion (b) is internally contradictory as written (it constructs `kind_specific: None` yet expects the platform-specific `"X thread"` — with no payload there is no platform, so the honest output would be `"Thread thread"`). The contradiction is a downstream symptom of the wrong-premise above. I tested (b) against the *realistic* fabric-timeout shape a thread actually carries at the seam (`kind_specific = Some(Thread{platform:"x", author:None})`, `fallback_reason = Some("fabric-timeout")`, summary `"[fabric-timeout]…"` from the real `distillers::fallback_distilled`), which produces `"X thread"`, non-numeric, with no leaked `[fabric-timeout]` — satisfying the criterion's actual intent. I also added a separate test for the ONE real `kind_specific: None` path (the outer `dispatch-error` fallback in `distill_for_publish_thread`), which correctly yields `"Thread thread"`.

### Tradeoffs
- Keying the fallback branch on `fallback_reason.is_some()` sends *every* degraded thread distillation to the generic `"<Platform> thread"` title, including `reduce-selection-failed` / `partial-chunk-failure`, which carry a real (non-`[reason]`) summary and sometimes a real author. Those could in principle still build an `"<author> on X"` title. I chose the generic floor for all `fallback_reason` cases anyway — it exactly matches the doc's stated behavior ("builder-`None` goes straight to a generic platform label"), is strictly leak-safe (never reads a summary on any fallback), and keeps the seam a single typed boolean rather than a per-reason allowlist that would drift as new fallback reasons are added. The alternative (per-reason handling) is unrequested scope for a 2-live-note bug.

### Open questions
- None. Confirmed the phase's prerequisite directly: on the SUCCESS path, `ThreadDistiller::distill` always calls `attach_platform(bounded, infer_platform(source_url), …)`, and `infer_platform` returns `"x"` / `"reddit"` / `"hn"` for the three thread hosts. So `distilled.kind_specific` is populated (`Some(Thread{platform})`) for all three platforms on success — no pre-existing gap to flag. The only `kind_specific: None` at the seam is the outer `dispatch-error` fallback, which the generic-label path handles as `"Thread thread"`.

## Phase 3: Regression test

### Design decisions
- Added the regression pair directly to `borg/src/thread/tests.rs` (not a new `tests/` integration file) — `break_the_code_extract_article_title_degenerates_to_numeric_id` and `resolve_title_override_prevents_the_numeric_id_from_becoming_the_title` — reusing the module's existing `is_purely_numeric` helper and `thread_distilled` fixture builder from the Phase 2 tests rather than duplicating them.
- The fixture (`BROWSER_UA_THREAD_BODY`, `THREAD_URL`, `THREAD_NUMERIC_ID`) is a header-less markdown body for `https://x.com/tom_doerr/status/2067473155988332909` — no `Title:` line, no `# ` heading, author handle inline as a markdown link — modeling exactly what `BrowserUaFetcher` serves when the Jina rung fails (design doc Background, `borg/src/jina.rs:18-28`).
- Reached `extract_article_title` (`borg/src/pipeline/handlers.rs`) from `thread::tests` via `crate::pipeline::extract_article_title` — the function is `pub(crate)` inside the private `pipeline::handlers` submodule, and `pipeline.rs` re-exports it crate-wide with `pub(crate) use handlers::*;` (`borg/src/pipeline.rs:37`). This is the real production function, not a copy or a re-implementation of Strategy 3's logic.
- The break-the-code test (`break_the_code_extract_article_title_degenerates_to_numeric_id`) calls `extract_article_title` directly on the fixture and asserts it returns the bare numeric ID — this is the pre-fix code path unmodified (threads never stopped calling `extract_article_title`; Phase 2 stopped *trusting* its output for threads). No test-only "revert the override" scaffolding was needed: calling the article-title function directly on the fixture already reproduces the exact pre-fix behavior a plain `title = scraped_title` binding would have produced.
- The fix test (`resolve_title_override_prevents_the_numeric_id_from_becoming_the_title`) re-asserts the same precondition (`extract_article_title` still degenerates), then feeds that same numeric string into the real `resolve_title` seam alongside a synthetic success-path `Distilled`, and asserts the final title is non-numeric and matches the built thread title. This proves both halves the doc's Phase 3 section asks for on one fixture: the bug reproduces at the scrape step, and the override — not a numeric-ID guard — is what prevents it from reaching `title`.

### Deviations
- The design doc's Phase 3 bullet describes the negative case as "with the Phase 2 override removed" (implying a code revert). No code was reverted or feature-flagged to prove this — the SAME effect is achieved by calling `extract_article_title` directly (the function the pre-fix `title` binding used verbatim) instead of routing through `resolve_title`. This is the exact recommendation the invoking instructions gave as the sanctioned approach for this seam, and it is strictly more faithful than a temporary code revert would be: the "positive" and "negative" tests exercise the identical real functions the pipeline calls today (`extract_article_title` is still called for every non-thread URL; `resolve_title` is what routes threads away from trusting its output), so there is no risk of the two tests drifting out of sync with production code the way a hand-reverted copy could.

### Tradeoffs
- Kept the regression pair in `thread/tests.rs` rather than `pipeline/tests.rs`, even though the break-the-code half calls a `pipeline` function. The seam under test (`resolve_title`) lives in `thread.rs`, both fixtures and helpers it needs (`thread_distilled`, `is_purely_numeric`) already live in `thread/tests.rs` from Phase 2, and `crate::pipeline::extract_article_title`'s `pub(crate)` re-export makes it reachable from there with no visibility changes. Splitting the pair across two files would separate the "reproduce" and "fix" halves of one regression story for no benefit.

### Open questions
- None.
