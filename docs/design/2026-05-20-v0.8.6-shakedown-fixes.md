# Design Document: v0.8.6 Shakedown Follow-up Fixes

**Author:** Scott Idler
**Date:** 2026-05-20
**Status:** Implemented
**Review Passes Completed:** 4/4

## Summary

Resolve the four defects surfaced by the v0.8.6 shakedown (docs/shakedown-sb-v0.8.6.md): verbose-mode Location restoration (D1), missing-path exit code for `oracle call note_read` (D2), `sb doctor` exit-code contract (D3), and the `results` rename scope miss for `ingest_history` / `inbox_status` (D4). All four are small, but two carry contract decisions (D3, D4 are consumer-visible) that should be recorded before the patch lands.

## Problem Statement

### Background

v0.8.6 shipped four cleanup phases from the prior design pass: config unification under `~/.config/sb/`, oracle response-key unification on `results`, `--format`/`--scan` enum validation at parse time, and `daemon --status` parity between borg and cortex. The shakedown (45 commands exercised) confirmed all four behaviors land correctly, but flagged four follow-ups.

The shakedown report's diagnoses are largely accurate, with one important exception: D2's "the is_error -> exit code translation is missing" claim does not match the code. `sb/src/cli/oracle.rs:113-121` already exits 1 when `result.is_error == Some(true)`. The actual bug is in `oracle::server::note_read` (`oracle/src/server.rs:320`), which returns `CallToolResult::success(...)` with text content "Note not found: ..." instead of marking the response as an error. The same pattern exists in `duplicate_groups` for a missing `group_id` (`oracle/src/server.rs:793`).

### Problem

Four defects of varying severity:

- **D1 (bug, Phase 3 spec drift):** `sb -v` does not restore the `Location:` block. The hand-rolled `EyreHandler::debug` impl in `sb/src/error.rs:46` delegates to `fmt::Debug::fmt(error, f)` on the inner `dyn Error + 'static`, but eyre's `Location` is captured on the `Report` wrapper, not the inner error. Verbose mode changes the chain rendering but never prints Location.
- **D2 (bug, CLI exit-code contract):** `sb oracle call note_read --json '{"path":"notes/missing.md"}'` exits 0. The original draft proposed making `note_read` return `is_error: true` on missing paths, but Architect review (2026-05-20) correctly flagged this as protocol abuse: MCP's `isError` is reserved for tool *execution* failures (invalid args, internal panics), not domain-level "no row matched." LLM agents treat `isError: true` as a hard tool crash, which would degrade their behavior on a perfectly valid "note doesn't exist" outcome. The fix needs to live at the CLI wrapper boundary, not the MCP server.
- **D3 (contract clarification):** `sb doctor` exits 0 when `Issues detected. See suggested fixes above.` is printed. Comparable tools (`rustup doctor`, `brew doctor`) also exit 0 on warnings. The contract needs to be confirmed in code so script consumers know what to expect.
- **D4 (inconsistency, Phase 2 scope miss):** `ingest_history` returns `{count, entries}` and `inbox_status` returns `{classified, inbox_count, needs_review, notes, review_candidates}`. Both are list-of-things shapes that should follow the canonical `{count, results}` key already used by `tag_search`, `source_browse`, `creator_browse`, `list_notes`, `find_similar`, `recent_activity`, `quality_report`. The original Phase 2 design classified them as "per-tool object, unchanged"; this was a miscall.

### Goals

- Restore verbose-mode behavior to match the Phase 3 spec (Location visible when `-v` or `RUST_BACKTRACE=1`).
- Establish an explicit semantic boundary for oracle tool responses: domain "not found" is a structured success result, MCP `isError` is reserved for protocol-level failures (invalid args, internal panics). Implement that boundary at the five affected sites.
- Make `sb oracle call` exit non-zero on both kinds of failures: protocol-level `is_error == true` (already wired) AND domain-level `found == false` (new wrapper-side translation).
- Decide and codify the `sb doctor` exit-code contract; document it in `--help`.
- Extend the `results` rename to `ingest_history` and `inbox_status` so all list-shaped oracle tools share the same key.

### Non-Goals

- Reworking the eyre error machinery beyond what is needed to restore Location in verbose mode. (No move to `color-eyre` unless the simpler fix is rejected.)
- Auditing oracle tools outside `oracle/src/server.rs` for similar response-shape inconsistencies. Inside this file the sweep is complete (five sites; see D2 below); other call sites are not in scope.
- Documenting the full output schema of every oracle tool in its `#[tool(description = ...)]` string. The Architect review surfaced this as a separate broader-scope concern; it deserves its own design pass once the "tool description includes output schema" convention is decided. Out of scope here.
- Changing `find_links` (returns `{outbound, inbound, note, orphan}`) or `duplicate_groups` (returns `{count, groups}`). The shakedown confirmed both shapes are justifiably distinct from a flat `results` list.
- Reducing boot-time log noise (Observation O3) or regenerating systemd units (Observation O1). Out of scope; tracked separately.

## Proposed Solution

### Overview

Four independent, small patches landed in a single release cut (v0.8.7). No phase gating, no soak time; each fix has a test, all fixes ship together. Two contract decisions are made up front: doctor uses the `warnings != failure` model (matching `rustup`/`brew`), and the `results` rename extends to `ingest_history` + `inbox_status` as the shakedown recommends.

### D1: Restore `Location:` in verbose mode

`sb/src/error.rs` currently captures the `verbose` flag at hook install and switches between a compact custom format and `fmt::Debug::fmt(error, f)` on the inner error. The latter does not include the eyre Report's Location for a fundamental reason: eyre captures Location not at hook-construction time and not on the inner error, but via a separate `EyreHandler::track_caller(...)` callback that eyre invokes on the handler instance AFTER the hook closure returns it (`eyre-0.6.12/src/lib.rs:605`). Our custom `Handler` does not override `track_caller`, so it inherits the default no-op impl from the trait and silently drops the Location. Calling `eyre::DefaultHandler::default_with(error)` inside our `debug` is not a workaround - it returns a fresh handler with `location: None` for the same reason.

**Fix:** capture Location on our own `Handler` by overriding `track_caller`, and print it in the verbose branch.

```rust
struct Handler {
    verbose: bool,
    location: Option<&'static std::panic::Location<'static>>,
}

impl EyreHandler for Handler {
    fn track_caller(&mut self, location: &'static std::panic::Location<'static>) {
        self.location = Some(location);
    }

    fn debug(&self, error: &(dyn Error + 'static), f: &mut fmt::Formatter<'_>) -> fmt::Result {
        // Compact chain stays the same.
        write!(f, "{error}")?;
        let mut source = error.source();
        let mut depth = 0;
        while let Some(cause) = source {
            depth += 1;
            if depth == 1 {
                write!(f, "\n\nCaused by:")?;
            }
            write!(f, "\n    {depth}: {cause}")?;
            source = cause.source();
        }
        // Verbose adds Location below the chain.
        if self.show_verbose() {
            if let Some(location) = self.location {
                write!(f, "\n\nLocation:\n    {location}")?;
            }
        }
        Ok(())
    }
}
```

The hook closure becomes `move |_| Box::new(Handler { verbose, location: None })`. Eyre will set `location` on the boxed handler via `track_caller` between hook return and first `debug` call. No new dependency. No fallback to `color-eyre` is needed; the in-tree fix is one field + one trait-method override.

### D2: Domain-level "not found" vs. protocol-level error

**Architectural rule (codified by this design):**

- **Protocol-level error** (`CallToolResult::error`, sets `is_error: Some(true)`): the tool *failed to execute*. Invalid arguments, internal panic, transport error, schema mismatch. MCP agents treat this as a tool crash and should not retry naively.
- **Domain-level "not found"** (`CallToolResult::success` with a structured payload): the tool *executed successfully* and the answer is "no such item." MCP agents treat this as a valid negative answer and can branch on it.

Applying this rule to the five sites:

| Line | Tool | Branch | Category | Fix |
|---|---|---|---|---|
| 320 | `note_read` | path not in DB | Domain not-found | Return `success` with `{"found": false, "kind": "note", "path": "...", "message": "Note not found"}` |
| 525 | `find_similar` | path not in DB | Domain not-found | Same JSON shape as above |
| 531 | `find_similar` | both `content` and `path` empty | Protocol error (invalid args) | `CallToolResult::error(...)` |
| 601 | `find_links` | path not in DB | Domain not-found | Same JSON shape as above |
| 793 | `duplicate_groups` | group_id not in DB | Domain not-found | `success` with `{"found": false, "kind": "duplicate_group", "group_id": N, "message": "..."}` |

Only the line-531 site uses `is_error: true`. The four not-found sites switch from `Content::text(...)` to `Content::json(json!({"found": false, ...}))` so consumers (agents and the CLI wrapper) get a structured signal instead of having to string-match on prose.

**CLI wrapper translation** (`sb/src/cli/oracle.rs:113-121`): extend `print_call_result` to also exit 1 when the parsed JSON has a top-level `"found": false`. The existing `is_error == Some(true)` branch stays. The two checks compose:

```rust
fn print_call_result(result: &rmcp::model::CallToolResult) -> Result<()> {
    if result.is_error == Some(true) {
        for content in &result.content {
            if let Some(text) = content.as_text() {
                eprintln!("{}", text.text);
            }
        }
        std::process::exit(1);
    }

    let mut not_found = false;
    for content in &result.content {
        if let Some(text) = content.as_text() {
            if let Ok(parsed) = serde_json::from_str::<serde_json::Value>(&text.text) {
                if parsed.get("found").and_then(|v| v.as_bool()) == Some(false) {
                    not_found = true;
                }
                println!("{}", serde_json::to_string_pretty(&parsed)?);
            } else {
                println!("{}", text.text);
            }
        }
    }
    if not_found {
        std::process::exit(1);
    }
    Ok(())
}
```

This keeps MCP semantics honest (agents see a clean negative response, not a tool crash), and gives shell consumers the exit code they need.

### D3: `sb doctor` exit-code contract

**Decision:** `sb doctor` exits 0 when only `Warn` or `Info` findings are present, and exits 1 only when at least one `Error` severity finding is present. This matches `rustup doctor` and `brew doctor` and the established convention that warnings are advisory, not blocking.

`sb/src/cli/doctor.rs` already collects findings with severity. The `Severity` enum at `sb/src/cli/checks.rs:6` derives `PartialOrd` and `Ord` with `Ok < Info < Warn < Error`, so the check is a max-severity computation. Replace the current `had_issue` boolean (triggers on `>= Warn`) with an `error_count` that increments on `Severity::Error`. Return `Ok(())` when `error_count == 0`; otherwise return `Err(eyre!("doctor found {error_count} error-severity issue(s); see output above"))`. `main.rs` (`sb/src/main.rs:22`) propagates that `Err` to the binary exit code via the standard `Result` `Termination` impl, giving exit 1.

Keep the existing "Issues detected. See suggested fixes above." print for warn-or-worse - it's a user-facing summary, not an exit-code trigger. Update `sb doctor --help` to state the contract: "Exits 1 only when an Error-severity issue is detected; warnings exit 0 (matches `rustup doctor` / `brew doctor`)."

### D4: Rename `entries` -> `results` (ingest_history), `notes` -> `results` (inbox_status)

Clean rename, same pattern as the Phase 2 unification:

- `oracle/src/server.rs:425-428` (ingest_history): change the JSON key `"entries"` to `"results"`.
- `oracle/src/server.rs:746-752` (inbox_status): change the JSON key `"notes"` to `"results"`. Leave `inbox_count`, `needs_review`, `classified`, `review_candidates` unchanged - they are not "the list" and have semantic meaning of their own. `review_candidates` is a secondary list; if it ever needs canonical-keying, it gets its own response-tool, but that's out of scope.

Update the pipeline recipe at the bottom of the shakedown report (line 207, the DLQ-pending-traces example) to use `.results[0]` instead of `.entries[0]`.

### Data Model

JSON shape changes in oracle responses:

| Tool / branch | Before | After |
|---|---|---|
| `ingest_history` (D4) | `{count, entries}` | `{count, results}` |
| `inbox_status` (D4) | `{inbox_count, needs_review, classified, notes, review_candidates}` | `{inbox_count, needs_review, classified, results, review_candidates}` |
| `note_read` not-found (D2) | `Content::text("Note not found: ...")` | `Content::json({"found": false, "kind": "note", "path": ..., "message": "Note not found"})` |
| `find_similar` not-found (D2) | `Content::text("Note not found: ...")` | same shape as `note_read` not-found |
| `find_similar` missing-args (D2) | `Content::text("Provide either 'content' or 'path' ...")` (success) | `CallToolResult::error(Content::text(...))` (is_error: true) |
| `find_links` not-found (D2) | `Content::text("Note not found: ...")` | same shape as `note_read` not-found |
| `duplicate_groups` not-found (D2) | `Content::text("Duplicate group not found: ...")` | `Content::json({"found": false, "kind": "duplicate_group", "group_id": ..., "message": ...})` |

The `found` key is the new convention: `found: false` at the top level of an oracle JSON response means "tool ran fine; the requested item doesn't exist." `find_links`'s `orphan` field is unaffected (orphan describes a found note with no link neighbors, not a missing note).

### API Design

No API surface changes other than the JSON-key renames listed above. `note_read` and `duplicate_groups` keep their tool signatures; only the `is_error` field on the response result flips for not-found inputs.

## Alternatives Considered

### Alternative 0: Force `is_error: true` on domain not-found (original D2 draft)
- **Description:** Swap `CallToolResult::success` for `CallToolResult::error` at all five oracle sites that currently return "not found" text, making the CLI exit non-zero via the existing wrapper translation.
- **Pros:** One-line change per site. No wrapper logic needed.
- **Cons:** Architect review (2026-05-20) correctly flagged this as protocol abuse. MCP's `isError` is reserved for tool *execution* failures. LLM agents treat `isError: true` as a hard tool crash and may abandon a workflow or hallucinate recovery instead of branching on a valid "not found" outcome. Solves a CLI convenience problem by breaking semantic accuracy for the protocol's primary consumer.
- **Why not chosen:** The wrapper-side translation (the proposed solution) preserves MCP semantics for agents while still giving shell consumers exit-code gating. The cost is small (one extra check in `print_call_result`) and the benefit is correct separation of concerns.

### Alternative 1: Adopt `color-eyre` wholesale for the verbose path
- **Description:** Replace the hand-rolled `EyreHandler` with `color-eyre`'s hook for verbose mode and keep a compact filter for non-verbose.
- **Pros:** Battle-tested; gives Location, source chain, optional backtrace, and color formatting for free.
- **Cons:** Adds a dependency for what is a two-line fix (one field + one trait method override). Color codes in verbose output may not be desired by default. Maintaining two hooks (one for compact, one for verbose) is more code than the in-tree fix.
- **Why not chosen:** The in-tree fix is mechanical and confirmed correct against `eyre-0.6.12` source. No reason to take a dependency.

### Alternative 2: `sb doctor` exits 1 on any warning
- **Description:** Treat warn-level findings as failures.
- **Pros:** Script consumers gate on exit code without parsing stdout.
- **Cons:** Diverges from `rustup doctor` / `brew doctor` convention; makes the command noisy in healthy environments where one warn is normal (e.g. pending DLQ rows from a vault that has organic backlog). Penalizes the most common steady-state.
- **Why not chosen:** Convention parity matters more than convenience for a single use case. Scripts that need warn-gating can grep the output or wait for JSON output to be added in a separate ticket.

### Alternative 3: Restructure `inbox_status` more aggressively
- **Description:** Split `inbox_status` into two tools: `inbox_list` and `review_candidates_list`, each returning `{count, results}`.
- **Pros:** Each tool has a single canonical list; uniform shape across all oracle tools.
- **Cons:** Doubles the tool surface for a low-value gain; breaks an existing tool signature (consumers calling `inbox_status` would have to switch). The two lists today share state (limit, detail level) and were grouped together intentionally to give a single snapshot of "inbox health."
- **Why not chosen:** The shakedown's recommendation - rename the primary list to `results`, leave secondary keys intact - is the minimum disruption that achieves consistency without breaking the single-snapshot contract.

### Alternative 4: Defer D3 (doctor exit code) entirely
- **Description:** Document the current behavior (always exit 0) and call it done.
- **Pros:** No code change.
- **Cons:** Leaves the contract unwritten. Scripts have to discover behavior by trial.
- **Why not chosen:** Writing the contract is cheap, and the change to return `Err` on Error-severity findings is a one-line accumulator swap. Worth doing once.

## Technical Considerations

### Dependencies

- D1 may add `color-eyre` if the in-tree fix is not reachable. All other phases use existing dependencies.

### Performance

- No performance impact. All four fixes are O(1) format/JSON changes on rare paths.

### Security

- No security implications. The verbose-mode change still gates Location on an explicit user flag (`-v`) or env var (`RUST_BACKTRACE`); the default remains the compact, no-Location output.

### Testing Strategy

Each phase carries its own targeted test. Together:

- D1: unit test on the EyreHandler's verbose vs compact branches.
- D2: unit tests on the two server methods asserting `is_error: Some(true)` for not-found cases.
- D3: unit tests on `doctor::run` with synthetic findings.
- D4: smoke tests on `ingest_history` and `inbox_status` asserting the `results` key.
- The follow-up mini-shakedown (Phase 5) is the integration backstop: run the same commands that failed in v0.8.6's shakedown and confirm new behavior.

### Rollout Plan

Single release v0.8.7 cut from main. No feature flags, no staged rollout. `otto deploy` reinstalls `~/.cargo/bin/sb`; no daemon restart needed for any of these fixes (none touch the borg/cortex/oracle daemon paths). MCP consumers (Claude Desktop, others) pick up the new oracle behavior on next `sb oracle serve` invocation; no restart since oracle is launched on demand per `.mcp.json`.

## Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| `eyre`'s `track-caller` feature disabled in workspace | Very Low | Low | Verified default-on against `eyre-0.6.12`; Phase 1 plan re-confirms via `cargo tree -e features`. |
| Renaming `entries`/`notes` breaks an undocumented in-tree consumer | Low | Med | Grep the tree for both keys before commit; the codebase is small enough that a full audit is cheap. Update the recipe in shakedown doc. |
| External MCP consumer relies on `entries` or `notes` keys | Low | Low | No known external consumers parse these specific keys today; oracle is single-user. If broken, easy to revert. |
| D3 contract change surprises a script that gated on exit 0 | Very Low | Low | The only behavioral change is exit 1 on Error-severity findings, which were already printed and visible. Any script that hit this case was silently swallowing a problem. |
