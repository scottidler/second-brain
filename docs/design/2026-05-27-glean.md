# Design Document: glean

**Author:** Scott Idler (drafted by Claude)
**Date:** 2026-05-27
**Status:** Implemented
**Review Passes Completed:** 5/5

## Summary

glean is an intermediate-stage tool that mines Scott's own Claude Code session transcripts to distill the technique he uses when guiding LLMs. Tier 1 normalizes JSONL transcripts into per-session records with repo/design-doc/theme metadata. Tier 2 clusters those records into work-items and emits one four-part knowledge chunk per work-item (task / context / interaction / review, per Nate B Jones's apprenticeship framing) to a persistent vault location. A separate non-destructive dreaming pass consolidates the corpus (per Anthropic's agents-that-remember layering). The consumer is Scott reading his own technique back; the eventual public-facing tool is out of scope for this iteration. The validation gate is a recognition test on one real distilled chunk before any pipeline plumbing ships, which is the gate the prior facet v1/v2 effort skipped.

## Problem Statement

### Background

Two prior efforts under the name `facet` attempted to mine Scott's session corpus. v1 (`failed-facet-v1` branch) produced one-line "judgment moments" rolled up into six static mode-bucketed spectra. The output was incorrect on inspection. v2 (also on `failed-facet-v1`, never validated against the real corpus) attempted to rescue v1 by extending the schema (multi-turn gems with four-part anatomy, emergent narrative spectra, an Anthropic-style dreaming layer) while preserving v1's pipeline and migration story. The v2 effort shipped seven phases of code, never produced validated output against the real corpus, and was nuked from main on 2026-05-27 with main rewound to the pre-facet commit `f1c77d2`.

The two source notes that informed v2 remain valid inputs for a fresh design:

1. **`shopify-ceo-reveals-their-secret-ai-developer.md`** (Nate B Jones). Names four parts of AI work to make visible to colleagues: task, context, interaction, review. The talk's actual thesis is *public* AI work as a substrate for organizational learning; the four-parts framing is an instrument inside that program.
2. **`agents-that-remember.md`** (Kevin / Anthropic). Names three composable layers: ephemeral sessions, persistent memory stores (file-system-like, agent-readable via bash/grep), and dreaming (async, non-destructive consolidation that clones and improves the store).

Both source talks describe systems whose consumer is someone other than the author: a junior engineer reading a Slack channel, or a future agent reading a memory store. The intermediate-stage tool described here has a different consumer (Scott reading his own technique back), and the design honors that distinction rather than papering over it with imported vocabulary.

### Problem

Scott has months of Claude Code session JSONL transcripts that contain his actual LLM-collaboration technique. The technique is not in any single session in retrievable form; it is distributed across sessions, often centered around design docs that span days. There is no tool that surfaces "what Scott does when working with an LLM" as a readable artifact he can recognize, refine, and eventually publish.

The prior facet effort tried to solve this and failed in two ways:

1. **Wrong unit of capture and output.** v1's one-line "judgment moments" (paraphrased into a structured row) were too shallow to convey technique. v1's mode-bucketed rollups (six static spectra files: frame / iterate / reject / push-for / sequence / name-the-failure) could not tell a story across work that spans days and design docs.
2. **Evolutionary morph instead of redesign.** v2 inherited v1's whole shape: cluster turns within a session into "work-items," extract structured rows per work-item, roll those rows up into per-mode spectrum notes. v2 enriched the row schema (one-line moment became multi-turn gem with four-part anatomy) and added new output kinds (narrative spectra, dreams), but it preserved the pipeline, the closed tag vocabulary, the coexistence flags, and the inherited nouns. Architect rounds patched local pain points without questioning the inherited shape. The schema got richer; the underlying question ("is this pipeline the right shape at all?") never got asked.

### Goals

**Vocabulary (defined once, used throughout):**
- A **session** is one Claude Code conversation, captured as one `.jsonl` file under `~/.claude/projects/`.
- A **session-record** is the tier-1 row glean produces from that JSONL: metadata + LLM-extracted classification.
- A **work-item** is a cluster of related session-records that span minutes to days, often centered on one design doc. Many sessions, one work-item; sometimes one session is its own work-item.
- A **chunk** is the tier-2 output: one markdown file per work-item, body shaped as four parts (task / context / interaction / review).

**Goals:**

1. Capture per-session metadata (repo, design-doc anchors, theme tags) sufficient to cluster sessions across days into work-items, with no pre-baked vocabulary.
2. Produce one four-part knowledge chunk per work-item that Scott can read and recognize as his technique.
3. Preserve a non-destructive consolidation pass (dreaming) that detects duplicates, cross-references, and stale chunks across the corpus.
4. Make every prompt the LLM sees a file Scott can edit; re-running regenerates output. The prompt file is the iteration surface.
5. Gate any pipeline plumbing on a recognition-test pass against one real distilled chunk before subsequent phases ship.
6. Treat sessions that cannot be classified as quarantined, not dropped silently; Scott reviews and resolves.

### Non-Goals

- Public-facing output. Eventually the distilled technique should be shareable to a teammate or junior dev (per Nate's frame), but that's a future iteration; this design produces private notes Scott alone reads.
- Pre-loaded agent memory. glean chunks are not loaded into future agent context at session start (e.g., via `~/.claude/CLAUDE.md` or per-project memory). The primary consumer is Scott reading the vault. Note: chunks ARE retrievable by future agents through normal oracle search, since they live in the vault that oracle indexes; the distinction is between pre-loaded memory (rejected) and on-demand retrieval (acceptable).
- Backwards compatibility with facet v1/v2. The `failed-facet-v1` branch is dead. No coexistence flag, no migration script, no shared vocabulary.
- Preservation of any v1/v2 vault output. Existing `notes/facet/` content is left in place; Scott decides if and when to clean it. glean writes to `notes/glean/`.
- Real-time UI. Output is markdown notes; navigation is Obsidian.
- Time estimates for any phase.

## Proposed Solution

### Overview

A two-tier pipeline plus a non-destructive consolidation pass.

```
JSONL transcripts (fossil record, read-only)
        │
        ▼
[ Tier 1: per-session classify + normalize ]
        │
        ▼
sessions table (SQLite)        quarantine table (SQLite)
        │
        ▼
[ Cluster: design-doc anchor + semantic similarity ]
        │
        ▼
work-items (materialized in SQLite)
        │
        ▼
[ Tier 2: per-work-item four-part distill ]
        │
        ▼
notes/glean/<work-item-slug>.md   (canonical store)
        │
        ▼
[ Dreaming: dedup + cross-ref + stale-detect ]
        │
        ▼
notes/glean-dreams/<kind>-<hash>.md   (proposals only)
```

### Architecture

**Data flow in one line:** one JSONL session file becomes one session-record (tier 1); session-records cluster into work-items (cluster step); each work-item becomes one chunk file on disk (tier 2); the chunk corpus is periodically inspected for consolidation opportunities (dreaming).

**Tier 1 (harvest).** One pass over `~/.claude/projects/`. For each JSONL session file: parse, normalize the interaction, detect design-doc file touches and skill invocations, send one sonnet fabric call for LLM-extracted fields (summary, emergent theme tags, design-doc focus, orphan flag). Upsert into the `sessions` table keyed on `session_uuid` (re-classify only when `jsonl_sha256` differs from the stored value). Sessions that fail to classify go to the `quarantine` table with a reason.

**Cluster.** Pure function from the `sessions` table to a `work_items` table. Three-stage:

0. **Force singletons for orphan sessions.** Any session with `is_orphan = true` (LLM-judged self-contained, no signal that it relates to other sessions) becomes a Singleton work-item immediately, bypassing both hard and soft cluster.
1. **Hard cluster on `design_doc_focus`** (LLM-judged primary anchor, not the full `design_doc_files` list). Sessions touching the same `design_doc_focus` path within the same repo form one work-item, keyed on that path. Sessions that touch a design doc as a side-effect (e.g., updating a doc reference in CLAUDE.md while doing unrelated work) will have `design_doc_focus = None` and a populated `design_doc_files`; they fall through to stage 2 with the design-doc paths informing the embedding signal but not anchoring the cluster.
2. **Soft cluster on remaining sessions** via embedding similarity over `(summary + theme_tags + design_doc_files_joined)`. Agglomerative with **configurable linkage** (default `complete-link`; also `average-link` or `single-link`). Single-link is provided for explicit override only; complete-link is the default because it does not chain — a known weakness of single-link that would let "rust topic" and "tokio topic" collapse into one mega-cluster once any pair of sessions bridges them. Threshold and linkage are knobs in `~/.config/sb/glean.yml` under `cluster.algorithm` and `cluster.similarity-threshold`. Singletons stay as singleton work-items.

Each work-item carries a `content_hash = sha256(sorted member session_uuids)` that serves as its **stable identity** across re-cluster passes. The title and slug derived from the distill output may shift between renders; `content_hash` does not, so re-renders can find the prior chunk file even when the slug has changed (see the render path under Tier 2).

Re-cluster is always full recompute over the current `sessions` table. No incremental state. When a session's `jsonl_sha256` changes (Claude Code resume appends to the file), the session is re-classified and its `theme_tags` may shift; the next cluster pass then sees the updated tags and may reassign that session. The cascade is local: at most a handful of work-items shift, never the whole corpus.

**Concurrency**: `distill` opens a `BEGIN IMMEDIATE` SQLite transaction over `work_items` for the duration of one work-item's bundle-compose + fabric call + file write. A concurrent `cluster` pass blocks until the transaction closes. With distill running for minutes per work-item and cluster for seconds, the rare collision waits on cluster, which is the cheap side.

**Tier 2 (distill).** Per work-item, one opus fabric call emits a four-part knowledge chunk plus a title; the slug is derived from the title at render time. The render path uses `work_item.content_hash` as the chunk's stable identity: before writing, it scans `notes/glean/` for a chunk whose frontmatter `content-hash` matches; if found at a different path (the slug changed), the existing file is **renamed in place** (preserving any fencepost-protected operator edits) rather than orphaned at the old slug. The body uses `## Task`, `## Context`, `## Interaction`, `## Review` as visible sections. Fencepost-merged on re-distill so operator edits outside the fenceposts survive. Idempotent on `content_hash`.

**Dreaming (consolidation).** Three async detectors, one fabric pattern call per detector kind, run on a slower cadence than tier 1/2:

- **dedup**: identifies pairs of work-items whose content suggests they should be one
- **xref**: identifies cross-reference opportunities (chunk A's review concepts overlap with chunk B's task)
- **stale**: identifies chunks whose member sessions have grown since the chunk was last distilled

Each detector writes proposals to `notes/glean-dreams/<kind>-<sha256-12>.md`. NEVER mutates `notes/glean/`. Scott approves a proposal by editing its frontmatter `status: proposed` to `accepted`; manual application is fine until corpus size makes an apply CLI worth its weight.

### Data Model

#### Session record (tier 1 output)

```rust
pub struct SessionRecord {
    pub id: i64,
    pub session_uuid: String,
    pub jsonl_path: String,
    pub jsonl_sha256: String,
    pub repo_slug: Option<String>,        // e.g. "scottidler/second-brain"
    pub repo_path: Option<PathBuf>,
    pub cwd: Option<PathBuf>,
    pub started_at: DateTime<Utc>,
    pub ended_at: DateTime<Utc>,
    pub design_doc_files: Vec<PathBuf>,   // any docs/design/*.md touched
    pub skill_invocations: Vec<String>,   // e.g. ["create-design-doc", "architect"]
    pub interaction_normalized: String,   // truncated turn-by-turn for LLM input
    pub summary_one_line: String,         // LLM-extracted
    pub theme_tags: Vec<String>,          // LLM-emergent, 3-7
    pub design_doc_focus: Option<PathBuf>,// LLM-picked primary anchor if any
    pub is_orphan: bool,                  // LLM-judged self-contained
    pub classified_at: DateTime<Utc>,
    pub classifier_model: String,
}
```

Idempotence key: `PRIMARY KEY (session_uuid)`. `jsonl_sha256` is a tracked column, not part of the key. On harvest: if the row's stored hash matches the file's current hash, skip; if it differs (JSONL grew on resume), re-classify and update the row in place. One row per session_uuid for the lifetime of the corpus.

#### Quarantine record

```rust
pub struct QuarantineRecord {
    pub id: i64,
    pub session_uuid: String,
    pub jsonl_path: String,
    pub reason: String,
    pub quarantined_at: DateTime<Utc>,
}
```

Reasons: `unresolvable-repo`, `malformed-jsonl`, `classify-call-failed`, `empty-interaction`. Adds rather than mutates; same session can have multiple quarantine rows from multiple runs if the reason changes.

#### Work-item

```rust
pub enum WorkItemKey {
    DesignDoc,   // hard-cluster: shared docs/design/*.md path within a repo
    Theme,       // soft-cluster: embedding similarity above threshold
    Singleton,   // session that did not cluster with anything
}

pub struct WorkItem {
    pub id: i64,
    pub key_type: WorkItemKey,
    pub key_value: String,                // for DesignDoc: the design-doc path. for Theme: cluster id. for Singleton: session_uuid.
    pub repo_slug: Option<String>,
    pub content_hash: String,             // sha256(sorted member session_uuids); stable identity across re-cluster passes
    pub session_uuids: Vec<String>,
    pub time_span: (DateTime<Utc>, DateTime<Utc>),
    pub aggregated_tags: Vec<String>,     // union of theme_tags across member sessions
    pub materialized_at: DateTime<Utc>,
}
```

Work-items are rematerialized on every cluster pass; the table is truncate-and-rebuild, not upsert-by-key. Tier 2 reads the current `work_items` table and distills each.

#### Knowledge chunk (tier 2 output)

A vault markdown file at `notes/glean/<work-item-slug>.md`. No SQLite row; the file is the artifact.

```markdown
---
type: glean
content-hash: <sha256-of-sorted-member-session-uuids>   # stable identity; survives slug churn
work-item-key: <design-doc-path | theme-slug | singleton-session-uuid>
work-item-key-type: design-doc | theme | singleton
repo: <reponame>
title: <human-readable title produced by the distill prompt>
sessions: [<uuid>, ...]
time-span: [<start>, <end>]
tags: [<aggregated-from-sessions>]
extractor: glean-distill-v1
extractor-model: claude-opus-4-7
extracted-at: <date>
---

# <Work-Item Title>

> [!tldr]
> <one-paragraph synthesis>

<!-- glean:fencepost-start -->
## Task

<what Scott was trying to accomplish across the work-item>

## Context

<what Scott brought in: design docs, prior decisions, repo state, constraints>

## Interaction

<the back-and-forth: how Scott steered the LLM, where the LLM got it right or wrong, what was rejected or kept>

## Review

<Scott's verification and judgment: what was tested, what was committed, what feedback was given>
<!-- glean:fencepost-end -->
```

#### Dream proposal

A vault markdown file at `notes/glean-dreams/<kind>-<sha256-12>.md`. Frontmatter includes `type: glean-dream`, `kind: dedup|xref|stale`, `status: proposed|accepted|dismissed`, and pointers to source work-items.

### API Design

CLI surface on `sb glean`:

```
sb glean harvest                        # tier 1: classify all unprocessed JSONL sessions
sb glean cluster                        # rematerialize work-items table
sb glean distill [--work-item <slug>]   # tier 2: distill one or all work-items
sb glean dream                          # consolidation pass: write dream proposals
sb glean quarantine list|inspect|drop   # failure-recovery surface
sb glean show <work-item-slug>          # print a work-item's source sessions for inspection
sb glean status                         # report counts + cadence
sb glean daemon [--install|--uninstall] # background cadence runner
```

Configuration (`~/.config/sb/glean.yml`):

```yaml
cluster:
  algorithm: complete-link        # complete-link | average-link | single-link
  similarity-threshold: 0.78      # cosine cutoff for soft-cluster
  min-cluster-size: 2

daemon:
  harvest-interval-secs: 600      # 10 min
  dream-interval-secs: 86400      # 24 h
  # cluster and distill fire after harvest when any session changed
```

Cluster algorithm defaults to **complete-link** because single-link is susceptible to chaining (the Architect's concern: A clusters with B, B clusters with C, so unrelated A and C merge into one work-item). Complete-link does not chain. `average-link` is the middle-ground option for cases where complete-link is too conservative. `single-link` is provided only for explicit override during diagnostic work.

Quarantine is never automatic; always operator-driven via the CLI.

### Implementation Plan

#### Phase 0: Recognition-test gate (pre-code)
**Model:** opus

Goal: run the tier-2 distillation prompt by hand against one real work-item Scott just lived through (the facet-v2 effort itself, since the JSONL transcript is fresh and Scott can recognize-test the output cold).

Steps (no code, fabric and shell only):

1. Hand-write the first version of `glean-distill.md` per the four-part chunk schema.
2. Pick one cluster of sessions from `~/.claude/projects/-home-saidler-repos-scottidler-second-brain/` that span the facet-v2 work (the JSONL files from 2026-05-26 through 2026-05-27).
3. Compose the input bundle: per-session normalized interaction (turn-by-turn, AI says and Scott says, tool-result blobs > 800 chars replaced with `<tool-result: N lines, $tool>` placeholders), concatenated with explicit `=== session <uuid> ===` separators. If the bundle exceeds ~150k input tokens (well inside opus's 200k window with headroom), split the selected session range temporally at its median timestamp and run Phase 0 twice (one per half), producing two chunks. Never summarize a member session as input; summarized-and-distilled would defeat the recognition test we're trying to pass.
4. Scott reads. The chunk either passes the recognition test (Scott says "yes, that's me, I could teach that") or it doesn't.
5. If pass: lock the prompt as the working spec for Phase 3. Phase 1 starts.
6. If fail after three prompt-iteration rounds: stop iterating on the prompt within the four-part schema. The legitimate next moves are (a) try a different chunk shape (teaching-journal essay, pattern-catalog entry, daily-review entry) on the same input, or (b) declare the design wrong and stop. The four-part schema is a design hypothesis, not a fixed constraint.

Output: a working `glean-distill.md` prompt and one validated chunk pinned as a regression artifact at `~/.local/share/sb/glean-phase-0/recognition-passing-chunk.md` (outside the crate; Phase 0 ships nothing into the repo). Phase 1 will copy this artifact into `glean/tests/fixtures/phase-0/` once the crate exists. If no chunk shape under any of (a), (b), or (c) passes the recognition test on one real work-item, the entire design is wrong and we stop.

#### Phase 1: Crate scaffold, tier-1 schema, JSONL parser, classify pattern
**Model:** sonnet

- `glean/` crate added to workspace; `Cargo.toml`, `src/lib.rs`, `src/cli.rs` skeleton.
- `glean/src/ledger/schema.rs`: initial schema as a Rust constant, applied idempotently on `Ledger::open` via `CREATE TABLE IF NOT EXISTS`. No bash migration script. glean has no prior schema to migrate from, so the per-workspace rule "no Rust schema migrations" does not apply (the rule covers changeover between versions; initial setup in Rust is the workspace's established pattern in facet v1, cortex, oracle).
- `glean/src/jsonl.rs`: parser that yields `RawTurn` records from a JSONL session file. Detects file-touch events (Edit/Write tool calls with file paths), skill invocations (slash-commands), tool-result blobs (truncated to placeholders > 800 chars).
- `glean/src/classify.rs`: builds the normalized interaction string, runs the sonnet fabric call against `glean-classify.md`, parses JSON output (`summary_one_line`, `theme_tags`, `design_doc_focus`, `is_orphan`), upserts a `SessionRecord` via `glean/src/ledger/sessions.rs`.
- `glean/patterns/glean-classify.md`: source of truth, syncs to `~/.config/sb/patterns/` on `otto deploy`.
- Tests over real JSONL fixtures.

Exit criterion: `sb glean harvest` (placeholder CLI) processes the user's JSONL corpus end-to-end without crashing; quarantine table receives any sessions that fail to classify.

#### Phase 2: Clustering
**Model:** sonnet

- `glean/src/cluster.rs`: two-stage cluster as described in Architecture.
- Embedding: reuse `vault::embedding::embed_query` (Candle backend via the `vec` feature; `vec` pulls `vec-candle`, not fastembed, since fastembed was rejected for this workspace).
- Cluster algorithm: agglomerative with configurable linkage. Default `complete-link`; also `average-link` and `single-link`. Threshold defaults to `cluster.similarity-threshold: 0.78`. Both knobs live in `~/.config/sb/glean.yml` under `cluster.*`. Hardcoded constants are limited to module-level fallback defaults read by the config loader.
- `glean/src/ledger/work_items.rs`: truncate-and-rebuild on every cluster pass. `content_hash` is computed at materialization: `sha256(sorted_member_session_uuids.join("|"))`, hex-encoded.
- Tests: synthetic fixture sets covering hard-cluster (shared design-doc), soft-cluster (similar themes, no design-doc), singletons, and empty. Plus a chaining-resistance test: a fixture of three groups of 5 sessions each, where one session in group A weakly resembles one in group B and one in B weakly resembles one in C; complete-link must keep all three groups separate, single-link must merge them (asserted as a property check that catches the linkage knob being silently flipped).

Exit criterion: `sb glean cluster` rematerializes the work-items table; running twice on unchanged input produces identical output.

#### Phase 3: Tier-2 distill library + fencepost-merge vault renderer
**Model:** opus

- `glean/src/distill.rs`: per-work-item dispatch. Loads work-item, loads member sessions, composes the input bundle (full interaction for every session; no summarization), runs the opus fabric call against `glean-distill.md`, parses output as four-part body + title + tldr. Holds a `BEGIN IMMEDIATE` SQLite transaction on `work_items` for the full call to prevent slug churn during write.
- `glean/src/render.rs`: vault note render with fencepost-merge plus **content-hash rename-on-write**. Before writing, scans `notes/glean/` for any chunk whose frontmatter `content-hash` matches the current work-item's `content_hash`. If found at a different filename (the slug changed), the file is renamed in place via `std::fs::rename` and then the fencepost-merge updates the body. If not found, a new file is written. If found at the current filename, normal fencepost-merge. This makes the work-item's content_hash the load-bearing identity; the slug is a label that can drift. The fencepost-merge primitive itself is copied forward from `failed-facet-v1`'s `facet/src/block.rs::block::merge` (the only Rust salvage); it is content-agnostic and well-tested.
- `glean/patterns/glean-distill.md`: locked from Phase 0. Produces JSON `{title, tldr, task, context, interaction, review}`; the renderer composes the markdown.
- Tests: render a known input, assert frontmatter shape (including `content-hash`), assert fencepost boundaries, assert operator-content-outside-fenceposts is preserved on a second render, **assert that a second render with the same `content_hash` but a different title renames the existing file rather than orphaning it**.

Exit criterion: `sb glean distill --work-item <slug>` produces a chunk at `notes/glean/<slug>.md` for the Phase 0 work-item that matches the Phase 0 hand-validated output (modulo minor LLM nondeterminism).

#### Phase 4: Dreaming layer
**Model:** opus

- `glean/src/dream/{dedup,xref,stale}.rs`: one detector module per kind. Each detector emits a `Dream` enum variant; renderer at `glean/src/dream/render.rs` writes to `notes/glean-dreams/<kind>-<hash>.md`.
- `glean/patterns/{glean-dream-dedup,glean-dream-xref,glean-dream-stale}.md`: prompts per detector.
- Dreams are never persisted in SQLite; each pass regenerates from canonical inputs. Persisting dream state in SQLite would create a second source of truth (the chunks are one source; dream state would be a second), and operator-accepted dream edits to markdown frontmatter would then need a sync-back path to the database. By keeping dreams as pure-function output over the chunk corpus, the only persistent state is the chunks themselves; dreams are regenerated on every pass and operator edits to dream files are the only durable state.
- Tests: detector fires on a known-duplicate pair; renderer produces a valid markdown file; second run with identical input produces identical filename (content-addressed).

Exit criterion: `sb glean dream` produces non-empty proposals on the current corpus; running twice on unchanged input is a no-op.

#### Phase 5: CLI surface, quarantine, daemon
**Model:** sonnet

- `sb/src/cli/glean.rs`: full subcommand surface (`harvest`, `cluster`, `distill`, `dream`, `quarantine list|inspect|drop`, `show`, `status`, `daemon`).
- `glean/src/daemon.rs`: cadence loop with `last_*_at` timestamps and gated dispatch (per facet-v2 Phase 7 pattern, since the gating logic itself is mechanical and worked).
- `glean/src/daemon/systemd.rs`: install/uninstall via `sb glean daemon --install`. Unit file written to `~/.config/systemd/user/glean.service`.
- `~/.config/sb/glean.yml` template added to `config/templates/`.
- Workspace `CLAUDE.md` updated to describe glean's role alongside borg / cortex / oracle (the facet section is removed; the facet name is dead).
- `cortex::watcher::WatcherConfig::default` and `vault::config::ScanConfig::default` updated to include `notes/glean/` and `notes/glean-dreams/` so oracle indexes glean output (per the `feedback-vault-scan-defaults-cross-cutting` memory).

Exit criterion: `sb glean daemon --install && systemctl --user start glean` runs the full cadence loop; `sb glean status` reports counts; `sb oracle knowledge_search` returns glean chunks in results.

#### Phase 6: Real-corpus soak + recognition-test on multiple chunks
**Model:** opus

- Run `sb glean harvest && sb glean cluster && sb glean distill` against Scott's full JSONL corpus.
- Inventory: how many sessions classified, how many quarantined, how many work-items produced, how many chunks rendered.
- Scott reads 5-10 chunks at random and assigns each a recognition verdict (yes / no / partial).
- If any verdict is "no": trace back to the prompt or the cluster, iterate, re-run for that work-item.
- If the overall yes-rate is below acceptable: roll back to Phase 3 prompt tuning.

Fail-fast clause: if after three rounds of prompt iteration the yes-rate has not improved, the design is wrong and we stop. The fix is not more iteration; it is a different design. This is the explicit refusal to repeat the facet-v2 "ship more pipeline" failure mode.

Exit criterion: Scott confirms the corpus is read-worthy and that the distilled chunks let him recognize his own technique. This is the soak gate v2 skipped.

## Alternatives Considered

### Alternative 1: Keep the facet name and shape, fix the prompts

- **Description:** Reuse facet's crate, schema, and pipeline; only revise the gem/spectrum/dream prompts to improve output quality.
- **Pros:** Less code churn. Reuses existing tests.
- **Cons:** The shape itself was wrong. v2 already tried this (Architect rounds patched prompts within v1's structure) and it produced more elaborate pipeline rather than recognition-quality output. The unit-of-capture and unit-of-output were not amenable to prompt-fixing.
- **Why not chosen:** the user explicitly described v2 as making v1 worse; perpetuating the inherited shape under a different prompt invites a v3 of the same morass.

### Alternative 2: Manual span selection (point-and-distill)

- **Description:** No clustering. Scott manually points at a turn-range in a session and asks for a distilled chunk.
- **Pros:** Drastically simpler. Recognition test is built in (Scott picks the span). No clustering ambiguity.
- **Cons:** Work that spans days and design docs cannot be selected by hand at corpus scale, and the cluster signal (design-doc + theme + repo) is real and usable. Scott confirmed this explicitly in the brainstorming conversation that preceded this doc.
- **Why not chosen:** Scott's workflow produces work-items algorithmically (per-design-doc + per-theme); manual selection would reduce throughput to roughly zero.

### Alternative 3: Per-session chunks (no clustering)

- **Description:** Each session produces its own chunk. No work-item concept.
- **Pros:** Simpler. No cluster step.
- **Cons:** Work that spans days produces N disconnected chunks that don't tell the full story; the technique only emerges across sessions. The four-part anatomy is naturally a work-item-scale artifact, not a per-session one.
- **Why not chosen:** the consumer (Scott reading his technique back) needs the work-item-scale view to see patterns; per-session chunks reproduce the v1 shallowness.

### Alternative 4: Skip the recognition-test gate; ship phases sequentially

- **Description:** Build all phases on a "tests pass, ci green" definition of done. Validate output afterward.
- **Pros:** Faster to a shipped binary.
- **Cons:** This is exactly what facet-v2 did. The unit tests passed; the corpus output was never validated; the result was 22 commits of slop on main that had to be nuked.
- **Why not chosen:** the recognition-test gate is the explicit lesson from the prior failure.

### Alternative 5: Use Anthropic's managed memory directly

- **Description:** Skip the local distillation entirely; let Claude's managed-agents memory + dreaming features run on Scott's sessions.
- **Pros:** Native to the framework that inspired the design.
- **Cons:** Scott's sessions are Claude Code sessions, not managed-agents sessions. The memory store and dreaming features in Anthropic's product are not surfaced for Claude Code session corpora. Even if they were, the consumer would be a future agent, not Scott (the intermediate-stage problem still wouldn't be solved).
- **Why not chosen:** wrong product, wrong consumer.

## Technical Considerations

### Dependencies

- `rusqlite` (already a workspace dep): SQLite for sessions, quarantine, work-items.
- `vault::embedding` with the `vec` feature (Candle backend via `vec-candle`; bge-small-en-v1.5 model). Note: the `vec` feature flag pulls Candle, not fastembed. fastembed was previously considered for this workspace and explicitly rejected; the design stays with Candle.
- Fabric (already installed at `~/.cargo/bin/fabric`): LLM invocation.
- `serde_json`, `serde_yaml`: parsing.
- `chrono`, `clap`, `eyre`, `tokio`: unchanged.
- No new external services.

### Performance

- Tier 1: one sonnet call per session. Roughly 50-200 sessions per run after backfill, mostly cached.
- Cluster: O(N²) similarity computation for the soft-cluster stage where N is the count of sessions without a design-doc anchor. Acceptable up to a few thousand.
- Tier 2: one opus call per work-item. Work-item count is order-of-tens. Per-work-item input is the aggregated normalized interaction across member sessions. Estimated upper bound: a dense 5-session work-item with 50 average turns per session and a 2 KB average turn (after tool-result truncation) is ~500 KB of text, roughly 125k input tokens. Opus's 200k context handles this. Larger work-items either trigger the bundle-composer's per-session token cap (see Risks) or get split by the cluster step.
- Dream: three sonnet calls per pass. Daily cadence.

### Security

No new attack surface. Local JSONL files in, local markdown files out, fabric shell-out.

**Secret redaction at the prompt level.** Claude Code session transcripts routinely contain pasted secrets: API keys, tokens, .env contents, command outputs that include credentials. The prompts at `glean/patterns/glean-classify.md` and `glean/patterns/glean-distill.md` carry the same `<redacted>` instruction borg's `distill-*.md` patterns use: the LLM is instructed to substitute `<redacted>` for any token, key, URL with embedded credentials, or block that matches a secret-shaped pattern. A post-LLM pass also scans the output against a known-secret-shape regex set (the same set borg uses); any matches quarantine the session-record or chunk file rather than letting it land in the vault. The fallout from a missed redaction is local to Scott's vault, but the vault is also the source for borg notes that he sometimes publishes, so the leak path is real.

### Testing Strategy

- **Phase 0 hand-validation** is the load-bearing gate (see Implementation Plan Phase 0).
- **Unit tests** per module in the sibling-`tests.rs` workspace convention.
- **Real-JSONL fixtures** at `glean/tests/fixtures/`: a small synthetic JSONL covering one session, expected SessionRecord shape, expected work-item materialization.
- **Idempotency tests:** harvest twice over the same input is a no-op; cluster twice is identical; distill twice produces matching output modulo fenceposts.
- **Phase 6 real-corpus soak** is the final test (see Implementation Plan Phase 6).

### Rollout Plan

1. Phase 0: prompt iteration by hand. No code shipped.
2. Phases 1-5: ship together as one PR. The pipeline is one tier-1 + cluster + tier-2 + dream + CLI; splitting them introduces partial states with no operator value.
3. Phase 6: real-corpus soak runs locally; tuning happens via prompt edits, no code changes. When Scott confirms read-worthiness, the design is done.
4. No coexistence flag, no migration script. There is no v1 to coexist with from glean's perspective.

## Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Phase 0 recognition test fails repeatedly; the four-part schema is not the right shape for technique recognition. | Medium | High | Phase 0 is the gate. If the prompt cannot produce a recognition-passing chunk by hand on one real work-item, the design is wrong and we stop, not push through. The lesson from facet-v2 is exactly this. |
| Cluster step produces work-items that span unrelated work; chunks become incoherent. | Medium | Medium | Hard-cluster on design-doc is unambiguous. Soft-cluster uses **complete-link** agglomerative by default (not single-link) so two unrelated themes cannot bridge via one weak connector — a known single-link failure mode. Threshold and linkage are both tunable via `~/.config/sb/glean.yml` (`cluster.algorithm`, `cluster.similarity-threshold`). If a work-item is still incoherent on inspection, the threshold tightens. Singletons are legitimate. |
| Work-item slug churn on re-cluster orphans chunk files; Scott's manual edits to a chunk get stranded at the old slug. | Medium | High | Work-items carry a stable `content_hash` (sha256 of sorted member session_uuids); the chunk's frontmatter stores it. On render, the path is determined by `content_hash` lookup, not slug match: an existing chunk with the same `content_hash` at a different path is **renamed in place**, preserving its fencepost-protected operator content. Only when the membership set itself changes (truly a different work-item) does a new file land at the new slug and the old chunk become stale (dream-stale flags it). |
| Concurrent `distill` and `cluster` produce inconsistent file artifacts (chunk written to a slug the cluster pass just invalidated). | Low | Medium | `distill` opens `BEGIN IMMEDIATE` over `work_items` for the full bundle-compose + fabric-call + file-write window. `cluster` blocks until that closes. With distill at minutes-per-work-item and cluster at seconds, the rare collision waits on cluster, which is the cheap side. |
| LLM-emergent tagging produces inconsistent vocabulary across runs. | Medium | Low | Tags are aggregated at work-item level; minor variation per session is fine. If the corpus develops a stable de-facto vocabulary, the prompt can be tightened to encourage reuse; no closed list is baked in. |
| Tool-result blobs in JSONL push the classify call past the 8k output cap. | Medium | High | Same capture-side truncation rule as facet-v2: tool-result blobs > 800 chars replaced with `<tool-result: N lines, $tool>` placeholders. Carry over the mechanism, not the schema. |
| Sessions with multiple design-doc touches anchor to the wrong work-item. | Medium | Low | `design_doc_focus` field is LLM-judged primary anchor; `design_doc_files` keeps all touches for cross-reference. Hard-cluster uses `design_doc_focus` as the key; `design_doc_files` informs the dream `xref` detector. |
| Existing v1 facet output in `notes/facet/` confuses Scott when alongside `notes/glean/`. | Low | Low | glean writes only to `notes/glean/`; v1 output is left untouched. Scott decides if and when to clean. No auto-deletion. |
| Recognition-test verdicts are subjective; Scott may not be a consistent rater across days. | High | Medium | The Phase 0 chunk is pinned as a regression fixture; later distill runs against the same work-item are compared head-to-head with that fixture, not judged in isolation. Soft drift is detectable when a same-input run produces a chunk that misses things the fixture caught. Hard drift (the fixture itself no longer reads as right) means re-running Phase 0 from scratch with the prompt that diverged. |
| Recognition test fails repeatedly and the team is tempted to "ship and iterate later." | Medium | High | Phase 0 is the gate. If the gate cannot be passed by hand on one real work-item, downstream phases are not started, period. The doc names this explicitly because facet-v2 broke exactly here by treating "tests pass" as a substitute for "output is read-worthy." |
| The four-part chunk is not the right artifact shape for self-recognition; the schema forces technique into a frame that fits Nate's public-AI-work program but not Scott's private self-mining. | Medium | High | Phase 0's failure response is not only "iterate the prompt within the four-part schema." The legitimate Phase-0-failure responses are: (a) iterate the prompt; (b) try a different chunk shape (teaching-journal essay, pattern-catalog entry, daily-review entry); (c) declare the design wrong and stop. Three rounds of (a) without recognition-pass success means trying (b) or (c) before any code ships. The schema itself is a design hypothesis, not a fixed constraint. |
| Work-item input bundle for very large work-items (15+ sessions, dense interactions) exceeds opus context window. | Low | Medium | The bundle composer never summarizes; summary-only sessions would destroy the technique signal that the tool exists to capture. If the bundle does not fit opus context with full interaction for every member session, the cluster step splits the work-item temporally (median timestamp) and re-distills as two chunks. The split is reflected in `content_hash` (the membership set changed), so the prior single chunk's identity no longer matches; the dream-stale detector flags it for operator review. |
| Multi-repo sessions (a session whose interaction touches files in more than one repo). | Low | Low | Rare. `repo_slug` is set from the cwd at session-start; sessions whose interaction crosses repos still have one cwd. If the LLM classifier flags the session as multi-repo, it gets quarantined with reason `multi-repo`; Scott decides per-case. |
| Secrets in pasted command outputs pass through redaction. | Medium | High | Two-layer defense: prompt-level `<redacted>` instruction (LLM substitutes inline), plus regex-based post-LLM scan against the known-secret-shape set borg uses. Failures quarantine the row/file rather than land it. |
