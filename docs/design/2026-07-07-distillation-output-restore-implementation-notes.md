## Phase 0: Prove the enumeration prompt on the April baseline

### Design decisions
- Draft patterns live at `docs/design/2026-07-07-distillation-output-restore-patterns/` (`distill-video.md`, `distill-video-chunk.md`, `distill-video-reduce.md`) - NOT in `borg/patterns/` - because landing them there is Phase 4's job and `otto deploy` syncs `borg/patterns/` to the live `~/.config/sb/patterns/`. Phase 4 picks them up from the drafts dir.
- Proof ran the REAL raw transcript, not only the recovered legacy body. `ytx KjEFy5wjFQg -f json` (Whisper) recovered the actual 16-minute transcript of the April video; converted to the production `[HH:MM:SS] text` line format. The recovered legacy body (demoted under `## Transcript` in the vault note) already contains the April Enumerated Points verbatim, so it alone is a weak test - the real transcript makes the model extract the enumeration from spoken content. Both inputs were run single-call; the real transcript fed the chunk -> reduce simulation. Reproduce the input with: `ytx KjEFy5wjFQg -f json` then prefix each segment with its `[HH:MM:SS]` start.
- Chunk -> reduce simulation: 4 line-boundary chunks (~48 lines each) via `split -n l/4`. Production would single-call this transcript (under `SINGLE_CALL_TOKEN_THRESHOLD`); the doc explicitly asks for a *simulated* chunk path. The split deliberately landed Firecrawl's discussion across chunks 01/02, producing 11 candidates for 10 items - the reduce deduplicated correctly, keeping the earliest anchor (00:07:33).
- Chunk pattern emits `declared_count` (chunk-level) + `enumeration_candidates` with an `ordinal` field (`#N` when the speaker numbers the item, `#?` when not). The reduce-input wire format (built by Phase 4's `build_reduce_input` extension) is a `## Enumeration Candidates` section: optional `Declared count: N` line, then one candidate per line as `[HH:MM:SS] #N name - text`. Section omitted entirely when no chunk found candidates.
- Reduce gate is evidence-based, default-null: even with candidates present, populate `enumeration` only when (a) a declared count exists, OR (b) most candidates carry real ordinals, OR (c) candidates span the timeline and are what the video is about. This rule earned its shape from a live failure: the first reduce run on the Herdr control FORCED a 2-item "UI sections" enumeration from two spurious chunk candidates (no declared count, no ordinals, one chunk). After strengthening the gate, the same input yields `enumeration: null` and the Top-10 positive case still yields 10/10.
- Fabric invocation mirrors production: `fabric -p <absolute pattern path> -m claude-sonnet-4-6` (`vault::fabric::resolve_pattern` passes absolute paths to `-p`), model = fabric's configured `DEFAULT_MODEL`.
- serde_yaml validation harness (scratch project, not committed) mirrored the design's data-model structs (`Enumeration { lead_in, declared_count, items }`, `EnumeratedItem { name, text, anchor }`, serde-defaulted `tldr`/`enumeration`/`key_ideas`). All five outputs parse and pass:
  - single-call real transcript: 10/10 items in creator order, declared_count=10, 10/10 anchored, tldr + lead_in + 5 key ideas
  - single-call recovered legacy body: 10/10 in order, 10/10 anchored
  - chunk -> reduce real transcript: 10/10 in order, declared_count=10, 10/10 anchored, Firecrawl dedup correct
  - single-call Herdr control (real dirty VTT text, per-word timing tags and rolling duplicates intact): `enumeration: null`
  - chunk -> reduce Herdr control: `enumeration: null` (gate holds against spurious candidates)

### Deviations
- Doc says "run it against the recovered April 'Top 10' transcript source"; the spike ran that AND the stronger real-transcript input (same effect, better evidence - the recovered body already contains the answer key).
- The negative control was also run through the full chunk -> reduce path, beyond the doc's single criterion. It caught the forced-enumeration failure the single-call path missed; Phase 4 should keep a chunked negative control in its tests.
- Phase 0 commit includes the design doc itself (it was untracked; a phase commit referencing a doc absent from history would dangle).

### Tradeoffs
- `ordinal` on chunk candidates vs bare candidate lists - chosen because the reduce needs creator order across chunk boundaries and anchors alone cannot distinguish "speaker numbered this" from "speaker mentioned this"; the Herdr failure showed ordinals are also gate evidence.
- One fabric run per case (no repeat-sampling) - the spike proves the prompt CAN do it; drift protection is Phase 7's eval metric, not repeated spike runs.
- Herdr control input used as-is with its VTT dirt (timing tags, rolling duplicates) rather than pre-cleaned - realistic worst-case input today; Phase 1 cleans it upstream.

### Open questions
- The recovered-legacy-body run reported 10/10 anchors, but that input has no `[HH:MM:SS]` transcript lines - the model lifted anchors from the video description's `M:SS`-format timestamp list and normalized them. Phase 4's anchor-honesty rule should decide whether description-derived anchors are acceptable or must be stripped.
- Whisper mishears "Claude Code" as "Cloud Code" throughout the real transcript; item names came through correctly regardless. If Phase 7 fixtures use ytx-recovered transcripts, expect that dirt in fixture text.

## Phase 1: Fix parse_vtt_segments

### Design decisions
- Replaced the literal `.replace("<c>", "").replace("</c>", ...)` chain with a shared `VTT_TAG_REGEX` (`</?c[^>]*>|<\d{2}:\d{2}:\d{2}\.\d{3}>`) in a new `strip_vtt_tags` helper (`borg/src/youtube.rs`), matching the doc's exact regex ask. `<i>`/`</i>` stay a literal replace inside the same helper (unchanged behavior, not itemized in the doc but present in the original code - kept so italic markup does not regress).
- Extracted the rolling-overlap decision (`extends -> replace, covered-by -> skip, dup -> skip`) that already lived inline in `clean_vtt` into a standalone `rolling_dedupe_action(last: Option<&str>, candidate: &str) -> RollingAction` function, and call it from both `clean_vtt` and `parse_vtt_segments`. This is the "port... reuse/share it rather than reinventing" instruction: one function now owns the collapse rule instead of two independently-maintained copies (which is exactly how `parse_vtt_segments` fell behind `clean_vtt` in the first place per the doc's compounding-bug paragraph).
- In `parse_vtt_segments`, a `Replace` action keeps the *earliest* start timestamp (the first cue where the growing line began) rather than the latest cue's start - the replacement text is the same utterance, just more complete, so its earliest-known start time is the semantically correct anchor for `slides::bind_transcript` callers.
- Added function-level debug logging to `parse_vtt_segments` (entry: byte length; exit: segment count) and `clean_vtt` (entry: byte length; exit: collapsed line count / result length), matching the file's existing instrumentation pattern; neither had any logging before.

### Deviations
- None. Implemented at the seam the doc named (`borg/src/youtube.rs`, `parse_vtt_segments` + `clean_vtt`), no new crate, no behavior change to unrelated functions.

### Tradeoffs
- Shared `rolling_dedupe_action` returns an enum (`Push`/`Replace`/`Skip`) rather than mutating the caller's `Vec` directly - chosen so the same decision function serves `clean_vtt`'s `Vec<String>` and `parse_vtt_segments`'s `Vec<(f64, String)>` without either one adapting its data shape to the other.
- Kept the pre-existing match-arm ordering where `candidate.starts_with(last)` is checked before the exact-equality arm (so an exact-duplicate candidate takes the `Replace` branch, not the dead `Skip` arm below it) - this mirrors `clean_vtt`'s original code exactly (the equality arm was already unreachable there) and is a no-op in practice since replacing identical text with itself does not change the accumulated value.

### Open questions
- None.

- Placed the three new body fields between `summary` and `claims` in the struct so serialized YAML reads in note-body order (summary -> tldr -> enumeration -> key-ideas -> claims). Order is cosmetic for serde but keeps staged files legible.
- Rewrote the `Distilled.transcript` doc comment (`vault/src/distilled.rs`) to split the invariant: the FIELD stays populated (regression-guarded, do NOT revert to `None` - staging + embedding source), while the RENDER is now caller-gated. ## Phase 4: Prompts + parse (enumeration through map-reduce)

### Anchor-honesty decision (Phase 0 open question, RESOLVED)
- **Rule chosen:** an enumeration/claim anchor is honest ONLY if it maps to a real position in the TRANSCRIPT. For a chunked video, the pooled chunk candidates ARE the set of transcript positions the chunks observed, so the reduce may keep an item anchor only when it matches a candidate-pool anchor. A timestamp lifted from the video description, chapter list, or a pinned comment is NOT honest unless it ALSO appears as a real transcript line prefix. This is exactly the recommended default in the task: "a description-derived timestamp that also appears in the transcript is fine, a fabricated one is not."
- **Enforced in three layers:**
  1. Prompt (both single-call and chunk/reduce video patterns): explicit ANCHOR-HONESTY RULE forbidding lifting from description/chapters; copy only from `[HH:MM:SS]` transcript line prefixes; `null` otherwise.
  2. Reduce path (`parse::resolve_reduce_enumeration`): resolves each restored item's anchor against the candidate-pool anchor set; a non-matching anchor is stripped to `None` and counted in `anchors_stripped`, item text retained. An anchorless candidate pool (articles) strips every item anchor.
  3. Both paths (`video::validate_anchors`, extended): enumeration item anchors ride the same parse + duration-range gate as claim anchors (malformed or past `duration_seconds` -> stripped + counted). This catches the single-call path (no pool) where the model emits an in-format but out-of-range chapter timestamp.
- Articles and repos carry NO positional anchors: their item anchors are stripped unconditionally (`strip_item_anchors` in article.rs / repo.rs single-call; `resolve_reduce_enumeration` with an anchorless pool on the article long path).

### Design decisions
- Enumeration parse leaves added to `distillers/src/parse.rs`: `PatternEnumeratedItem`, `PatternEnumeration` (single-call/reduce shape, `into_enumeration()` returns `None` for an empty `items:` list so a stray `enumeration:` header never renders an empty section), `PatternEnumCandidate` (chunk shape with `ordinal`, `into_candidate()`), and the collected `EnumCandidate` (already-trimmed data the reduce-input builder consumes). Field names are snake_case (`lead_in`, `declared_count`, `key_ideas`, `enumeration_candidates`) to match the Phase-0-PROVEN prompt output verbatim, not the vault `Distilled` kebab-case serialization — the parse leaf and the staged/rendered form are separate representations bridged by `into_*` conversions, exactly as `PatternClaim -> Claim` already works.
- `PatternYaml` / `ReduceYaml` extended with serde-defaulted `tldr` / `enumeration` / `key_ideas` (plus `declared_count` / `enumeration_candidates` on `PatternYaml` for the chunk shape). No `deny_unknown_fields` (tolerant-envelope carve-out honored). repo's local `PatternYaml` got the three single-call fields.
- `build_reduce_input` signature grew `enum_candidates: &[EnumCandidate]` + `declared_count: Option<u32>` and emits a `## Enumeration Candidates` section (format `[HH:MM:SS] #N name - text`, `#?` when unnumbered, anchor bracket omitted when absent, optional `Declared count: N` line). The whole section is OMITTED when no candidate exists — that absence is the reduce pattern's gate signal for `enumeration: null` (preserving the Phase-0-tuned evidence-based gate). ALL callers updated in the same edit: video.rs, article.rs, voicenote.rs (`&[], None`), and `build_thread_reduce_input` (`&[], None`), plus the two parse test call sites.
- `select_reduce_claims` seam extended with a sibling `resolve_reduce_enumeration` (same anchor-honesty pattern applied to enumeration items).
- validate.rs bounds for the new fields: `MAX_ENUMERATION_ITEMS=30` (count cap), `MAX_ENUM_ITEM_CHARS=400` (per-item name+text, truncates text only), `MAX_KEY_IDEAS=10` + `MAX_KEY_IDEA_CHARS=400`, `MAX_TLDR_CHARS=400`. Each records a distinct `bounds_truncations` tag. Folded into `enforce_bounds` via three helpers.
- Enumeration shortfall wiring (Resolved Decision 2026-07-07): `ValidationMeta` gained a serde-defaulted `enumeration_shortfall: bool`. `distillers::mark_enumeration_shortfall` sets it (with a WARN) when `declared_count == Some(n)` and `items.len() < n`; called in every listicle distiller's exit AFTER `enforce_bounds` so the item-count cap (which only trims counts ABOVE declared) can never fabricate a false shortfall. Never hard-fails.
- Receipt-degraded signal: added `ValidationMeta::is_degraded()` as the single source of truth (`fallback_reason.is_some() || enumeration_shortfall`) and routed all five terminal pipeline degraded computations through it (`pipeline.rs` URL site, `handlers.rs` x2, `text.rs` x2). This is the "explicit degradation signal into the ingest result rather than piggybacking on fallback_reason" the panel required — a shortfall is not a fallback, but both OR into the receipt `degraded` flag that flows to `receipts::mark_succeeded`.
- Patterns landed in `borg/patterns/` (source of truth; `otto deploy` syncs to `~/.config/sb/patterns/`): the three video patterns (from the proven Phase-0 drafts, with the anchor-honesty rule made explicit in the prompt text), the three article patterns (enumeration added; article items carry `anchor: null`), and `distill-repo.md` (single-call enumeration; awesome-list READMEs).

### Deviations
- The task listed "video + article + repo -- single-call, chunk, and reduce variants." Repo is SINGLE-CALL ONLY (no `distill-repo-chunk`/`-reduce` files exist and `repo.rs` does not chunk — READMEs are short). Repo gained enumeration on its single-call path only; no chunk/reduce variants were invented. Same effect for the doc's intent (repos get the April fields), correct seam.
- Parse leaf field names are snake_case, not the vault kebab-case. Deliberate: they mirror the Phase-0-proven prompt output exactly (the Phase 0 harness used `Enumeration { lead_in, declared_count, items }` with no rename), and the LLM prompt emits snake_case. The kebab-case form lives only on the vault `Distilled` (staged/rendered), reached via the `into_*` conversions. Documented here so a future reader does not "fix" the parse leaves to kebab and silently break parsing.
- Receipt-degraded computation was refactored into `ValidationMeta::is_degraded()` and applied at all five terminal sites, not only the URL site named in the wiring note. The other four sites feed kinds that never populate enumeration (so `enumeration_shortfall` is always false there) — the refactor is DRY and harmless, and keeps the degraded rule in one place.

### Tradeoffs
- A dedicated `resolve_reduce_enumeration` (candidate-pool anchor gate) vs relying solely on `validate_anchors` (duration-range gate): chosen the layered approach because the duration gate alone cannot catch a description-lifted timestamp that happens to fall within the video's runtime — only the candidate-pool gate distinguishes "real transcript position" from "in-range but never spoken." `validate_anchors` still runs on both paths as the structural backstop for the single-call path (which has no pool).
- Unit tests drive the map-reduce enumeration with a faked reduce output (FakeFabric returns canned YAML), so "all N items in order" tests the CODE plumbing (candidate collection -> reduce input -> parse -> resolve -> populate) deterministically. The real-model "April fixture survives" proof was Phase 0; Phase 7 adds the drift-protection eval metric. A repeat-sampling model run is out of scope for a unit test.
- `mark_enumeration_shortfall` keyed on `declared_count` only (not on ordinals or timeline span): the declared count is the one hard signal the user stated ("Top 10"); missing it is the exact regression this design exists to catch. A softer "we think there should be more" heuristic would be noise.

- None. The Phase 0 anchor-honesty open question is resolved above.

The staged `distilled.yml` is immutable after publish, so this is correct-by-construction; a sentinel skip is final until note-modification or a model bump.
- `NoteType::transcript_eligible()` unchanged (Article+Youtube stay): only the text SOURCE moved; the SQL staleness filter still selects those kinds. Confirmed, not changed.
- CLAUDE.md one-way-data-flow paragraph updated with the new read-only edge (cortex reads borg's staged `distilled.yml`); borg stays sole staging writer, cortex sole embeddings writer.

## Phase 6: Backfill strip sweep

### Design decisions
- Built `bin/strip-transcripts` as a genuine standalone Rust crate (new workspace member `bin/strip-transcripts`, added to `members` in the root `Cargo.toml`, NOT to `default-members` so `cargo build`/`otto install` still default to `sb` only), not a bash script. The design's own "housed beside `bin/migrate-receipts` (its exact precedent)" language describes the *operational pattern* (standalone one-shot tool outside `sb`, prints a manifest, refuses on a dirty tree) — every actual `bin/*` precedent in this repo (`migrate-receipts`, `repair-url-wikilinks`, `recover-pais-migration`) is bash per a documented "no-Rust-migrations rule" (`docs/design/2026-06-11-cortex-linker-url-corruption.md:149`, `.../implementation-notes.md:31`: "otto ci (Rust-only) does not run it"). This phase's spec directly contradicts that rule: it names `vault::note::write_atomic` (a Rust function) and requires importing the `NoteType` enum ("schema is law, do not hardcode kind strings") — neither is reachable from bash. A bash rewrite would either hand-roll frontmatter/enum parsing (violating schema-is-law) or shell out to a throwaway Rust helper anyway. Built it as a first-class crate so `cargo check --workspace --all-targets --features vec` and `otto ci` (both explicitly required by this phase's success criteria) actually exercise it — the same otto-ci coverage the no-Rust-migrations rule says migration bash scripts deliberately forgo.
- Kind scope: `vault::schema::NoteType::transcript_from_staging()` (Youtube/Video/Article), not a hand-rolled match. This is the exact seam Phase 5's embed re-point already keys on, and its doc comment cites this very design — using it here means Phase 6 cannot drift from Phase 5's kind scope.
- Candidate population: **every note whose kind is in `transcript_from_staging()`**, examined regardless of `ingested` presence or date (not pre-filtered by date). Rationale: the design's own required test matrix (from the task) demands a reachable "missing-ingested -> refused" case and a reachable "pre-cutoff -> refused, untouched" case in the SAME manifest run; a candidate definition that pre-filters by `ingested >= cutoff` would make both cases unreachable (a note failing either check would never enter the candidate set to begin with). Examining the full kind-scoped population and expressing date/ingested-presence as per-note disposition guards makes every guard the design calls out (missing ingested, unparsable ingested, pre-cutoff) independently observable and testable, and gives the operator a complete audit trail (they can see the protected legacy notes listed as `refused: pre-cutoff`, not just absent) — directly answering the design's own High-impact risk "Backfill strips a legacy-body note."
- Strip mechanism: `find_transcript_start` walks `note.raw` with `split_inclusive('\n')`, matching a line whose `.trim()` is exactly `"## Transcript"`, and accumulates exact segment byte lengths for the offset (never a computed/arithmetic offset) — satisfies the UTF-8 char-boundary rule while still being a "safe find/split," per the phase's explicit instruction. Operates on `note.raw` (the full original file, frontmatter included) rather than reassembling frontmatter + body via `Frontmatter::to_yaml()`, so untouched notes and the untouched prefix of stripped notes are guaranteed byte-identical to the original file — `to_yaml()` re-serialization was explicitly flagged elsewhere in this codebase as a "data-loss trap" (`cortex/src/summarize.rs:322`) for exactly this kind of rewrite, and sidestepping it here means Phase 6 can't reintroduce that class of bug.
- Disambiguating "## Transcript" from a plural or demoted heading (`"## Transcripts"`, `"### Transcript"`) is handled by the exact-line-trim match rather than a substring search — a raw `.find("## Transcript")` would false-positive on `"## Transcripts"`.
- `ensure_clean_worktree` shells out to `git -C <vault> status --porcelain`; any non-empty output refuses the whole run before any writes happen. Kept as a separate public function (not inlined into `run`) so unit/integration tests can exercise classification and stripping against a plain temp dir with no git repo, and exercise the git guard itself against a real throwaway git repo, independently.
- `main.rs` is the only place that prints (manifest lines + the `N candidates / M stripped / K refused` summary, counted live from the returned `Report`, never hardcoded); `lib.rs` returns typed data only and carries the same `#![deny(clippy::print_stdout, clippy::print_stderr)]` (test-exempted) convention `borg`'s lib root uses.
- No `--dry-run` flag: the design doc's Phase 6 spec does not call for one, and the operator's actual rollback mechanism is the pre-run clean-worktree requirement (`git checkout`/`git revert` after the fact), which is the same reasoning the design gives for the dirty-worktree guard ("git is the rollback only when the tree is clean"). Adding a dry-run flag not requested by the design would be unrequested scope.

### Deviations
- **Candidate-set semantics are an inference, not a literal spec quote.** The design says "N candidates ... (37 candidates at research time)" without defining exactly what population "candidate" denotes. This implementation chose "all Video/Article/Youtube-kind notes in the vault" (see Design decisions above) over the narrower "kind + `ingested >= cutoff`" reading, specifically because the narrower reading makes the phase's own required missing-ingested and pre-cutoff refusal tests structurally unreachable. This cannot be verified against the live vault from this sandboxed session (no vault access); flagged here for confirmation against the actual `37` research count when the operator runs this for real.
- The design names the cutoff informally as "2026-06-28"; implemented as `CUTOFF_RFC3339: &str = "2026-06-28T00:00:00Z"` (midnight UTC) since `ingested` values in the live vault are full RFC-3339 timestamps with timezone offsets (confirmed by inspecting `~/repos/scottidler/obsidian/notes/*.md`), not bare dates. Same effect, correct seam.

### Tradeoffs
- Standalone Rust crate vs. a bash script that shells out to `sb` (or a scratch Rust one-liner) for the frontmatter/enum work: chosen the full crate because the phase's success criteria explicitly require `cargo check --workspace` and `otto ci` to cover it, which only happens for a real workspace member — a bash wrapper invoking a separate uncommitted Rust binary would not get that coverage and would violate "schema is law" the moment the wrapper tried to interpret `type:` strings itself.
- Re-deriving `find_transcript_start`'s offset once in `classify` (to decide disposition) and again in `run` (to actually slice) rather than threading `Option<usize>` through: a single one-shot tool over the note-body-sized text is a negligible cost twice; the duplication keeps `classify` a pure, standalone-testable predicate.

### Open questions
- Confirm the live count: run `strip-transcripts` (after Phase 5 lands and the one daemon-host deploy happens, per the design's ship-order) and compare N/M/K against the "37 candidates" research figure. If the counts diverge meaningfully, the candidate-set semantics above may need revisiting with the operator before this becomes routine practice.

## Phase 7b: eval report wiring

Follow-up closing acceptance criterion #4 (design line 197): "`sb borg eval` reports listicle-survival = 1.0 on April fixtures, enforces the note-size metric." Phase 7 landed the two deterministic metrics as pure functions in `calc.rs` but did not surface them through the report; this phase wires them in.

### Design decisions
- Resolved Phase 7's own open question ("which fixtures does listicle-survival apply to") with the natural per-fixture ground-truth gate: **listicle-survival is graded ONLY for fixtures whose EXPECTED `distilled.yml` carries an `enumeration` with a `declared_count` set.** That declared count IS the authored assertion "this fixture is a listicle and must survive." A fixture without one is N/A for the axis - excluded from the aggregate entirely, never folded in as a 0.0 (`borg/src/eval.rs::evaluate`, gated on `fx.distilled.enumeration.as_ref().and_then(|e| e.declared_count).is_some()`). Against the current committed fixture set (22 fixtures) exactly one - `video/top-10-claude-code-skills-plugins-clis-april-2026` - declares a `declared-count`, so it is the sole row in the aggregate at `1.0`.
- Added two new report types (`borg/src/eval/report.rs`): `ListicleMetric { fixture, score }` (one row per APPLICABLE fixture) and `NoteSizeMetric { fixture, rendered_bytes, within_ceiling }` (one row per fixture, unconditionally). `EvalReport` grew `listicle: Vec<ListicleMetric>`, `listicle_aggregate: Option<f64>` (`None` when no fixture is applicable, distinct from `Some(0.0)` which is a genuine failure), and `note_size: Vec<NoteSizeMetric>`.
- New pure aggregator `calc::listicle_aggregate(scores: &[f64]) -> Option<f64>` (mean of the applicable scores, `None` on empty input) - kept in `calc.rs` alongside the two Phase 7 metric functions it aggregates, matching the file's "pure judge-free math" charter.
- note-size is enforced across EVERY fixture regardless of kind, per the task's explicit instruction. Rendering a fixture with the wrong transcript policy would misrepresent its true published size (an Image/VoiceNote/Idea fixture is a verbatim-preservation kind that keeps its transcript in production; rendering it transcript-free would understate its real byte count and make the ceiling check meaningless for those kinds). Added `fixtures::render_options_for_kind(kind: &str, distilled: &Distilled) -> RenderOptions`, a small typed lookup mirroring the design's own six-site policy table: video/article/repo/thread render via `RenderOptions::for_url_publish` (the same seam Phase 7 already used for the video fixture, keyed on the typed `KindPayload` so only Thread keeps its transcript); every other kind (image/voicenote/idea/vocabulary) uses the literal `RenderOptions { include_transcript: true }` those call sites hardcode in production. `evaluate()` renders each fixture with its kind's real policy and reuses `crate::config::MAX_NOTE_BYTES` (via `calc::note_size_within_ceiling`, unchanged from Phase 7) - never redefined.
- `EvalReport::render()` (`report.rs`) gained a "deterministic metrics (zero judge calls)" section: the listicle aggregate + per-applicable-fixture rows (or an explicit "N/A" line when nothing is applicable), and a note-size pass-count summary (`M/N within the <ceiling>-byte ceiling`) with an explicit `FAIL <fixture> <bytes>` line for every fixture over the ceiling - fail loudly, not a silent aggregate.
- Both metrics are computed unconditionally at the top of `evaluate()`'s per-fixture loop, before the cache lookup / judge dispatch block - they never touch the cache or the judge, so they cannot perturb `new_judgments`/cache-hit behavior. Confirmed by inspection and by the existing `rerun_is_cache_hit_stable_zero_new_judge_calls` test remaining green untouched.
